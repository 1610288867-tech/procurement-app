## 三、十一个阶段各自解决了什么

**M0 准备与设计定稿**（2026-10-01）：四份设计产物定稿（ER 图 / 业务规则 / 金额-审批链对照表 /

金额→审批链对照表被明确写成"需求文档 + 测试用例 + 验收标准"三合一，M6 直接拿它当参数化测试。

**M1 骨架贯通**（2026-10-02）：用「供应商」（4 个字段、无状态机）把
表 → ORM → 仓库 → 协调者 → 路由 → 页面 这条链路完整走通一次，并定死三样东西：统一错误体
`{"error":{code,message,request_id}}`、结构化 key=value 日志、仓库只 `flush()` 不 `commit()`。
后面 9 个阶段都是照这个模板扩展。

**M2 主数据**（2026-10-02）：部门 / 品类 / 供应商 / 预算四类主数据落地。最关键的是给两个 JSONB

M6 可达性，因为"结构合法但语义错误"的策略不会报错，只会让申请以更低层级被批准。

**M3 账号与权限**（2026-10-02）：8 个角色能登录（7 个人），JWT 双令牌放 httpOnly Cookie，

**M4 前端设计系统**（2026-10-02，10-04 二次打磨）：在页面还只有六个的时候把设计令牌

**M5 采购申请**（2026-10-02）：草稿 / 明细 / 提交 / 撤回 / 丢弃 + **幂等** + **乐观锁**。

## 四、面试官最可能追问的 25 个「技术决策点」

**1. 并发一律用条件更新，不用"先查再写"**
- 替代方案：`SELECT` 余额再判断；`SELECT … FOR UPDATE` 显式锁行；调高事务隔离级别。
- 为什么选它：一条 SQL 同时完成"判定 + 扣减"，不需要显式锁，也不会因为漏写判断而超支；
  `rowcount != 1 → 409` 这一句在项目里出现六次，每次挡的都是"重复扣款 / 重复付款"。
- 代价/风险：失败方拿到的错误信息天然是"受影响行数为 0"，必须**失败后强制重读**才能把原因说成人话。

**2. 幂等用"占位行 + 独立提交"，不是"查不到就执行"**
- 替代方案：只查 `(actor,scope,key)` 存不存在；依赖客户端不重试。
- 为什么选它：两个请求带同一把 key **同时**到达时，双方都查不到记录，于是双双执行——幂等失效且静默。
- 代价/风险：占位行必须独立事务提交，否则业务回滚会把它一起带走；过期清理是"120 秒过期即删、
  每次请求顺带跑一次"，长期没请求时卡住的行会一直留着（自认真债）。

**3. `(actor, scope, key, payload_hash)` 四元组，scope 用端点标识**
- 替代方案：只用 key；scope 留空。
- 为什么选它：同键同载荷重放返回原响应，同键不同载荷 409；scope 含糊会让同一把 key 在"提交"与
  "撤回"之间串味，第二次请求拿到第一次的响应而看起来一切正常。
- 代价/风险：payload_hash 的计算口径要跟着请求体演进走（文档没展开这一点，属**盲点**）。

**4. 乐观锁把 `version` 和 `status` 一起放进 `WHERE`**
- 替代方案：只比 `version`；用 `updated_at` 比对。
- 为什么选它：一条语句同时挡住"版本过期"和"状态不对"两种冲突。
- 代价/风险：条件更新后会话里缓存的对象仍是旧值，必须 `populate_existing=True` 回读（踩了四次）。

**5. 审批链是纯函数（`resolve_approval_chain`）**
- 替代方案：边写接口边算；硬编码 if/else 按金额分支。
- 为什么选它：四条金额对照表直接当参数化输入，20 条纯函数测试跑 0.07 秒；改策略不改代码。
- 代价/风险：请求上下文里的键名（`amount_fen`）成为隐式契约，写错不报错只静默降级。

**6. 审批规则存在品类上，用受限 JSON DSL 表达**
- 替代方案：规则写成代码；规则放独立表 + 管理界面。
- 为什么选它：金额阈值是**数据**，M6 验收里"改品类策略不改代码、审批链跟着变"测的就是它。
- 代价/风险：必须额外做路径白名单 / 整数分 / 零阈值兜底三条语义校验，否则错误策略静默生效。

**7. "当前轮到谁"只存一处：`approval_flows.current_step_order`**
- 替代方案：给 `approval_tasks.status` 加一个 `WAITING`（设计里原本就有 `DELEGATED`）。
- 为什么选它：一个概念只存一处；两份状态必然漂移，漂移出来的数据比原问题更难查。
- 代价/风险：`SKIPPED` 留在词表却没触发路径（策略重修审批链才用得上），属有意留的坑。

**8. 任务一次全建出来，但只有当前级是活的**
- 替代方案：逐级建任务（上一级批完再建下一级）。
- 为什么选它：进度能一眼看全，`ApprovalTimeline` 能直接画"已完成 / 当前 / 未开始"三态。
- 代价/风险：待办查询与决定接口都必须加 `step_order = current_step_order`，漏一处就出现
  "越级可见 + 越级可批"，而且**点了真的会生效**。

**9. 推进指针用条件更新 + 流那一行取行锁**
- 替代方案：先读再写；给 flow 表加版本号；串行化整个事务。
- 为什么选它：跨事务看不见对方未提交的改动，两人同时通过同一级的两个会签任务时谁都不推进；
  行锁把"判定 + 推进"变成串行临界区，且锁在**单个申请**的流上，不同申请互不影响。
- 代价/风险：这是 M6 卡最久的一处（约 60 分钟），先误判成"读缓存对象"。

**10. 主单与审批两层状态用事件解耦**
- 替代方案：审批模块直接改 `purchase_requests.status`。
- 为什么选它：将来加"补充式驳回"之类新流程才不会把代码搅成一团。
- 代价/风险：多一跳，排查时要顺着事件表看（探针专门断言"恰好两条状态迁移"）。

**11. `policy_snapshot` 存提交那一刻的策略原件**
- 替代方案：存品类 id，事后现查策略。
- 为什么选它：现查等于拿今天的规则解释三个月前的申请；成本一列 JSONB，收益是审批链可复现可解释。
- 代价/风险：策略结构演进时快照的兼容性没被讨论（**盲点**）。

**12. 预算流水 `UNIQUE(request_id, kind)`**
- 替代方案：只改 `budgets` 上那三个数字；靠幂等表兜住重复。
- 为什么选它：三个数字说不清"为什么是这个数"；唯一约束顺手把"重试重复扣钱"变成一次可见的冲突。
- 代价/风险：`kind` 只有三种，将来加"预算调整流水"要动约束（**盲点**）。

**13. `settle()` 把两步封成一个不可分割的方法**
- 替代方案：付款接口里写 `spend_budget` + `release_budget` 两次调用。
- 为什么选它："差额必须显式释放"这条规则在**新的调用点自动成立**；M7 封好、M10 只接一个调用。
- 代价/风险：算术一旦写错，账面完全正常只是可用额度永久虚低，只能靠断言撞。

**14. `budget_id` 在提交那次条件更新里一起写死**
- 替代方案：提交后再 `UPDATE` 一次认领预算；每次用的时候按部门 × 品类 × 年度现查。
- 为什么选它：少一次写、少一个中间状态；"这笔申请占的是哪条预算"从推断变成事实。
- 代价/风险：部门 / 品类调整后旧单仍绑旧预算（这正是设计意图，但演示时容易被误解）。

**15. 部分收货被砍掉，连状态一起砍**
- 替代方案：允许收一半、主单停在 `ORDERED`；加 `PARTIALLY_RECEIVED` 状态。
- 为什么选它：状态机里没有那个状态，"收一半"就无处安放——硬做会造出"订单已收货 + 主单还在
  ORDERED"这种模型禁止的组合，而且走不到任何终态。
- 代价/风险：要恢复必须按实施计划 5.5 节 E 的四步把状态、转移、主单判定、验收项**一起**加回来。

**16. 订单明细是快照复制，`item_id` 刻意不加外键**
- 替代方案：订单明细外键指向申请明细。
- 为什么选它：订单一旦生成就是独立凭证；申请明细是覆盖式替换的，不该带走历史订单（可能已付过款）。
- 代价/风险：数据冗余，且"申请改了订单不跟着改"要靠文档纪律而不是数据库保证。

**17. 三单匹配返回问题列表，不是布尔值**
- 替代方案：返回 `False`；用"挂起 + 异常任务"。
- 为什么选它：布尔值只能说"失败了"，问题列表能说清"哪里不对、差多少"；前端一个组件渲染三种差异
  （`check_awardable` / `receipt_problems` / `precheck_three_way` 形状一致）。
- 代价/风险：问题列表的 `code` 成为跨层契约，前端硬编码 code 就会随后端演进漂移（**盲点**）。

**18. 匹配粒度定死"订单级 + 先求和再比"**
- 替代方案：明细行级匹配（能发现"甲行多收、乙行少收"）。
- 为什么选它：`match_three_way` 签名全是标量，明细行级要三张表逐行对齐 + 数量拆分，是另一个量级；
  先订单级跑通，M10 不会在"按行还是按单"上耗掉两天。
- 代价/风险：行级不一致查不出来；签名保持标量是为了让粒度成为"可替换的决策"。

**19. 容差用整数万分比 `TOLERANCE_BP = 200`，不是 `int(amount * 0.02)`**
- 替代方案：`TOLERANCE_RATIO = 0.02` 浮点乘（领域设计附录 A.5 原文就是这么写的）。
- 为什么选它：`0.02 × 2500 = 50.000000000000007` 恰好落在边界上；整数万分比让边界可解释。
- 代价/风险：比例部分**向下取整**（容差只可能偏小），方向选严的一侧——小额单会被更严地卡。

**20. 三单匹配跑在"执行付款"，不是创建付款单**
- 替代方案：登记发票时校验；创建付款单时校验。
- 为什么选它：执行付款是唯一真正动钱的时刻，也是唯一能保证"校验通过后单据没再被改"的时机。
- 代价/风险：预检接口必须严格只读（文档专门有一条验收：连跑 3 次版本与事件数不变）。

**21. `pay` 的顺序：先抢付款权，再动预算**
- 替代方案：先 `spend_budget` 再改 `payments.status`。
- 为什么选它：抢输的一方在动钱之前就退出了；反过来两个请求会**各动一次预算**，回滚只能救一个。
- 代价/风险：顺序写反不会立刻暴露，只在真并发下表现为重复记账。

**22. `payments` 用部分唯一索引 `WHERE status <> 'FAILED'`**
- 替代方案：`UNIQUE(request_id)`（领域设计与 ER 图原文的写法）。
- 为什么选它：判据是"这条约束防的是**同时存在两条**，还是**历史上出现过两条**"——前者用部分索引。
  普通唯一约束会把合法的重试一起防掉，而且表现为一个数据库冲突，看起来像偶发故障。
- 代价/风险：`attempt_no` 让失败行不断累积，界面上要看得懂"试过两次"。

**23. 附件校验是四层，且 `verify()` 之后必须再 `load()`**
- 替代方案：只校验扩展名；只校验 magic bytes；只调 `PIL.Image.verify()`。
- 为什么选它：前三层各自的绕过手法都是教科书级的（改名 / 伪造头 / 头对内容假）；本机实测
  `verify()` 拦不住截断的数据流。压缩炸弹防线放在解码**之前**（先读 IHDR 尺寸再决定要不要 `load()`）。
- 代价/风险：`Pillow` 成为全项目唯一的重依赖，被关在 `infrastructure/image_probe.py` 一个文件里，
  domain 通过回调拿"能不能解码"。

**24. `Content-Type` 只做兜底、绝不做判定**
- 替代方案：`application/octet-stream` 一律 422。
- 为什么选它：octet-stream 不是"另一种类型"而是"**没告诉我**"——`python-multipart` 对没带类型的部分
  就填它，`curl -F` 对 PDF 也送它。拒掉它挡的是工具而不是攻击者（攻击者会老实写 `application/pdf`）。
- 代价/风险：兜底必须**只在声明缺失时**启用，且补出来的类型照样过 magic bytes 与真解码；
  顺序写反会让"声明 pdf + 文件名 .txt"被当纯文本收下（M11 真踩过一次）。

**25. 权限判据必须在"建"和"办"两侧同源**
- 替代方案：建链时按部门挑人、办事时看角色名（M9 之前的实际状态）。
- 为什么选它：两处判据不一致是最难发现的越权形态——中间没有任何一步会报错。修法不是新造规则，
  而是复用 `domain/permissions.resolve_request_scope`（申请列表、待办、决定三处同源）。
- 代价/风险：会签那一支**刻意不加**部门判定（候选人本来就是建链时按部门挑的），
  再卡一次只会制造"被指派了却批不了"的死结——这条写进代码注释，免得以后被"顺手补齐"。

## 五、真实踩过的坑（按"最容易问出来"排序）

> 全部来自 PROGRESS.md / Development progress.md 的实测记录。

**1. 条件更新之后，内存里的对象还是旧值**（M5/M6/8.1/8.2 共四次）
- 现象：写成功了但读到的还是旧值——"提交成功、响应里却还是 DRAFT"；定标后"主单还是 SOURCING、
  选中的那家还是 SUBMITTED"；收货后"响应里收齐了显示成没收齐、订单状态显示成 ORDERED"。
- 根因：bulk `UPDATE`（`synchronize_session=False`）不刷新会话里已加载的对象，而它在身份映射里，
  普通查询会把它原样还回来；`select(Model.col)` **也一样**会经过身份映射。
- 修法：回读加 `populate_existing=True`（做成默认关闭的显式参数）；M5 那次最终解法是**回读另开一个会话**。
  中途还误用 `expire_all()`，在异步会话里抛 `MissingGreenlet` 并被 503 处理器当成"数据库不可用"。
- 不修会怎样：所有"改完立刻回读"的接口返回自相矛盾的响应，用户以为操作没生效而重复操作。

**2. 同事务内多条事件的时间戳完全相同，顺序退化成 UUID 随机比较**（M6 发现，M8 修）
- 现象：时间线里"提交"与"生成审批链"顺序颠倒；预算流水里 `SPEND` 与 `RELEASE` 顺序颠倒。
  全量测试 5 轮里失败 2 轮，两个不同用例、同一根因。
- 根因：PostgreSQL `now()` 返回**事务开始时间**，同一事务写的多条记录时间戳完全相同；
  M6 改成应用侧微秒时间戳只把概率压小、**没有消除**（`datetime.now(UTC)` 仍可能落在同一微秒）。
- 修法：迁移 `b7d3f0c41a26` 给 `request_events` 与 `budget_transactions` 各加 `seq BIGINT
  GENERATED BY DEFAULT AS IDENTITY`，排序改用它，`created_at` 只用于显示。迁移三步走：加可空列 →
  按原排序键回填并推进序列 → 补 `NOT NULL`。
- 不修会怎样：时间线顺序偶发错误，且**只在全量连跑时才出现**，单跑永远是绿的。

**3. 跨事务看不见对方未提交的改动，并发推进指针谁都不动**（M6，卡 ~60 分钟）
- 现象：两人同时通过同一级的两个会签任务，指针停在原地（应该推进一级）。
- 根因：每个请求一个会话 + 默认隔离级别，双方都看到对方还是 `PENDING`，于是都判"这一级还没完"。
- 修法：在流那一行取行锁（`SELECT … FOR UPDATE`），把"判定 + 推进"变成串行临界区。
  锁粒度锁在单个申请的流上。
- 不修会怎样：审批流永久卡在当前级，且没有任何报错。

**4. 提交人的 `Content-Type` 被自定义头静默覆盖**（M3 起存在，M5 暴露，藏了两个阶段）
- 现象：提交/撤回接口 422，报 `"Input should be a valid dictionary or object to extract fields from"`；
  后端直连测试**通过**，只有浏览器发出去的请求才失败。
- 根因：`client.ts` 的 `send()` 里 `...init` 写在 `headers` 之后，把默认的
  `Content-Type: application/json` 整个顶掉，后端于是按表单解析。
- 修法：调整展开顺序；教训是"对象展开的顺序不是风格问题，是语义问题"。
- 不修会怎样：**只有带自定义头的接口会中招**（提交/撤回要带 `Idempotency-Key`），
  所以它藏了整整两个阶段，而且看起来像后端 bug。

**5. 回归入口自己有个"假通过"缺陷**（M8 抓到）
- 现象：`pytest` 明明输出 `1 failed, 221 passed`，入口仍标 ✓ 并给出退出码 0。
- 根因：`Invoke-Step` 在函数作用域读 `$LASTEXITCODE`，而外部命令是在 `& $Body` 的**子作用域**里跑的；
  函数里那句 `$LASTEXITCODE = 0` 又在本作用域建了副本，比较的永远是 0。
- 修法：退出码检查放进**每个脚本块内部**（与外部命令同作用域），失败即 `throw`；
  已用 `cmd /c exit 7` 单独验证这条判据能捕获失败。
- 不修会怎样：**回归入口本身也会坏，而且它坏了会让人以为一切正常**——M8 的结论会直接失真。
  修好之后第一次跑，它立刻报出全量测试的偶发失败（即坑 #2）。

**6. `IntegrityError` 只是一种异常，不是一种原因**（M8）
- 现象：7 条预算用例全挂在一句"这笔申请已经有一条 RESERVE 流水"上，指错方向整整一轮。
- 根因：把 `created_at` 从应用侧挪给数据库时，`budget_transactions.created_at` **没有数据库默认值**
  （`request_events` 那一列有 `now()`），触发的是 `NOT NULL` 违约——而违约发生在 `flush()` 里，
  正好被 `_append` 的 `except IntegrityError` 接住。
- 修法：包装 `IntegrityError` 时不要丢掉 `orig`，转换错误码时不要把底层原因盖掉。
- 不修会怎样：唯一约束与 NOT NULL 的报错长得一样，每次都要重新挖一遍。

**7. 跨部门真实越权面：审批待办与审批决定缺部门范围**（M9 发现并修，P1）
- 现象：`test_all_mode_creates_one_task_per_person_and_needs_all` 断言"会签人待办里只有自己那一条"，
  实得 4 条。**第一次归因是"测试数据脏了"，这个归因是错的。**
- 根因：`DEPT_MANAGER` / `DEPT_HEAD` 是部门级角色，建链时引擎按部门范围挑了人（`_department_scope`），
  但"办的时候"只校验角色名。于是**财务部的部门负责人能看到、也能批掉行政部那张单子的「部门负责人」那一级**。
- 修法：`list_todo` 加 `*_scope_conditions(scope, actor_id=...)`（与采购仓库**同一个函数**）；
  `_assert_can_act` 在或签那一支补部门判定；会签那一支刻意不加；部门只从登录态取；
  `get_task_detail` 同步收紧。三条新用例**先写成"应当失败"**再改实现。
- 不修会怎样：**这个 bug 的可见性依赖数据巧合**（开发库里恰好没有"另一个部门停在同一级"的单子），
  而不是依赖任何一道防线。全量 313 → 316 passed。

**8. SoD（职责分离）整整一类要求从未被设计过**（M6 验收全过之后才发现）
- 现象：**申请人能批掉自己的申请**（实跑复现：`APPROVED`、指针 10→20）。
- 根因：M0 定稿角色表时只回答了"谁能做什么"，没回答"谁不能做什么"。全库搜索确认
  **设计文档里一个 SoD 字眼都没有**；M6 的 15 条验收里也没有一条涉及"谁不能审什么"。
- 修法：补的是**文档先行**——SoD 写进 `业务规则.md` 第 9 条与领域设计 2.1，修法才有依据可对；
  然后落成三层拦截。**只做建链那一层是不够的**：或签任务 `assignee_id` 为 NULL、只按角色可见，
  第一层挡不住它——这个洞是写测试时才暴露的。
- 不修会怎样："验收全过"不等于"业务对"；**验收项是从设计来的，设计漏了，验收就一起漏。**

**9. 主单状态 CHECK 忘了加 `AWARDED`，报错却是"数据库暂不可用"**（M10/8.1）
- 现象：定标返回 **503「数据库暂不可用，请稍后重试」**——完全指错方向（数据库好得很）。
- 根因：撞 `ck_request_status_known`（那条 CHECK 还是 M6 的六个状态），
  `CheckViolationError` 经过应用层的 `SQLAlchemyError` 处理器之后被折叠成 503。定位绕了三层，
  最后**写一个探针直接调协调者**，并给 `Session.flush/commit` 挂上打印 `exc.orig` 的钩子才看到真身。
- 修法：新增状态必须与改 CHECK 同一次改动（模型里的 `KNOWN_REQUEST_STATUSES` 与迁移一起），
  已在两处注释里写死这条提醒。同类共踩三次（`AWARDED` / `ORDERED`+`RECEIVED` / `INVOICED`），
  M10/8.4 是第四次——**Alembic 看不见 CHECK 约束的内容变化**，这是工具的能力边界不是偶发失误。
- 不修会怎样："数据库暂不可用"这句话本身不含信息，排障要靠一次性探针把它挖回来。

**10. 惰性结算写完不提交 = 白写（而且是静默的）**（M10/8.1）
- 现象：界面上永远看不到 `EXPIRED`，而判定（只认时间）又是对的，谁也说不清那行到底算不算数。
- 根因：`GET /requests/{id}/quotations` 里顺手把过期报价结算掉，但**忘了提交**，
  请求结束时会话回滚，结算结果被丢掉。
- 修法：把"结算 + 读"合成**唯一入口** `quotations_ready()`（先 `expire_overdue`，有改动就提交，再读），
  比价表与定标都改走它；装配收进 `build_sourcing_coordinator`（边界层与测试共用同一份）。
- 不修会怎样：**报表是按状态列数的**——判定对、投影落后，统计就会错，而且错得不报错。
  留下的边界写清楚了：绕过协调者直接 `SELECT status` 依然可能读到过时的行，**不是数据库级保证**。

**11. 派生字段靠响应模型自己解析，读写各说一套**（M10/8.2）
- 现象：**同一张收货单，写接口说"收齐了"、读接口说"没收齐"。**
- 根因：`receipt.fully_received` 不是表上的列，是判定结果；读接口用 ORM 记录直接喂 Pydantic，
  它退到字段默认值 `False`。
- 修法：响应体由协调者算好（`_receipt_payload`），读写两条路共用同一份；并且
  `ReceiptOut.fully_received` **不给默认值**——少给一个字段就当场报错。
- 不修会怎样：这个标志是**下游付款的闸门**，说反了后果最重。

**12. `fully_received` 按"当前主单状态"判定，会随时间倒退**（M10 前端阶段发现）
- 现象：订单详情页收票之后**突然说"没收齐"**，而仓库明明收齐了。它当时测试是绿的
  （另一条用例只在 `RECEIVED` 那一刻看了一眼）。
- 根因：判据写成"当前主单状态是不是 `RECEIVED`"，而收齐之后主单会继续往前走（收票 → `INVOICED`）。
- 修法：正确判据是"这张申请有没有收货单"（第一版只做整单收货，有单就等于收齐）；
  加回归 `test_fully_received_does_not_go_backwards_after_invoicing`。
- 不修会怎样：状态往前走一步，历史判定就翻一次，界面自相矛盾。

**13. `fetch` 里写 `Content-Type: ""` 不等于"没设置"**（M9）
- 现象：页面上传挂住 12 秒，后端报 `422 file: Field required`（完全指错方向）。
- 根因：浏览器会真的发一个空头，multipart 解析失败。**单元测试与接口测试都碰不到它**，
  因为它们不走浏览器的 fetch。
- 修法：`Headers.delete("Content-Type")`。三种写法对比实测：`""` → 422、不传 headers → 201、
  `delete` → 201。
- 不修会怎样：光看"上传按钮点了没反应"永远查不出来；这是**页面实测**抓出来的。

**14. `PIL.Image.verify()` 拦不住截断的数据流**（M9）
- 现象：第一版以为 `verify()` 就是"真解码"，实际它只校验结构 / CRC，不读像素——
  PNG 只校验各 chunk 的 CRC，JPEG 的扫描数据它根本没碰。
- 根因：`verify()` 的语义是"校验文件完整性"，不是"解码"。
- 修法：`verify()` 之后**必须再 `load()` 一次**；本机实测五种损坏构造文件的结果写进了
  `image_probe.py` 的模块注释，并由 `test_image_probe.py` 钉住。
- 不修会怎样：会写出一个"看起来有压缩炸弹防护、实际漏一半"的上传接口。

**15. 单元测试的替身解码器比被测边界松，绿色是假的**（M9）
- 现象：第一版 `fake_png` 只判"开头是 PNG 头"就返回尺寸，于是"PNG 头 + 一句废话"被判成合法图片——
  **那条用例其实什么都没验**（它测的还是第 4 步）。是 `DID NOT RAISE` 这个失败把它暴露出来的。
- 根因：替身比真实边界宽松。
- 修法：不是改断言，而是让替身**至少比 magic bytes 严一档**（要求出现 `IEND` 收尾块）。
- 不修会怎样：整套上传校验的单测全绿而毫无保证。

**16. 容差写浮点会恰好落在边界上**（M10/8.3）
- 现象：`int(amount * 0.02)` 在 `0.02 × 2500` 上得到 `50.000000000000007`，恰好落在 50 元边界。
- 根因：浮点乘法。项目硬约束本来就禁止 float，这里是它**真正救到人**的一次。
- 修法：比例存成万分比整数 `TOLERANCE_BP = 200`，全程整数乘除；专门一条用例
  （`test_tolerance_arithmetic_is_integer_and_has_no_float_error`）把这个数钉住。
- 不修会怎样："差 1 分算不算超容差"这种没法向用户解释的问题。

**17. 拿"申请金额"当匹配基准是个陷阱**（M10/8.3）
- 现象：申请 5800 元、订单 240 元（询价压价），拿申请金额当基准，这笔单子会**一律判成不匹配**。
- 根因：差额其实由 M7 的"实付小于预留则显式释放"处理，基准**只能是订单金额**。
- 修法：用 `test_amount_basis_is_the_order_not_the_request` 钉住它。
- 不修会怎样：**每一笔走询价的单子都付不出去**，而且不报错，只表现为"发票金额超容差"。

**18. `precheck_three_way` 与 `match_three_way` 必须分两层**（M10/8.3）
- 现象：A.5 的函数是标量对整单，没法表达"压根还没有订单"——传 0 进去会得到
  "发票金额 0 与订单金额 24000 相差 24000，超出容差"，**指错方向**。
- 根因：结构性判断（`NO_ORDER` / `NO_INVOICE`）和数值判断混在一层。
- 修法：结构性判断放外层，三条匹配规则仍只有 A.5 那一份实现。
- 不修会怎样：**指错方向的报错比不报错更贵**——它会让人去查一个不存在的问题。

**19. 全部发票作废后报的是 `AMOUNT_MISMATCH` 而不是 `NO_INVOICE`**（M10/8.3 补）
- 现象：拿"登记条数 > 0"判有没有发票，会得到"金额差超容差"。
- 根因：真正的原因是"一张有效发票都没有"；登记条数不是"有效张数"。
- 修法：判据收在 `domain/settlement_policy.voidable(...)`，只看有效发票。
- 不修会怎样：财务按报错去查金额，实际上该去重开发票。

**20. 付款失败方拿"请求开始时的预算快照"解释原因**（M7）
- 现象：并发用例拿到 `[200, 409]` 而不是 `[200, 422]`；失败方算出"钱明明够啊"，
  于是本该是 422"预算不足"的响应退化成一句含糊的 409。
- 根因：判定由条件更新做（正确），但**解释**用了请求开始时的旧数字。
- 修法：**失败后强制重读**（`populate_existing=True`）再算差额。**判定与解释必须分开**：
  判定只由条件更新做，解释才允许读库。
- 不修会怎样：并发冲突的用户看到的是"冲突"而不是"预算不足"，不知道该怎么自救。

**21. 重复版本报 503 而不是 409，异常被推迟到"无关的 SQL"上才炸**（M11）
- 现象：上传同一份制度第 2 版 → **503「数据库暂不可用」**（数据库好得很）。
- 根因：`create_doc` 的 flush 被推迟，`UNIQUE(source_key, version)` 的异常从后面"插入片段"
  那条语句冒出来，`except IntegrityError` 接不住。
- 修法：两层——**显式查重**给一句人话的 409 + 在 `create_doc` 里**显式 flush**
  （让异常在最接近它原因的地方抛出）；并发仍由唯一约束兜底。
- 不修会怎样：用户看到的方向完全错，且这是同一类"报错被折叠"的第 N 次。

**22. 前端 `done` 事件没回调出去**（M11，由浏览器实测脚本发现）
- 现象：页面永远停在"正在回答…"，光标一直闪。
- 根因：`streamAnswer` 的 `emit()` 在 `done` 分支只置了 `closed = true`，从未调 `handlers.onDone()`。
- 修法：补上回调；并补上 `GET /sessions/{id}/messages` 的历史回放面板
  （该页**没有读历史消息**，标了句"不假装能回放"——那是**没做完**，不是取舍）。
- 不修会怎样：SSE 每一条 delta 都对，只有"结束"这件事永远不发生。

**23. 测试隔离：admin 是共享账号，`World.purge` 按 `uploaded_by` 删 = 删掉所有用例的文档**（M11）
- 现象：空库用例看到 1 条来源、版本过滤用例同时命中 1 和 2 两版。
- 根因：admin 被所有用例共用，"按账号删"等于"把所有用例的文档都当自己的"。
- 修法：**两种条件都删**（按账号 + 按本用例的 `source_key`）。
- 不修会怎样：漏删的表现是下一条用例看到上一条的数据，归因方向会跑到产品上。

**24. 清理脚本与测试不能同时跑**（M11）
- 现象：两条用例在并发下失败；串行重跑全绿。
- 根因：一边跑全量 `pytest`、一边让子代理跑清理脚本，清理脚本把测试正在用的数据删了。
- 修法：串行。教训：**清理脚本与测试的判据天然冲突。**
- 不修会怎样：偶发失败被误当成并发缺陷，白查很久。

**25. 测试脚本的报错质量决定调试速度的上限**（M10，为同一个脚本重跑 6 轮）
- 现象：点链接没反应 / 找不到「通过」按钮 / 第一次点付款没反应……每一次都**长得像产品 bug**。
- 根因：真因全在测试侧或数据侧——等了一个会消失的渲染状态、在列表还没渲染完时点它、
  或签级没先认领、选择器撞上两个同样的 placeholder、**上一步没等完就点下一步**
  （第一次点击时按钮还是"创建中…"）、提交人选错导致自审 422。
- 修法：让 `waitFor` 超时时打印 **URL + 页面文字 + 按钮清单**，一次就把现场摆出来；
  每一步以"那一步的完成信号"（按钮回到可点状态）为准，而不是以"某段文字出现"为准。
- 不修会怎样：**先怀疑产品而不是先怀疑时序**，绕三圈。

## 六、并发与一致性相关的具体机制

| 机制 | 关键字 / 落点 | 用在哪 · 解决什么 |
| --- | --- | --- |
| **条件更新（守卫条件进 `WHERE`）** | `amount_total - (amount_reserved + amount_spent) >= :amount`；`rowcount != 1` / `.returning(id)` | 预算预留（`budget_repo.reserve`）、审批决定（`decide`/`claim`）、指针推进、定标抢权（`mark_awarded`）、付款抢权（`PENDING → PAID`）、发票作废（`WHERE status='ACTIVE'` + `RETURNING`）。挡的是"重复扣款 / 重复付款 / 越级审批"。 |
| **乐观锁** | `version` 与 `status` **一起**放进 `WHERE`，`values(version = version + 1)` | 主单编辑 / 提交 / 撤回；明细保存；任务决定。`rowcount != 1 → 409`。 |
| **行锁串行化临界区** | `SELECT … FOR UPDATE`（锁在 `approval_flows` 那一行） | 会签级"判定 + 推进指针"。解决跨事务看不见未提交改动导致指针不推进。锁粒度只有单个申请。 |
| **幂等键 + 占位行** | `idempotency_records(actor_id, scope, key, payload_hash, status IN_PROGRESS/COMPLETED/FAILED, response)`；`UNIQUE(actor_id, scope, key)`；占位行**独立事务提交** | 全部写操作（提交 / 撤回 / 定标 / 下单 / 收货 / 登记发票 / 付款 / 归档）。同键同载荷重放返回原响应，同键不同载荷 409，撞上 `IN_PROGRESS` 409。 |
| **唯一约束兜底** | `budget_transactions UNIQUE(request_id, kind)`；`quotations UNIQUE(request_id, supplier_id)`；`budgets UNIQUE(department_id, year, category_id)`；`idempotency_records UNIQUE(actor_id, scope, key)` | 把"重试重复扣钱 / 同一家报两次价"从静默错误变成一次可见的冲突。 |
| **部分唯一索引** | `uq_payment_active ON payments (request_id) WHERE status <> 'FAILED'`；`invoices` 的号 `WHERE status = 'ACTIVE'` | 保证"**至多一条有效**付款单/发票号"，同时不堵死合法重试与"录错号 → 作废 → 重录"的纠错路径。 |
| **只追加（append-only）** | `request_events`、`budget_transactions`、`audit_logs` 永不 UPDATE / DELETE；附件只 `soft_delete`；发票作废是状态变更不是删行 | 审计与时间线的可信度。删除只标记（`deleted_at` / `VOIDED`）并写事件。 |
| **单调序号列** | `seq BIGINT GENERATED BY DEFAULT AS IDENTITY`（迁移 `b7d3f0c41a26`） | 只追加日志的**排序**。`created_at` 同事务内可能相同，排序会退化成 UUID 随机比较。 |
| **CHECK 约束兜底** | `budgets`：`amount_reserved >= 0 AND amount_spent >= 0 AND amount_reserved + amount_spent <= amount_total`；`request_events` 等表的状态白名单 CHECK；`budget_transactions.amount > 0` | "应用层的判断总有一条路径是你没想到的"。 |
| **外键语义区分** | `budget_transactions.budget_id` 用 RESTRICT（有流水的预算行不许被删）、`request_id` 用 CASCADE（流水是申请的从属数据） | 数据生命周期。同类的还有 `purchase_order_lines.item_id` **刻意不加外键**（快照复制）。 |
| **权限写进 `WHERE`** | `resolve_request_scope` / `_scope_conditions(scope, actor_id=...)`，申请列表 / 待办 / 决定三处同源 | 可见范围外 → 404，可见但无权 → 403。杜绝"先查出来再判断能不能看"。 |
| **失败关闭（fail-closed）** | 空审批链 → 422 `EMPTY_APPROVAL_CHAIN`；缺审批人 → 422；计划外（无预算行）→ 422 `NO_BUDGET`；超预算 → 422 `BUDGET_INSUFFICIENT`；自审只剩自己 → 422 `SELF_APPROVAL_NOT_ALLOWED` | 宁可挡住并说清原因，也不留静默的豁免路径。 |
| **判定与解释分离** | 判定只由条件更新做；失败后**强制重读**（`populate_existing=True`）再算人话 | 并发失败响应从含糊的 409 变成准确的 422。 |
| **条件更新后回读必须显式刷新** | `populate_existing=True`（默认关闭的显式参数） | 身份映射缓存旧对象（踩了四次）。 |
| **同一事务** | 事务边界只在 `application/coordinators/`；仓库只 `flush()` | "推进状态 + 预留预算 + 写事件 + 写幂等记录"任一步失败整体回滚（失败那笔仍是草稿、`budget_id` 为空、无流水）。 |
| **惰性结算的唯一入口** | `quotations_ready()` = 先 `expire_overdue`（有改动就提交）再读 | 让"忘掉结算"从"每处都要记得"变成"绕不过去"。**明确不是数据库级保证。** |

### 上传与下载安全

- 六步校验，**顺序不可调**：① 申请存在且属于当前用户 → ② 大小 ≤ 10 MB → ③ 类型白名单 →
  ④ magic bytes 与声明一致 → ⑤ 图片**真解码**（含解码前的像素上限）→ ⑥ SHA-256 存元数据。
  **先校验、后落盘**（11 MB 被拒时落盘目录仍为空）。
- 附件一律 **UUID 键 + 两层目录**落盘，**永不用用户提供的文件名**（防 `../../app/main.py` 路径穿越）。
- `uploads/` **不挂静态目录**；直连 `/uploads/<文件名>` → **404**；**拿到真实存储文件名也一样 404**。
- 下载强制 `Content-Disposition: attachment` + `X-Content-Type-Options: nosniff`；
  `content_type` 用**入库时校验过的那一个**；中文名走 `filename*=UTF-8''…` + ASCII 兜底。
- 越权下载 → **403**（附件存在但看不到它挂的申请）；不存在 → 404。
- 删除是**软删除**（只写 `deleted_at`，磁盘文件留着）+ 时间线写 `ATTACHMENT_REMOVED` + 界面二次确认。
- 磁盘与库的一致性顺序：**先发键 → 再落盘 → 后写库**（`ObjectStore.new_key()` 单独存在就是为此；
  反过来会留下"库里有记录、文件不存在"的附件，点下载必然 500）。

### Token 机制与 CSRF 三道防线

- Argon2id 口令哈希（校验失败一律 `False`，不把异常抛给登录接口）。
- JWT 双令牌放 httpOnly Cookie；`SameSite=Lax`；`secure=False`（本地 http，上 HTTPS 时改 True —— 真债）。
- CSRF 三道：`SameSite=Lax` 挡跨站 POST/PUT/PATCH/DELETE + refresh Cookie 限定 `Path` +
  **所有写操作要求 `Idempotency-Key` 自定义头**（浏览器不会跨站自动带自定义头）。
- `token_version`：冻结账号时 `+1`，签发与校验都比对 → 旧 token **立即失效，不用维护黑名单**；
  **刻意不做 refresh token rotation**（同一件事不叠两套机制）。
- 登录失败的响应必须**一模一样**（区分"用户不存在"与"密码错误"等于免费提供账号枚举接口）。
- 前端拿到 401 自动续期一次并重放请求，**并发的多个 401 只续一次**；续期失败就认输、不循环。
- 前端菜单按 `me.roles` 自判（`App.tsx`），**后端始终是最终边界**；口径是"继续前端自判，
  8 角色规模下不引入后端权限清单下发"。

### SoD（职责分离）落地状态

| 不相容岗位 | 本项目 | 状态 |
| --- | --- | --- |
| 请购与审批 | **三层拦截**：① 建链剔除提交人（`exclude_requester`，该级只剩他则 422 `SELF_APPROVAL_NOT_ALLOWED`）② 待办查询 `requester_id != actor_id`（挡**或签**）③ `decide`/`claim` 的 SQL `NOT EXISTS` + `_assert_can_act` 403 | ✅ |
| 询价与核价、确定供应商 | **v1 不分离**，靠"≥3 家有效报价 + 供应商合格 + 报价完整 + 记成交单价"兜底 | 🟡 已定稿取舍 |
| 合同订立与审核 | 项目无合同环节 | ⚪ 范围外 |
| 采购、验收与会计记录 | `PROCUREMENT` / `RECEIVER` / 系统记录三方分离 | ✅ |
| 付款的申请、审批与执行 | **v1 不拆出纳**（`FINANCE` 同时审核与付款），靠"三单匹配 + 状态机"兜底 | 🟡 已定稿取舍 |

**skip** 而不是"显示但禁用"）、OWASP 授权清单（最小权限 / 默认拒绝 / 每个请求都校验 /
**客户端校验绝不能作为放行依据**）。（采购内控对照.md 一）

### 三条分层自查是什么

```powershell
Select-String -Path backend\app\domain\*.py -Pattern "import (fastapi|sqlalchemy|redis|httpx|minio)"
Select-String -Path backend\app\**\*.py -Pattern "Mapped\[float\]|Float\("
Select-String -Path backend\app\infrastructure\repositories\*.py -Pattern "\.commit\(\)"
```
依次对应：领域层不许依赖框架、**不许有浮点列**（查的是浮点**列**，不是"出现 float 这个词"——
`domain/rules.py` 会正当地提到 `float`，它的职责就是识别并拒绝浮点阈值）、仓库层不许决定事务边界。
**纪律只写在文档里会失效，所以做成了可执行的检查**（M0 当天就靠它逼出了 `app/__init__.py`）。

### 三条"静默失败"约束（每阶段都要回头看）

| 约束 | 违反的后果 | 怎么撞 |
| --- | --- | --- |
| 审批链不许为空 | 某金额区间无人审批直接通过（合规失控） | 直连库造 `approval_policy = {}` 的品类 → 提交 → 422 `EMPTY_APPROVAL_CHAIN`，主单回滚仍 `DRAFT` |
| 预留与实付的差额必须显式释放 | 差额永久挂在 `amount_reserved`，可用额度虚低 | 预留 800 元 → 撤回 → `reserved` 80000 → 0，流水相加 = 0 |
| 权限范围必须写进 `WHERE` | 漏一处就是越权，且不报错 | 另一部门申请人拿 id 读/改 → 404（本人 200） |

> **SoD 也被归入这一类**：自审自批不报任何错，账面完全正常，只是内控失效。

### 跨阶段接缝四条

登录 → 跳回原目标页（不是首页）；界面「元」→ 请求体「分」→ 库里「分」三处一致；
事件条数与状态迁移一致（提交后 3 条事件，其中**恰好两条**状态迁移，第三条 `from == to`）；
同键重放**响应逐字节相同**且不产生第二条记录。

### 两条"质量"纪律

- **相对断言 > 绝对断言**：预算断言写死"已花 === 30000"会失败在与本次流程无关的数字上
  （库里残留别的运行的预留）；改成先记基线再比变化量。
- **N+1 的判据是"不随行数增长"**：`test_todo_list_is_one_query` 从"SELECT 条数 ≤ 4"
  改成**比较 3 条待办与 6 条待办的 SELECT 条数是否相等**（固定阈值只是在记录某一次实现的样子）。

SQLAlchemy 2.0.52）+ Android（Java + WebView 本地资产）+ MCP Server + Mock 政务 API +
PostgreSQL 16.4 + Redis 7.4 + Milvus 2.6 + MinIO + etcd + LibreOffice Worker + 可选华为
MetaStudio 数字人 / HMS 导航。**83 个 operation / 76 个 path**；**62.8 MB / 376 个文件**，
其中华为数字人资产 **59.9 MB / 15 个文件 = 95.4%**；compose 资源上限合计 **≈ 8.2 GB**；
后端最大文件 `repositories.py` **3,589 行**、`coordinators.py` **2,698 行**；**60 多个环境变量**。
（AI--main-项目技术清单.md、AI--main-改造与轻量化方案.md）

### 刻意**不**借鉴的（裁剪取舍）

- 巨型文件：单个 `repositories.py` **3,589 行** → 本项目按聚合拆文件。
- 重依赖：Milvus / etcd / MinIO / LibreOffice 全部砍掉，用 **pgvector 替掉 Milvus + etcd
  （省约 3 GB 内存和两个容器）**、本地目录替 MinIO（省 768 MB）。参考项目的
  `Milvus → pgvector` 被其自己的分析文档评为"最有价值的一条"（⭐⭐⭐⭐⭐）。
- **60 多个环境变量 → 4 项配置**（每加一项先问"能不能不给它开关"）。
- `langchain-core + langchain-deepseek` → **`httpx` 直连**（"性价比第二高"）。
- 不抄双路 RAG + RRF 融合：**"单路就够，不要抄原项目的 RRF 融合，那是双路才需要的"**。
- 唯一的容器从 8 个降到 **1 个**（只有 db）。

### 借鉴的（保留骨架）

分层方式（边界 / 协调者 / 领域 / 基础设施、端口抽象 `ports.py`、组合根 `runtime.py`）、
**受限规则 DSL**（`eq/ne/in/exists/lt/lte/gt/gte/all/any/not`）、幂等与乐观锁的写法、
事件与审计只追加、**「没有来源就不回答」的溯源策略**、三个类型分离（`Record` / 实体 / DTO）。
**代码全部重写，不复制。**（README 参考项目）

## 十二、可以用来出题的「盲点」

> 以下都是文档里**没有**明确回答、或只有一句话带过的问题。它们最适合当面试题，
> 因为能看出候选人是否真的想过。

1. **`payload_hash` 的计算口径是什么**——哪些字段进哈希？字段顺序 / 浮点 / 时间戳怎么处理？
   请求体演进时旧占位行怎么办？文档只反复说"同键同 payload_hash"，从未定义它怎么算。

2. **有并发同键提交，但有"并发同键撤回/定标/付款"的覆盖吗**——`asyncio.gather` 的并发用例
   逐条列在文档里的只有预算预留（跑 20 次）、同键提交、同级两个会签任务、两人同时付款。
   其余写操作的并发行为没有实测记录。

3. **`policy_snapshot` 的结构版本兼容**——策略 JSON 结构将来演进（比如新增步骤字段）时，
   旧快照怎么渲染？文档只说"存原件"，没说快照要不要带 schema 版本、旧快照怎么迁移。

4. **`approval_tasks` 的 `SKIPPED` 到底在什么条件下写**——词表里有、验收项里没有、
   文档只说"策略变化导致某级被跳过时用得上"，但项目里没有任何路径会写它。

5. **`urgency_extra_step`（紧急加一级）被真实执行过吗**——策略示例里有这段 JSON，
   DSL 里有 `urgency` 字段，但验收项与实测记录里**只出现四档金额**，没有一条走紧急路径。

6. **`skip_when_framework_contract` / `framework_contract` 从哪里来**——策略字段保留了，
   但在"砍掉"清单里写着"先不做，字段可以先留着不实现"。那这个字段现在是永假还是可配置？

7. **审批链的"可达性校验"探测金额是硬编码的 6 个点**（0 / 100 元 / 1 千 / 1 万 / 10 万 / 100 万）——
   只在这 6 个点可达、其他金额段不可达的"死步骤"能查出来吗？文档没讨论探测点的完备性。

8. **`ALL`（会签）模式的人数上限与选人策略**——"N = 该角色下的合格人数"，但 N 很大时
   （比如 50 个同角色的人）会签怎么收敛？有没有上限、能不能部分跳过？文档没写。

9. **阈值调整后的"历史在途单据"**——`budgets.amount_total` 被调低到低于
   `amount_reserved + amount_spent` 时，文档只说"加 CHECK 约束 + 应用层校验"，
   但**应用层到底做了什么**（拒绝调整？警告？）没有写。

10. **`?page=1&size=20` 的统一分页契约 vs 实际实现**——领域设计 7.1 写了全局分页约定，
    但审批任务列表、看板、待办队列的分页参数一致吗？前端有翻页控件吗？文档里的说法互相不一致。

11. **`m6-页面实测.mjs` 造的数据不自动清理**——文档明确"仍未做成跑完自动清，属运维动作"。
    那在多次连跑时会互相污染吗（预算断言已经因为这个改成相对基线了）？谁负责保证幂等？

12. **`uploads/` 的容量与保留策略**——软删除意味着磁盘只增不减；孤儿文件判据散在
    `testdata_cleanup.py` 里。没有容量上限、没有配额、没有清理策略。

13. **运维与可观测性**——只有结构化 key=value 日志 + 三个健康检查。没有指标（metrics）、
    没有链路追踪（trace）、没有告警。参考项目的分析文档里"可观测性"是**待新增**项。

14. **HTTP 端点的总数口径**——README 的"主要 API"表约 55 行，收口说 **58 条路由**。
    这 3 条差在哪（含 SSE 1 条）？哪些是 `/health/*`？文档没有一张完整的路由清单。

15. **时区与"预算年度"的边界**——年度取"提交时刻所在年度（UTC）"，
    但界面显示、`timestamptz`、以及跨年夜的申请（本地时间已跨年而 UTC 还没跨）怎么处理？
    文档只有那一句括号里的 "(UTC)"。

16. **`try` 与"已付款后作废发票"的分支**——作废被拒绝是因为"已付金额 vs 有效发票合计会对不上，
    而系统没有退款流程"。那如果发票**本来就该作废**（供应商开错票且已付款）呢？
    文档说"宁可人工"，但没有定义人工之后系统如何恢复一致。
