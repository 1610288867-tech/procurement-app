## M0 · 准备与设计定稿（2026-10-01）

**一句话**：环境 100% 就绪，三份设计产物齐备，前后端骨架跑通。

### 1. 这个阶段实际学到了什么？

- **文档里的代码不跑一遍就不算验证过。** 领域设计 A.4 的预算写法看着专业，实跑直接抛
  `TypeError: Boolean value of this clause is not defined`——SQLAlchemy 把 `C >= amount`
  重载成了 SQL 子句，而不是 Python 布尔值。更危险的是"看起来很对"的补括号写法：守卫会**恒真**、
  `where()` 静默丢弃，**余额检查从未生效**。读代码学不到这个。
- **单侧都测过 ≠ 链路通。** 前端能开、后端能通，但 Vite 代理只转发了 `/api`、健康检查在 `/health`，
  中间那条线是断的。两侧单测全绿，只有端到端验证能发现。"部分正确"比完全失败更危险。
- **环境问题吃时间的能力和逻辑问题一样。** 四个坑（Docker Hub 不可达 / pip 挂死 / GBK 编码 /
  大版本漂移）没有一个是架构问题，却吃掉一半以上时间，其中三个的症状还是"看起来在正常工作"。
- **三个健康检查语义不同，是性价比最高的 20 行代码。** `/db` 那条后来救了场：它把"数据库到底通没通"
  从猜测变成一行输出。
- **纪律要写进代码文件本身，不能只写在文档里。** 四层包的 `__init__.py` 顶部写了"这一层禁止什么"，

### 4. 为什么使用这样的技术栈，它比别的好在哪？

**一句话：每一处选型都在「减少活动部件」，而不是「用更新的东西」。**

| 选型 | 替代方案 | 为什么选它 |
| --- | --- | --- |
| **FastAPI 四层**（边界/用例/领域/基础设施） | Django / Flask 一把梭 | 领域层是纯函数，毫秒级可测；换框架换库时 `domain/` 一行不改。本项目最难的几件事（审批引擎、预算策略、三单匹配）**天然是纯逻辑** |
| **纯 `uvicorn`** | `uvicorn[standard]` | 后者要源码编译 uvloop，**Windows 没有 wheel**，实测让 pip 卡死 25 分钟 |
| **`requirements.txt`**（pip freeze） | Poetry / uv / PDM | 依赖是单一事实来源；少一层工具就少一处出错点 |
| **PostgreSQL + pgvector** | MySQL / SQLite / Milvus | 一条 Docker 命令得到"关系库 + 向量库"；**pgvector 替掉 Milvus + etcd，省约 3 GB 内存和两个容器**。M11 前用不到向量，但镜像先用 `pgvector/pgvector:pg16`，将来零迁移 |
| **SQLAlchemy 钉 `>=2.0.36,<2.1`** | 追最新（默认装出 2.1.1） | A.4 的预算写法**按 2.0 实测过**，大版本漂移会让已验证的结论失效 |
| **暂不引 Redis** | 一上来就上缓存 | M0–M5 用不到，额度计数用 PG 就够。**少一个活动部件，就少一处"为什么不通"** |
| **Vite 代理，不用 CORS** | 后端加 `CORSMiddleware` | 同源，不需要 credentials 和预检；M3 上 httpOnly Cookie 时前端一行不改；排错更直白——代理直接报 `ECONNREFUSED` |
| **React + Vite + TS + TanStack Query** | Vue / 原生 JS / 手写 fetch | 就业价值最高；`invalidateQueries` 让"新增后刷新列表"永远不用手写 |
| **Tailwind v4（Vite 插件）** | 手写 CSS / Tailwind v3 | 只需一行 `@import "tailwindcss"`，**没有 config 文件** |
| **`lib/money.ts` 单独一个文件** | 各页面各转各的 | 元⇄分写错 1000 倍是这类系统的经典事故；全项目**只允许这一个文件碰金额单位** |
| **配置项只有 4 个** | 原项目 60 多个环境变量 | 每加一项先问"能不能不给它开关" |
| **pytest 分档**（`-m unit` 为默认档） | 单一档 | 最常敲的 `pytest` 永远毫秒级，测试才不会被跳过 |
| **三条分层自查做成命令** | 只写在文档里 | 写成 `Select-String` 才会当天见效——M0 当天就靠它逼出了 `app/__init__.py` |

## M1 · 骨架贯通（2026-10-02）

**一句话**：用「供应商」把 表 → ORM → 仓库 → 协调者 → 路由 → 页面 这条链路完整走通了一次。

### 1. 这个阶段实际学到了什么？

- **容器名 ≠ compose 项目名。** 薄封装在仓库根目录，Compose 会把项目名推导成 `procurement-app`，与基础设施的 `procurement` 是两个项目；而 `container_name: procurement-db` 是写死的，于是 `up -d` 报 "container name is already in use"。修法是给薄封装加 `name: procurement`，让两者指向同一个项目。
- **模块级引擎 + 每个用例一个事件循环 = `Event loop is closed`。** `create_async_engine` 的连接池绑定"创建它时的事件循环"，pytest-asyncio 默认每个用例新建循环，于是第二个用例起就炸。用会话级循环（`asyncio_default_test_loop_scope = "session"`）解决。
- **协议匹配时 `list` 不协变。** `list[SupplierRecord]` 不满足 `list[SupplierView]`，mypy 直接报冲突；换成 `Sequence`（协变）就通了。
- **`= Depends(...)` 是旧写法。** ruff 的 B008 会拦，`Annotated[AsyncSession, Depends(get_session)]` 才是现在的推荐写法，而且类型标注和依赖声明合一。
- **新版 FastAPI 里，include 进来的 router 在 `app.routes` 中是 `_IncludedRouter` 包装对象**，不再展平。我一度以为路由没挂上，其实挂了——正确的验证方式是 `app.openapi()["paths"]`。
- **迁移 docstring 的首行会进 Alembic 日志**，中文在 GBK 控制台会乱码，首行留 ASCII。
- **"数据库不可用"抛的不一定是 `SQLAlchemyError`。** 实测：asyncpg 在**连接阶段**失败（端口没人监听）时，
  SQLAlchemy 抛的是原始的 `ConnectionRefusedError`——它是 `OSError` 的子类，**不是** `SQLAlchemyError`。
  只接后者的话，数据库没起来时仍然是裸 500。所以 503 处理器必须同时接 `OSError`。
- **"后端没起来"在前端看起来是 500，不是连接错误。** Vite 代理在后端不可达时返回
  **空响应体的 500**（`content-length: 0`），页面上只显示"请求失败：500"，
  把排查方向误导向后端 bug。诊断口诀：**看 body 长度是不是 0**。

### 4. 为什么使用这样的技术栈，它比别的好在哪？

| 选型 | 替代方案 | 为什么选它 |
| --- | --- | --- |
| **`Annotated[AsyncSession, Depends(...)]`** | `session: AsyncSession = Depends(...)` | 不触发 ruff B008；类型标注与依赖声明合一，是 FastAPI 现在的推荐写法 |
| **`Protocol` 端口**（`application/ports.py`） | 让协调者直接 import `CatalogRepository` | `application/` 不依赖 SQLAlchemy，换 ORM 这层不用动；实现方**在结构上**满足协议即可，不需要额外适配器 |
| **`Sequence` 而非 `list`**（端口返回值） | `list` | `list` 不协变，`list[SupplierRecord]` 不满足 `list[SupplierView]`；`Sequence` 协变，类型检查能过 |
| **仓库 `flush()` + 协调者 `commit()`** | 路由里直接 commit | 事务边界集中在一处；一次用例里的多个仓库操作能进同一个事务 |
| **Vite 代理**（继承 M0） | 后端加 CORS | 同源，M3 上 httpOnly Cookie 时前端零改动 |
| **TanStack Query 的 `invalidateQueries`** | 手写"新增后刷新列表" | 缓存失效交给库，页面代码少一半 |
| **测试会话级事件循环** | 每个用例一个循环 | 模块级引擎的连接池要求整个会话共用一个循环 |

## M2 · 主数据（2026-10-02）

**一句话**：四类主数据（部门 / 品类 / 供应商 / 预算）+ 三层校验的前两层 + 三个管理页 + 演示数据脚本。

### 1. 这个阶段实际学到了什么？

- **"结构校验"和"语义校验"是两件事，后者才是关键。** Pydantic 只能挡"形状不对"（`role: "BOSS"`）。
  而 `{"gte": ["amount", 100_000]}` 形状完全合法，却会让整条规则**静默失效**——求值器对"缺字段"
  的语义是**返回 False（不满足）**，于是那一级审批不生效，申请**以更低的层级被批准**。
  这类错误不抛异常，只能靠专门的语义校验器拦（路径白名单 / 整数分 / 零阈值兜底 / order 唯一）。
- **写入时把默认值补齐**，M6 的求值器就不用再猜默认值。代价是存进去的策略比手填的多几个字段
  （`mode: "SINGLE"`、`skip_when_framework_contract: false`），换来的是"读出来即可直接用"。
- **mypy 抓到了 `Result.rowcount` 不存在**：SQLAlchemy 异步 `Result` 的类型标注里没有它。
  改用 `.returning(id)` 既类型干净又少一次查询 —— 这个写法 M7 的预算预留会直接沿用。
- **规格会改变既有接口的语义。** M2 把"创建供应商"从 `/api/v1/suppliers` 移到
  `/api/v1/admin/suppliers`，M1 的测试立刻 405。读规格时要连"旧接口怎么办"一起看，
  否则第一反应会是"接口坏了"。
- **同一个坑会踩第二次**：Python 脚本的中文输出在 Windows 上默认走 cp936，终端按 UTF-8 解码就是乱码。

| **种子脚本用 ORM 不用 SQL** | 手写 INSERT | 迁移一改种子跟着改，不会悄悄失效 |
| **种子里"已存在就跳过"** | 先删后插 | 反复跑安全，也不会覆盖手工改过的审批策略 |

## M3 · 账号与权限（2026-10-02）

**一句话**：8 个角色能登录（7 个人，GM 由 ADMIN 兼任），每个接口都有明确的权限边界，
数据级权限的判定函数写好并测绿，等 M5 把它挂进真实查询。

### 1. 这个阶段实际学到了什么？

- **"能不能用这个接口"和"能看到哪些行"是两套权限，后者才容易出事。**
  角色依赖只挡住"谁来敲门"；数据级权限决定"进门后能翻哪几个抽屉"。
  而且漏掉后者**不会报错**，只会安静地把别人的数据查出来 —— 所以它必须做成
  能直接塞进 `WHERE` 的条件函数，而不是"先查出来再判断能不能看"。
- **Cookie 的 `Path` 是一道免费的安全边界。** 把 refresh 限定到
  `/api/v1/auth/refresh` 一个路径，它就再也不会出现在别的请求里，泄露面当场变小，
  而代价只是 `set_cookie` 上一行参数。
- **`token_version` 一个整数字段替掉了两张表。** 冻结账号要"旧令牌立即失效"，
  直觉方案是黑名单 + refresh rotation；实际把版本号写进令牌载荷、每次比对即可。
  **同一件事不要叠两套机制**，否则调试时要同时怀疑两处。
- **库的时间校验会跟测试的注入时间打架。** PyJWT 内部读真实时钟，
  测试里"现在是几点"就注入不进去；关掉它的 `exp`/`iat` 校验、拿自己的时钟算一次，
  "已过期"才能在毫秒内被构造出来。
- **加权限会让既有测试集体变红，这是规格变更而不是测试坏了。**
  M2 踩过一次（接口搬家 405），M3 又踩一次（接口上锁 401）。
  第一反应应该是"读规格"，不是"回滚改动"。
- **登录失败的响应必须一模一样。** 区分"用户不存在"和"密码错误"，
  等于免费提供一个账号枚举接口。

### 4. 为什么使用这样的技术栈，它比别的好在哪？

## M4 · 前端设计系统（2026-10-02）

**一句话**：把界面从"六个页面各写各的 Tailwind"收成一套设计令牌 + 侧边栏骨架 +
共享组件，风格基准取自 MiMo 文档站（暖白极简）。

> **编号说明**：M4 是 2026-10-02 新插入的阶段，原 M4「采购申请」及其后各阶段
> 已**整体顺延**为 M5–M12（三张总表、依赖图、模块表、模块编号 `M-04→M-06` 等
> 与全部活跃引用一并更新过）。历史记录（M0–M3 的四问与小节标题）保持原编号不动。

### 1. 这个阶段实际学到了什么？

- **"好看"是可以量化的，不该靠感觉调。** 与其照着截图猜颜色，不如在参考站上
  取计算样式：`--color-bg-page:#fcfaf8`、`--color-sem-text-h1:#1a1a1a`、
  `--radius:.625rem`、按钮量到 `36px 高 / 14px 字 / 6px 圆角`。
  拿到数值之后再落成 `@theme` 令牌，改风格就只动一个文件。
- **层次方向错了，怎么加阴影都救不回来。** 第一版把卡片设成 `#faf7f3`、页面设成
  `#fcfaf8` —— 卡片比页面**深**，视觉上"陷进去"，内容区没有承载感。
  改成"页面最暖 → 侧边栏更深 → 卡片最亮（白）"之后，同一条边框立刻成立了。
- **选中态要显眼到"不用找"。** 原来选中项只是白底加粗，在浅色侧边栏里几乎看不出来；
  换成近黑底 + 反白字之后，"我现在在哪"是一眼可见的。
- **删掉一个文件会让 dev server 掉线。** 删 `_ui.tsx` 之后 Vite 进程直接没了。
  更值得注意的是：**用 `Start-Process cmd /c` 起的服务，进程死了你完全收不到信号** ——
  页面报 `ERR_CONNECTION_REFUSED` 时，第一反应会是"我改坏了代码"。
  改成用后台作业起服务、日志留在手里，才有得看。
- **样式改动会让"选择器型"测试集体失效。** 自检脚本原来靠
  `document.querySelector('nav')` 和"顶栏"这两个词定位；外壳一改成侧边栏，它
  断的不是功能，而是**它自己的假设**。修法不是把选择器改个名字了事，而是顺便把断言
  修**准**：菜单项要跟**后端返回的角色**对得上（见下条）。
- **"菜单按角色渲染"原来只验了一半。** 旧断言只检查菜单里有没有那三个字。
  现在改成：先 `GET /api/v1/auth/me` 拿真实角色，再断言侧边栏账号区显示的
  `ADMIN+GM` 与它一致、管理员菜单三项齐全；换 requester 后断言**菜单只剩两项**。
  这样"把菜单写死"或者"样式把账号区藏起来"都会被抓出来。
- **字体栈里 `system-ui` 排在前面，等于把中文交给浏览器去猜。** 它在 Windows 上解析成
  Segoe UI Variable，而**这个字体没有中文字形**，于是每个汉字都要走一次回退：
  中英文字形来自两套字体，字号与灰度都对不齐 —— 这就是"字体不好看"的根因。
  正确写法是显式列出西文与中文两段（`Segoe UI Variable Text` → `Microsoft YaHei UI`），
  回退才有确定性。顺带一个教训：**本机没有的字体写在栈首毫无意义**（原来首位的 `Inter`
  就没装），它只会让人以为字体已经换过了。
  另：`document.fonts.check("14px Inter")` 对没装的字体也返回 true，
  **不能用它判断字体是否可用**；要用"同一段文字在目标字体与兜底字体下的渲染宽度是否不同"来判。

## M5 · 采购申请（2026-10-02）

**一句话**：把"一张单子从草稿到提交"这半段做扎实 —— 四张表、9 个接口、幂等与乐观锁，
金额一律由后端按明细重算。

### 1. 这个阶段实际学到了什么？

- **`...init` 写在 `headers` 之后，会静默吃掉默认请求头。** 统一客户端里那一行
  `{ credentials, headers, ...init }` 让调用方传的 `Idempotency-Key` 把头部的
  `Content-Type: application/json` 整个顶掉，后端于是按表单解析、回一句
  "Input should be a valid dictionary or object to extract fields from"。
  **只有带自定义头的接口会中招**（提交/撤回），所以它藏了整整两个阶段才暴露。
  教训：对象展开的顺序不是风格问题，是语义问题。
- **条件更新之后，内存里的对象是旧的。** bulk `UPDATE` 不刷新会话里已加载的对象，
  而 `expire_on_commit=False`（异步下必须这么设）也不会在提交时让它过期 ——
  于是"提交成功、响应里却还是 DRAFT"。第一反应是 `expire_all()`，
  结果在异步会话里抛 `MissingGreenlet`，还被 503 处理器当成"数据库不可用"。
  最后的解法最土也最稳：**回读另开一个会话**。
- **幂等的难点不是"记住键"，是"两个请求同时到"。** 只做"查不到就执行"，
  并发同键会双双执行且悄无声息。做法是先抢一个 `IN_PROGRESS` 占位行并**独立提交**，
  撞上的那方拿 409 —— 这条在 `asyncio.gather` 的测试里才真正被撞出来。
- **幂等键的生成时机是语义的一部分。** 键在"用户点提交"时生成一次，重试**复用**它；
  在请求函数里现生成的话，每次重试都是新键，幂等就名存实亡。
- **权限兜底往窄里兜，会表现为"什么都查不到"。** `get_request` 少传 `actor_id` 时，
  `only_self` 退化成恒假条件，接口一律 404 —— 不越权，但静默失效。
  修法不是补一个默认值，而是把参数改成**必填**，让漏传在类型检查阶段就暴露。
- **测试的清理顺序会以"外键报错"的形式出现在 teardown 里。** 删账号时撞上
  `purchase_requests.requester_id`，报错却发生在用例之外，很难联想到是清理顺序。

### 2. 哪里卡了最久，为什么？

| 排名 | 卡点 | 耗时 | 根因 |
| --- | --- | --- | --- |
| 1 | 提交接口 422，前端却"看起来正常" | ~35 min | `Content-Type` 被自定义头覆盖；后端直连测试**通过**，只有浏览器发出去的请求才失败，必须抓真实请求头才能定位 |
| 2 | 提交后响应里仍是 DRAFT | ~25 min | 条件更新不刷新内存对象；`expire_all()` 又触发 `MissingGreenlet` |
| 3 | teardown 报外键违反 | ~15 min | 测试清理顺序：账号先于申请被删；修法是让清理**不依赖顺序**（先删引用行 + 部门前解绑） |
| 4 | 幂等重放 500 | ~10 min | 幂等记录里存的 dict 用了响应别名（`amount_total_fen`），而模型校验要的是字段名 |

### 3. 有没有留下"以后再说"的坑？

| 类型 | 坑 | 风险 | 回归阶段 |
| --- | --- | --- | --- |
| 有意留的 | `budget_id` 建表但没用（M7 预留时才填，故不加外键） | 无 | M7 |
| 有意留的 | 列表只做了 `limit/offset`，前端没做翻页控件 | 数据多了要翻页 | 数据量上来时 |
| **真债** | 幂等占位行的清理是"过期即删"（120 秒），靠每次请求顺带跑一次 | 长期没有请求进来时，卡住的行会一直留着 | 需要时改成定时任务 |
| **真债** | `application/coordinators/purchase.py` 里为回读直接开了会话（import 了 `database`） | 分层上不够干净；但回读必须是不带缓存的会话，暂时没有更好的落点 | 引入组合根（`infrastructure/runtime.py`）时收口 |
| **真债** | 品类 `form_schema` 只支持 string/number/date 三类字段 | 复杂表单（枚举、附件）渲染不了 | M7 附件 / 需要时 |

### 4. 为什么使用这样的技术栈，它比别的好在哪？

| 选型 | 替代方案 | 为什么选它 |
| --- | --- | --- |
| **幂等占位行 + 独立事务** | "查不到就执行" | 前者能挡住并发同键；后者会让两个并发请求双双执行，而且不报错 |
| **`StrEnum` 做状态** | 散落的字符串常量 | 成员本身就是 `str`，直接进 SQL 与 JSON，少一层 `.value` 转换 |
| **纯函数先测绿再动库** | 直接写接口再联调 | M5 的 90 条单测跑完 0.5 秒；状态机与金额规则的错误在这一层就被挡住 |
| **`RequestScope` 先算后进 `WHERE`** | "查出来再判断能不能看" | 后者漏一处就是越权且不报错；前者是唯一落点，兜底恒假、只能往窄里兜 |
| **事件只记状态变更** | 草稿每次改动都记 | 草稿反复改是常态，全记会把时间线淹掉；"提交后两条事件"这条验收也因此成立 |
| **回读另开会话** | `expire_all()` | 异步会话里惰性刷新会抛 `MissingGreenlet`；新会话没有缓存，读到的必然是已提交状态 |
| **`data-testid` + 断言对账** | 靠文案定位 | 菜单加一项（"我的申请"）时，断言失败点直接指向"多了哪一项" |

## M6 · 审批引擎（2026-10-03）

**一句话**：把"按金额动态生成审批链"做成**纯函数**，再用两处条件更新 + 一处行锁
把它落到库里 —— 顺序、并发、越级三件事都靠数据库挡住，不靠界面。

### 1. 这个阶段实际学到了什么？

- **"不会报错、只会算错"的 bug，只能靠主动去撞。** 这一阶段撞出 4 个，全都一声不响：
  指针永远不推进、时间线顺序随机颠倒、指针一次跳两级。它们**没有一个是靠读代码发现的**，
  全是"写完断言、跑一遍、发现数字不对"才挖出来的。第 3.1 节那三条约束之所以要反复撞，
  原因就在这里。
- **bulk `UPDATE` 之后读对象拿到的是旧值 —— 而且 `select(Model.col)` 也一样。**
  M5 已经踩过"条件更新后回读旧对象"，这一阶段换个形式又踩了一次：只选 `status` 列
  仍然会经过**身份映射**，把行映射回会话里缓存的那个对象。必须加 `populate_existing=True`。
  这次的诊断方式是"把接口返回的东西和库里的东西同时打出来"，
  一眼看到"库里 APPROVED、接口说还没完成"。
- **并发问题的根因常常不是"写错了"，而是"看不见"。** 每人一个会话 + 默认隔离级别，
  两个同时通过同一级会签任务的事务**互相看不到对方未提交的改动**，于是双方都判
  "这一级还没完"、谁都不推进。修法不是加判断，而是**在流那一行取行锁**
  （`SELECT … FOR UPDATE`），把"判定 + 推进"变成一个串行临界区。
  锁的粒度是关键：锁在**单个申请**的流上，不同申请完全不受影响。
- **一个概念只存一处，否则必然漂移。** "还没轮到"这件事**没有**做成任务状态
  （不加 `WAITING`），而是由 `approval_flows.current_step_order` 单独表达。
  界面上的"未开始 ○"是**算出来的**（任务状态 + 当前级），不是第三个状态。
  如果两处都存，推进时漏改一处就会出现"流说第 3 级、任务说自己在等"的数据。
- **时间戳也要看它是谁给的。** PostgreSQL 的 `now()` 返回**事务开始时间**，
  同一事务里写的多条事件拿到完全相同的时间戳，于是"按时间正序"退化成 UUID 随机比较。
  实测出现过"提交"与"生成审批链"两条事件顺序颠倒。应用侧取一次微秒时间戳就解决了。
- **审批链要有"依据"，不能只有"结果"。** 任务表记的是"走了哪几级"，
  `policy_snapshot` 记的是"当时那份策略长什么样"。只存结果的话，
  管理员改过两次阈值之后，**任何一笔历史申请都解释不清**。

### 2. 哪里卡了最久，为什么？

| 排名 | 卡点 | 耗时 | 根因 |
| --- | --- | --- | --- |
| 1 | 两人同时通过同一级的两个任务，指针停在原地 | ~60 min | 先撞到"读缓存对象"，加了 `populate_existing` 仍不对；真因是**跨事务看不见未提交改动**，最终用行锁解决 |
| 2 | 页面实测脚本反复失败（换了 6 轮才对） | ~70 min | 全是**测试脚本自身**的问题：用了不存在的账号名（`manager` 实为 `dept-manager`）、admin 没部门提交不了申请、或签要先认领、`waitFor` 条件在首帧就成立、换身份后没重载页面 |
| 3 | 越级审批返回 403 还是 409 的分寸 | ~15 min | "可见但无权 → 403；不在可见范围 → 404"这条约定要贯彻到每一个分支（含"已被别人认领"） |
| 4 | 事件顺序偶发颠倒 | ~10 min | 事务时间戳相同；`ORDER BY created_at` 退化成随机 |

> 第 2 名值得单独说：那 70 分钟**没有一行是产品代码的问题**，全是我自己写的验收脚本
> 在假设环境。教训是"实测脚本也是代码，它的失败要按证据排查，不能靠猜"——
> 每一次我都把 HTTP 状态与页面文本打出来，才一步步收敛。

### 3. 有没有留下"以后再说"的坑？

| 类型 | 坑 | 风险 | 回归阶段 |
| --- | --- | --- | --- |
| 有意留的 | 驳回只做**终止式**（整单变 `REJECTED`），没有"回退式 / 补充式" | 复杂流程用不了 | 需要时（领域设计 4.5 已记） |
| 有意留的 | 策略变化导致某级被跳过时，`SKIPPED` 状态已留在词表但没用上 | 无（词表先留着） | 做"改策略后重修审批链"时 |
| 有意留的 | `approval_tasks` 只按人 + 状态建索引，没有"按申请查全部"的分页 | 单笔申请的任务数很小（个位数） | 数据量上来时 |
| **真债** | 建账号**没有 HTTP 端点**，自检脚本只能直连库 | 演示/验收脚本要带数据库凭据；将来多人协作时要补一个受权限保护的建号接口 | 需要时（M8 回归会再碰一次） |
| **真债** | `application/coordinators/` 里仍直接 import `app.database` | 分层不够干净（M5 起就有） | 引入组合根（`infrastructure/runtime.py`）时收口 |
| **真债** | 浏览器自检 / 页面实测建的品类与申请**不自己清理** | 开发库会积测试数据 | ✅ 已有统一入口：`backend\scripts\testdata_cleanup.py --scope page\|all`（两个脚本末尾都会打印这行命令）；**仍未做成"跑完自动清"**，属运维动作，留给你按需执行 |
| **真债**（2026-10-03 补） | **被拒的尝试不留痕**（越权 / 越级 / 无权操作只有 403，没有审计记录） | 出事时查不到"谁试过"，OWASP 把"日志与监控不足"列为十大风险之一 | M8 之后：新表存安全事件，**不要**混进申请人看的时间线 |

> **2026-10-03 补记：走完 M6 才发现漏了"职责分离"整整一类要求。** 见下面第 4 条后的说明。

### 4. 为什么使用这样的技术栈，它比别的好在哪？

| 选型 | 替代方案 | 为什么选它 |
| --- | --- | --- |
| **审批链是纯函数** | 边写接口边算 | 20 条纯函数测试跑 **0.07 秒**；四档金额对照表直接当参数化输入，改一行立刻知道对错 |
| **`current_step_order` 单一事实来源** | 给任务加 `WAITING` 状态 | 一个概念存一处；两份状态必然漂移，而漂移出来的数据比原问题更难查 |
| **决定接口把"当前级"写进 `WHERE`** | 只在待办列表里过滤 | 列表是给人看的，接口可以被直接调用；写进 WHERE 后越级审批在**数据库层面**就被挡住 |
| **推进指针用条件更新 + 行锁** | 先读再写 | 先读再写会跳过一整级且不报错；行锁把"判定 + 推进"串行化，不同申请互不影响 |
| **`policy_snapshot` 存策略原件** | 存品类 id 现查 | 现查等于拿今天的规则解释三个月前的申请；成本一列 JSONB，收益是审批链可复现、可解释 |
| **待办一次 JOIN** | 查出任务再逐条查申请 | 待办是全系统最频繁的查询；20 条任务 → 21 次查询是经典 N+1，实测用 SQL 日志条数守住 |
| **候选人为空直接 422** | 生成"没人能审"的任务 | 后者让单据**永久卡死且无人知情**；前者在提交时就说清是哪一级缺人 |
| **应用侧事件时间戳** | 数据库 `now()` | `now()` 是事务时间，同事务多条事件时间相同，时间线顺序随机 |
| **职责分离做成纯函数 + 失败关闭**（2026-10-03 补） | 在接口里各写一个 `if actor == requester` | 自审这类判定**错了不报错、只是内控失效**；纯函数才测得动、测得全（5 条单测毫秒级） |
| **自审拦截分三层，不只建链一层** | 只在建链时剔除提交人 | 或签任务 `assignee_id` 为 NULL、只按角色可见 —— 建链那层**挡不住它**。这个洞是写测试时才暴露的：三层（建链 / 待办过滤 / 决定接口 SQL 守卫）缺一层就有口子 |

### 4.1 走完 M6 才发现的一件事：设计阶段漏掉了一整类要求

**M6 的 15 条验收全过之后**，做内控对账时实跑发现：**申请人能批掉自己的申请**。
回去查外部依据才知道，"不相容职务分离（SoD）"是采购内控的骨架
（财政部《企业内部控制应用指引第 7 号》第五条、上市公司制度范本的"五条不相容岗位"、
Oracle 的 Prohibit User Self-Approval），而**本项目设计文档里一个 SoD 字眼都没有**。

三条教训：

1. **"验收全过"不等于"业务对"**：M6 验收里没有一条涉及"谁不能审什么"，
   所以漏洞能一路全绿地走过去。**验收项是从设计来的，设计漏了，验收就一起漏。**
2. **补的不该只是代码，先是文档**：SoD 写进 `业务规则.md` 第 9 条与领域设计 2.1 之后，
   修法才有依据可对（而不是"我觉得应该这样"）。
3. **纯函数纪律在这件事上又赢了一次**：`exclude_requester` 5 条单测 0.06 秒跑完，
   而集成测试要起数据库、建账号、走完整链路才对得上。

依据与八条定稿口径见 [`docs/采购内控对照.md`](docs/采购内控对照.md)。

## M7 · 预算并发预留（2026-10-04）

**一句话**：把"钱怎么被占住、怎么放回去"做成**一条条件更新 + 一本只追加的流水**——
并发下只有一笔能占住、驳回与撤回各有一个释放入口、付款时差额必须显式释放。

### 1. 这个阶段实际学到了什么？

- **"够不够"这件事只能由数据库回答。** 两个请求各自都读到"可用 1000 元"，
  在 Python 里判断就两笔都通过 —— 而且**不报任何错**。守卫条件
  （`amount_total − (reserved + spent) >= :amount`）整个写进 `WHERE`，
  受影响行数为 0 才算"不够"，这是本阶段唯一不能让步的一条。
- **并发失败之后，不要用"你开始时的快照"去解释失败。** 这一步实测撞到了：
  失败的那一方拿着请求开始时读到的预算数字算差额，得出"钱明明够啊"，
  于是本该是 422"预算不足"的响应退化成一句含糊的 409。
  修法是**失败后强制重读**（`populate_existing=True`）再算人话。
  **判定与解释必须分开**：判定只由条件更新做，解释才允许读库。
- **"账本"要写在唯一能动钱的那一层。** 把"每次金额变动都写一条流水"交给调用方去记，
  早晚漏一处，而漏了不报错、只是事后对不上账。所以 `reserve/release/spend/settle`
  四个方法自带流水：想动钱就必须经过这里，也就必然留下痕迹。
- **一个动作的"差额"是最容易被漏掉的一笔钱。** 预留 1000、实付 900，
  只写 `SPEND(900)` 而忘了 `RELEASE(100)`：账面完全正常，可用额度却永久虚低。
  这类算术必须在**纯函数**里（`settlement()`）并被 5 条单测钉住 —— 它跑一次 0.05 秒。
- **失败关闭（fail-closed）比"聪明"更省事。** "没有预算行"该不该放行？
  放行等于把"计划外采购"变成一条无人知晓的通道；挡住则只多一条 422 文案。
  选了挡住之后，测试夹具与两个浏览器脚本都得先配预算 ——
  这些改动本身就是那条口径在项目里**真实生效**的证据。
- **权限要按动作拆，不要按接口拆。** "看钱"是财务的本职，"改钱"只该是管理员。
  把 `/admin/budgets` 的权限放宽成"财务也能看"就等于把改钱也一起放开了；
  于是单开一个只读看板，两个动作各自收紧。

### 2. 哪里卡了最久，为什么？

| 排名 | 卡点 | 耗时 | 根因 |
| --- | --- | --- | --- |
| 1 | 并发用例拿到 `[200, 409]` 而不是 `[200, 422]` | ~25 min | 失败方用请求开始时的快照算差额；改成失败后强制重读 |
| 2 | 加"必须有预算"之后 3 条 M6 用例集体 422 | ~20 min | 规格变更（不是回归）：那些用例临时造了新品类，新品类自然没有预算 —— 补一条预算即可 |
| 3 | 测试清理顺序撞 `budget_id` 的 RESTRICT | ~15 min | 预算引用部门与品类都是 RESTRICT，必须**先于两者**删；`World.purge` 原来是"删完品类再删预算" |
| 4 | 看板响应模型字段别名对不上（`amount_total` vs `amount_total_fen`） | ~10 min | 直接构造模型时不会走 `validation_alias`；改用 `model_validate({...别名...})`，与其它两个预算接口同一种写法 |

### 3. 有没有留下"以后再说"的坑？

| 类型 | 坑 | 风险 | 回归阶段 |
| --- | --- | --- | --- |
| 有意留的 | 付款结转的**调用方**要到 M10 才有（`settle()` 已就绪并被测试钉住） | 无：算术与流水已验证，M10 只接一个调用 | M10 |
| 有意留的 | 预算调整没有"审批流程"，只有管理员改总额（M7 之前也没有） | 口径已经定死"先调预算再提交"，但调整动作本身无留痕 | 需要时（业务规则第 1 条已记） |
| 有意留的 | 看板只能看最近 50 条流水，没有分页 / 时间筛选 | 流水多了不好查某一笔 | 数据量上来时 |
| **真债** | `application/coordinators/` 仍直接 import `app.database` | 分层不够干净（M5 起就有） | 引入组合根时收口 |
| **真债** | 建账号没有 HTTP 端点 | 脚本要带数据库凭据 | 需要时（M8 回归会再碰一次） |

### 4. 为什么使用这样的技术栈，它比别的好在哪？

| 选型 | 替代方案 | 为什么选它 |
| --- | --- | --- |
| **条件更新做守卫** | 先 `SELECT` 余额再判断、`SELECT ... FOR UPDATE` 锁行 | 一条 SQL 同时完成"判定 + 扣减"，不需要显式锁，也不会因为漏写判断而超支 |
| **只追加的 `budget_transactions` + `UNIQUE(request_id, kind)`** | 只改 `budgets` 上那三个数字 | 三个数字说不清"为什么是这个数"；唯一约束顺手把"重试重复扣钱"变成一次可见的冲突 |
| **差额释放的算术放 `domain/budget_policy.settlement()`** | 写在付款接口里 | 纯函数毫秒级可测；"漏释放差额"是**不报错只算错**的那一类，只能靠测试去撞 |
| **流水写在仓库层（`reserve/release/spend/settle` 自带）** | 让协调者记得写流水 | 纪律放在唯一能碰钱的入口上，漏不掉 |
| **`budget_id` 在提交那次条件更新里一起写死** | 提交后再 `UPDATE` 一次 | 少一次写、少一个中间状态；"这笔申请占的是哪条预算"从推断变成事实 |
| **看钱与改钱分成两个接口** | 放宽 `/admin/budgets` | 权限按**动作**收紧，而不是按接口取并集 |
| **看板把部门名 / 品类名一次带出** | 前端再查部门与品类接口 | 财务没有那两个管理员接口的权限；少两次往返就少两处 403 |

## M8 · 回归验收（2026-10-04）

**一句话**：不写新功能，用**一条命令**把 M0–M7 整体再撞一遍 ——
结果是把"手点过、当时过了"变成"可复跑、可核对"，并撞出三处与功能无关的卫生问题。

### 1. 这个阶段实际学到了什么？

- **"验收全过"和"整体还是好的"是两件事。** 每个阶段的验收都是**当时**跑的，
  而它们从来没有在同一天、同一份数据、同一个进程里一起跑过。回归的价值就在这个"同时"。
- **把"只能手点"的检查变成脚本，才发现有两个坑一直没被自动化覆盖**：
  ① 三条"静默失败"约束里，"审批链为空"只在**策略保存**那层被测过，
  **提交那一层**（历史脏数据 = 空策略）没人撞过；② "已登录打开 `/login` 会不会跳回目标页"
  从来没有断言。这一轮各补了一条。
- **回归入口不能有开关。** 一开始想加 `-OnlyBackend` 之类的参数，写完就意识到：
  有开关就一定会出现"这次时间紧、少跑一项"，入口也就白做了 ——
  于是把要跑的东西**写死**（实施计划 M8 的常见坑里恰好也写了这一条）。
- **"脚本自清理"这条纪律要能**自我修复**，否则它会诬告自己。**
  `m6_smoke.py` 的残留回查按 `t-smoke-%` 前缀数账号，但清理只删"本轮造出的名字"——
  上一轮中途失败留下的账号就永远算残留，脚本第二次跑必然报"没清干净"。
  改成按**前缀**删（并顺带删掉这些账号提交过的申请），它才真的自洽。
- **`$LASTEXITCODE` 是上一条外部命令留下的。** 纯 PowerShell 的步骤（三条分层自查）
  不碰它，`$null -ne 0` 为真 → 第一步就"失败"。回归脚本自己先踩了一次这个坑。

### 2. 哪里卡了最久，为什么？

| 排名 | 卡点 | 耗时 | 根因 |
| --- | --- | --- | --- |
| 1 | 回归脚本第 1 步假失败 | ~10 min | `$LASTEXITCODE` 残留 `$null` 被当成非 0；修法是每步开始先归零 + 用 `throw` 而不是 `exit` |
| 2 | `m6_smoke.py` 的残留回查说"没清干净" | ~15 min | 上一轮失败的账号挡住了账号删除（`purchase_requests.requester_id`），而回查按前缀数 —— 判据与清理口径不一致 |
| 3 | M3 的"requester 调管理员接口 → 403"现场探到了 404 | ~5 min | 我探的是 `/api/v1/admin/users` —— **那个接口根本不存在**（建号没有 HTTP 端点）。换成真实存在的三条 admin 路由后是 403 / 403 / 403。**探测脚本自己选错了对象**，不是权限错了 |
| 4 | 探针把时间线当成裸数组 | ~5 min | 接口返回 `{request_id, events}`；顺带发现第一条事件是"创建 → DRAFT"，于是把断言写准（**恰好两条**状态迁移） |

### 4. 为什么使用这样的技术栈，它比别的好在哪？

| 选型 | 替代方案 | 为什么选它 |
| --- | --- | --- |
| **一个 PowerShell 入口固定 11 步** | 每个检查各写一条命令、想起来才跑 | 回归的敌人是"这次少跑一项"；写成一条命令、没有开关，才可能真的每次都跑 |
| **失败即停 + 打印原始输出** | 跑完全部再汇总 | 回归是找问题，不是出报告；第一处失败往往就是根因，后面的失败多半是它的余波 |
| **"静默失败"探针单独一个脚本**（`regression_probes.py`） | 混进 `pytest` 用例里 | 这三条约束的撞法需要**造脏数据**（空策略品类、跨部门账号）——放测试里会让用例又长又难读；单独成脚本还能对着**真实服务**跑 |
| **入口最后一步自动清理并回查残留** | 让用户自己记得清 | "测试污染物零残留"本来就是 M8 的验收项之一，把它做成脚本的最后一步，验收就自带证据 |
| **复用 `start.ps1` 起服务** | 在回归脚本里再写一遍启动逻辑 | 启动逻辑只有一份；回归脚本只负责"确保在跑"，不重复实现 |
| **断言写成"恰好这两条迁移"而不是"至少一条"** | 宽松断言 | 宽松断言会让"多出第三条状态变更事件"这种漂移溜过去 —— 而时间线上多一条假状态正是最难发现的错 |

### 回归之后的两次追加（2026-10-04 晚）

**一、前端二次打磨**（用户点名，参考主流后台：文档站侧栏 / 分栏登录页 / 右侧本页导航 / 仪表盘首页）

改动集中在三处，页面写法不变：令牌（补 `--radius-lg` 与两级阴影）、原语（面包屑、`Stat`、
`PageToc`、`Badge`、`EmptyState` 带行动入口、`Button` 的 `size/block`）、外壳（分组侧栏 +
粘性顶栏 + 独立全屏登录页 + 工作台首页 + 申请详情两栏目录）。

常驻显示/隐藏按钮、`[data-testid=app-nav]` 的链接集合与顺序、草稿页不含「审批进度」字样）。
验证：自检 12/12、页面实测 20/20、tsc/vitest/build 全绿、回归入口退出码 0。

**二、回归入口自己有个"假通过"的 bug（本轮抓到的）**

现象：`pytest` 明明输出 `1 failed, 221 passed`，入口却标成 ✓ 并给出退出码 0。

根因：`Invoke-Step` 里用 `$LASTEXITCODE` 判断成败，而 **`& $Body` 里的外部命令是在子作用域里跑的**
—— 它写的是子作用域的 `$LASTEXITCODE`，我在函数里那句 `$LASTEXITCODE = 0` 又恰好在本作用域建了
一个副本，于是比较的永远是 0。**修法**：把退出码检查放进**每个脚本块内部**（与外部命令同作用域），
失败就 `throw`，由 `Invoke-Step` 的 catch 统一处理。已用 `cmd /c exit 7` 单独验证过这条判据有效。

> 这条 bug 的价值在于它**差点让 M8 的结论失真**：M8 的"退出码 0"是在这个缺陷下得到的。
> 换句话说，**回归入口本身也是需要被回归的对象**——它报绿并不等于底层真的绿。

**三、它顺手撞出一个真 bug（已在当日确认后修掉）**

修好判定之后，全量测试在 5 轮里失败了 2 轮，而且是**两个不同用例、同一个根因**：

- `test_timeline_is_append_only_across_actions`：时间线里 `提交` 与 `生成审批链` 顺序颠倒
- `test_ledger_covers_all_three_kinds_and_sums_to_zero`：预算流水里 `SPEND` 与 `RELEASE` 顺序颠倒

根因是 M6 那次的"应用侧微秒时间戳"**只把概率压小、没有消除**：两个事件在同一个事务里写入时，
`datetime.now(UTC)` 可能落在**同一微秒**，于是 `ORDER BY created_at` 退化成 `id`（UUID）随机比较。
修法就是给只追加的日志加**单调序列列**（`seq`，identity）并按它排序 —— 时间戳只用来显示。
落地为迁移 `b7d3f0c41a26`：加可空列 → 按原排序键回填 → 补 `NOT NULL`。
**验证**：全量 5 轮连跑 **5/5 全绿**（各 222 passed）；迁移可逆（`downgrade -1` 后 9 条事件一行没少，
再 `upgrade head` 回填逐行一致）。

> 修这个 bug 时踩了一个值得记的坑：`budget_transactions.created_at` **没有数据库默认值**
> （`request_events` 那一列有 `now()`）。我按"对称"把应用侧时间戳一起去掉，
> 结果 `NOT NULL` 违约被 `_append` 的 `except IntegrityError` 接住，
> 报出来的是"这笔申请已经有一条 RESERVE 流水"——**底层原因被转换后的错误码盖掉了**。
> 教训：包装 `IntegrityError` 时不要把 `orig` 丢掉；同一个异常类不止一种成因。

**四、窄屏（<768px）补验：新增 `scripts\窄屏自检.mjs`（20 项）**

之前"响应式只做了断点类、没有窄屏验证"这条，用**真的把视口切成 375×812**（CDP 设备模拟）
补上了：四个页面横向溢出 **0 处**；侧栏在窄屏是页顶整宽横条（375px）、宽屏是固定左栏（256px）；
详情页右侧「本页导航」窄屏 `display:none`、宽屏 `display:block`；顶栏面包屑与页内面包屑
**两处不同时出现**。过程中查出并补上一个真缺口：**首页原本没有页内面包屑**，
而窄屏只有页内那一处 —— 手机上就完全没有"我在哪"这层信息。

> 关键判断：窄屏验证不能靠看截图，要靠**量断点两侧的客观差异**（375 → 256 的宽度跳变、
> `display:none` → `block`）。截图只能证明"这一刻好看"，量出来的差异才能证明"断点真的生效"。

## M9 · 附件与时间线（2026-10-04，**已完成**）

**一句话**：把"用户能把任意字节送进来"的那条通道做成了六步校验 + UUID 落盘 + 鉴权下载，
并把事件流水与审批进度拆成两个时间轴组件；验收在接口层与页面层各过一遍。

### 1. 这个阶段实际学到了什么？

- **"校验文件类型"不是一个检查，是四层**：文件名后缀 → 声明的 Content-Type →
  文件头 magic bytes → **真的解码一次**。前三层各自的绕过手法都是教科书级的
  （改名、伪造头、头对内容假），所以第 4 层（解码）才是唯一有实质成本的那道。
- **`verify()` 不等于解码**：本机实测五种损坏文件，`PIL.Image.verify()` 拦不住"截断的数据流"
  —— 它校验结构/CRC，不读像素。必须再 `load()` 一次。这条如果只照着文档写，
  会写出一个"看起来有压缩炸弹防护、实际漏一半"的上传接口。
- **压缩炸弹的防线要放在解码之前**：PNG 的宽高就写在 IHDR 里，几百字节的文件能声明 4 亿像素。
  先读尺寸、判上限、再决定要不要 `load()` —— 顺序反了，防护本身就变成了拒绝服务。
- **`fetch` 里 `Content-Type: ""` 不等于"没设置"**：浏览器会真的发一个空头，
  multipart 解析失败，后端报 `422 file: Field required`（完全指错方向）。
  必须 `Headers.delete("Content-Type")`。这是本轮**页面实测**抓出来的 ——
  单元测试与接口测试都碰不到它，因为它们不走浏览器的 fetch。
- **`IntegrityError` 只是一种异常，不是一种原因**（上一轮踩的）：同一轮里我把
  `created_at` 从应用侧挪给数据库，撞的是 `NOT NULL`，却被 `except IntegrityError`
  转成了"已经有一条 RESERVE 流水"。

### 2. 哪里卡了最久，为什么？

**两处，都是"绿色是假的"这一类：**

1. **单元测试的替身解码器写得太宽松**：第一版 `fake_png` 只判"开头是 PNG 头"就返回尺寸，
   于是"PNG 头 + 一句废话"被判成合法图片 —— **那条用例其实什么都没验**（它测的还是第 4 步）。
   是"DID NOT RAISE"这个失败把它暴露出来的。修法不是改断言，
   而是让替身**至少比 magic bytes 严一档**（要求出现 `IEND` 收尾块）。
2. **页面实测的上传断言挂住 12 秒**：文件注入没问题，`DataTransfer` 也对，
   真正的原因是上面那条 `Content-Type: ""`。**光看"上传按钮点了没反应"永远查不出来** ——
   最后是在浏览器里用三种写法（空串 / 不传 / `Headers.delete`）对比才定位到的。

> 这是本阶段最值钱的一条：**测试里的替身如果比被测边界松，绿色就是假的；
> 而浏览器与测试客户端之间的差异，只有真的在浏览器里点一次才会暴露。**

### 3. 有没有留下"以后再说"的坑？

- **有意留的**：PDF 只查文件头，不解析内容（解析不可信 PDF 本身就是攻击面）——
  这是计划里写明的取舍，不是债。
- **真债两条**：
  1. ~~附件没有删除端点~~ **已补**（用户点名，2026-10-04）：`DELETE /api/v1/attachments/{id}` →
     204，软删除 + 时间线留痕 + 界面二次确认。**软删除的代价是磁盘不会因删除而变小** ——
     留痕优先；真要回收空间是运维动作（孤儿文件判据见 `testdata_cleanup.py`）。
  2. 真实用户传几百 KB 扫描件的耗时**仍未验证**：进度条已补（限速下实测百分比在涨），
     但"慢网络上传完 10 MB 到底要多久"没有实测数字。

### 4. 为什么使用这样的技术栈，它比别的好在哪？

- **Pillow 只出现在一个文件里**，领域层拿"解码回调"：所以六步校验里最贵的那一步
  在单元测试里可以用替身毫秒级跑完，而"真解码器到底拦得住什么"由另一组真文件用例覆盖。
  依赖被关在一层的边界上，测试才能分层。
- **本地目录 + `storage_key`**：存进库的是"相对根目录的键"而不是绝对路径，
  将来换 MinIO / S3 时库里那一列不用动 —— 这也是"先发键再落盘"能成立的前提。
- **两个时间轴分开**（`RequestTimeline` 读 `request_events`、`ApprovalTimeline` 读
  `approval_tasks`）：看起来重复，但一个"只追加"、一个"会变"，
  M10 要加"付款完成"时才知道该往哪个组件里放。**混成一个的代价要到下一个阶段才付。**
- **下载走 `fetch` + Blob 而不是 `<a href>`**：多写十行，换来"错误能显示成人话"
  与"401 能自动续期重放"。直接指过去的话，用户看到的是一页 JSON。
- **上传走 `XMLHttpRequest` 而不是 `fetch`**：反过来，这一次是为"进度条"破例。
  两套各管一段、边界写在注释里：`fetch` 负责全部 JSON 接口（含续期重放），
  XHR 只负责"把字节发出去 + 报进度"。
  **为一个能力换一次工具，比给所有接口加一层抽象便宜。**

### 追加：删除端点与进度条（2026-10-04，用户点名）

- **删除为什么必须是软删除**：附件是审计证据。"曾经附过一份报价单、后来被删了"
  本身就是必须留痕的事实 —— 物理删除会让"当时到底附了什么"永远查不出来。
  配套两件事：时间线写一条 `ATTACHMENT_REMOVED`（否则时间线上**一片安静**），
  以及界面上的二次确认（没有撤销入口的操作不能点一下就消失）。
- **进度为什么用"订阅"而不是"回调参数"**：进度是随时间连续变化的值，天生适合订阅；
  包成 `uploadAttachment` 的参数，就等于整个客户端为一次上传破例。
  代价是要管退订（漏了就是内存泄漏），所以令牌记在 ref 里、卸载时统一退订。
- **到 100% 不等于完成**：100% 只说明**字节发出去了**，服务端还有"六步校验 + 落盘"那一段，
  所以文案写「校验中…」。把两段混成一句"完成"就是在骗用户。

### 追加二：一个真实的越权面（2026-10-04 修）

**症状**：`test_all_mode_creates_one_task_per_person_and_needs_all` 断言
"会签人待办里只有自己那一条"，实得 4 条。我第一反应是"测试数据脏了"——
**这个归因是错的**，真相比它严重：

`DEPT_MANAGER` / `DEPT_HEAD` 是**部门级角色**，建链时引擎确实按部门范围挑了人
（`_department_scope`），但**"办的时候"只校验角色名**：

| 位置 | 修前条件 |
| --- | --- |
| `list_todo` | 任务 PENDING + 当前级 + 我持有该角色（或我是预分配人）+ 提交人不是我 |
| `_assert_can_act` | 提交人不是我 +（会签：必须是我）/（或签：**我持有该角色**） |

结果是：**财务部的部门负责人能看到、也能批掉行政部那张单子的「部门负责人」那一级。**
它平时不现形，只因为开发库里恰好没有"另一个部门停在同一级"的单子 ——
也就是说，**这个 bug 的可见性依赖数据巧合**，而不是依赖任何一道防线。

**两条教训：**

1. **"测试失败"先别急着归因到测试。** 同一条失败既可能来自脏数据，也可能来自真 bug；
   区别在于**断言本身对不对**。这次断言（"部门负责人只该看到本部门的"）是对的，
   错的是实现 —— 所以正确的动作是**改实现**，不是改断言或加清理。
2. **权限要在"建"和"办"两侧用同一套判据。** 建链按部门挑人、办事只看角色名，
   这种"两处判据不一致"是最难发现的越权形态：中间没有任何一步会报错。
   修法也不是新造规则，而是复用 `resolve_request_scope`（申请列表、待办、决定三处同源）。

**刻意没做的事**：会签（`MODE_ALL`）那一支**不加**部门判定 ——
候选人本来就是建链时按部门挑的，再卡一次只会制造"被指派了却批不了"的死结。
这条写进了代码注释，免得以后有人"顺手补齐"。

**验收**：先写三条"应当失败"的用例（看不到 / 批不了 / 本部门照常批得了），
确认前两条真的红，再改实现，然后全量 313 → **316 passed**、回归入口退出码 0、页面实测 38/38。

> 还顺手改了一条测试的写法：`test_todo_list_is_one_query` 原来断言"SELECT 条数 ≤ 4"，
> 加了部门树那一条查询之后就站不住了。改成**比较 3 条待办与 6 条待办的查询条数是否相等** ——
> "不随行数增长"才是"没有 N+1"的证据，固定阈值只是在记录某一次实现的样子。

## M10 · 履约链（2026-10-05 起，**8.1 已完成**）

**一句话**：把"审批通过之后怎么买"的第一段做出来了 —— 待询价队列、登记报价、
比价表、定标；定标用条件更新抢权，并与主单推进、事件写在同一个事务里。

### 1. 这个阶段实际学到了什么？

- **"阈值"和"规则"要分开**：比价这条规则是"金额 >= 比价线时至少 3 家有效报价"，
  而比价线是多少是**制度参数**。把阈值当参数（从配置注入纯函数），
  测试就能拿它当入参 —— 想验"超过比价线"就把它调小、
  想验"低于比价线一家也能定标"就调大，**不必造两套数据**。
  这就是计划里那句"规则是纯函数、阈值来自配置"的实际收益。
- **"读端点里顺手做写"是有代价的**：惰性结算过期报价让状态列跟上判定，很方便；
  但它让一个 GET 必须提交一次事务，忘了就是**静默失效**
  （界面上永远看不到 `EXPIRED`，而判定又是对的）。这是项目里第一次在"读"里做写。
- **新增枚举值 = 改三处**：Python 枚举、状态机转移表、**数据库 CHECK**。
  第三处最容易漏，而漏了之后的报错会被应用层包装成"数据库暂不可用"，完全指错方向。

### 2. 哪里卡了最久，为什么？

**卡在"定标返回 503，但数据库好得很"。** 真实原因是主单状态 CHECK 还是 M6 的六档，
`AWARDED` 不在白名单里 → `CheckViolationError` → 被 `SQLAlchemyError` 处理器转成 503。
定位绕了三层：

1. 应用层把 `IntegrityError` 统一转成 503（**只记异常类型，不记栈**）；
2. 我的第一反应是"报价的幂等或唯一约束"，方向错了；
3. 最后**写一个探针直接调协调者**，并给 `Session.flush/commit` 挂上打印
   `exc.orig` 的钩子，才看到真正的 `CheckViolationError` 与那条约束名。

> 教训：**"数据库暂不可用"这句话本身不含信息。** 把底层异常全折成一个友好提示，
> 代价就是排障时要靠探针把它挖回来。一次性的探针（临时脚本 + 猴补 flush）
> 比反复读代码快得多，而且用完就删、不污染仓库。

### 3. 有没有留下"以后再说"的坑？

- **有意留的**：8.2–8.4（订单 / 收货 / 发票 / 付款）还没做，属计划内的分批；
  状态机里**只加了 `AWARDED`**，`ORDERED` 等用时再加（与"不留走不到的状态"一致）。
- **真债两条**：
  1. **比价线是全局一条**：做不到按品类分档。真要分档时第一步是给 `categories`
     加一列（回落全局），而不是现在预留空壳；
  2. ~~`EXPIRED` 只在"有人读"的时候才结算~~ **已修（2026-10-05）**：
     把"结算 + 读"合成唯一入口 `quotations_ready()`，所有应用内路径都过它，
     "忘掉结算"从"每处都要记得"变成"绕不过去"；并加了守门用例断言
     "走入口后状态列与时间判定一致 + 重复走幂等"。
     **仍未做到的是数据库级保证**：绕过协调者直接 `SELECT status` 依然可能读到过时的行 ——
     这条写在这里，不假装它不存在。

> **这一条值得单独记**：一开始我把"`EXPIRED` 靠惰性结算"当成实现细节写进注释，
> 认为"判定只认时间所以没问题"。但**报表是按状态列数的** ——
> 判定对、投影落后，统计就会错，而且错得不报错。
> 教训是：**凡是有"派生状态"的地方，都要问一句"谁会按它做统计"**，
> 而不只是问"判定会不会错"。

### 4. 为什么使用这样的技术栈，它比别的好在哪？

- **问题列表而不是布尔值**：`check_awardable` 返回
  `["金额超过比价线，至少需要 3 家…还差 1 家"]`，可以直接渲染到界面。
  返回 `False` 的话边界层只能编一句"不满足条件"—— 而采购专员需要知道的正是
  "差什么、差多少"。
- **比价表是只读视图、定标才是判定点**：读比价表永远 200（把"还差几家"放进
  `problems`），只有定标会 422。否则工作台会变成报错页，用户连已登记的报价都看不到。
- **定标复用提交/撤回那套幂等**：它同样是"重复执行会改变结果"的动作。
  并发由条件更新兜住（第二个人拿到 409），**重试**由幂等键兜住
  （同键同载荷 → 拿回第一次的响应；同键不同供应商 → 409"改了主意"）。

## M10 · 履约链 / 8.2 订单与收货（2026-10-05 完成）

**一句话**：定标之后能下单、到货能收货了；订单金额按"定标成交单价 × 数量"由后端重算，
收齐才把主单推到 `RECEIVED`。

### 1. 这个阶段实际学到了什么？

- **"砍功能"必须连状态一起砍**：部分收货被砍掉了，状态机里就没有
  `PARTIALLY_RECEIVED`。于是"收一半"**无处安放** ——
  我一开始写了"收一半允许、主单不动"，结果订单状态没地方放：
  订单会被改成"已收货"而主单还在 `ORDERED`，造出**模型禁止的组合**，
  而且它走不到任何终态。正解是**当场 422 并说清差哪几行**。
  教训：砍掉的不是"一个界面"，是**一整个状态**；剩下的代码必须按"这个状态不存在"来写。
- **"派生字段"不能靠响应模型自己解析**：`fully_received` 不是表上的列，
  我让读接口用 ORM 记录直接喂给 Pydantic，它退到默认值 `False` ——
  同一张收货单，**写接口说收齐了、读接口说没收齐**。
  修法不是"记得传这个字段"，而是让**读写两条路共用同一个响应体构造函数**，
  并把该字段设成**必填**（少给就当场报错，而不是静默给一个可能相反的值）。
- **"拒绝"也是一种正确的实现**：与其把模型不支持的情形"宽容地"收下再想办法表示，
  不如在入口说清为什么不行。用户改完再提交，比留下一份自相矛盾的数据便宜得多。

### 2. 哪里卡了最久，为什么？

**卡在"条件更新之后回读"——第四次踩，这次一次踩两处。**
收货要改两个东西（订单 → `RECEIVED`、主单 → `RECEIVED`），两处都是 bulk UPDATE
（`synchronize_session=False`）。会话里那份对象还是旧值，
于是**响应里"收齐了"显示成没收齐、订单状态显示成 `ORDERED`**（库里明明已经改了）。
第一轮我甚至怀疑是数据库没更新，去 `psql` 查了一遍才确认是**读到了会话里的旧对象**。

> 教训：这类 bug 的表现是"写成功了但读到的还是旧值"，非常像"事务没提交"。
> 判据很简单：**去数据库查一眼**。库里对了 → 一定是会话/身份映射的问题。
> 本项目已经把这条写进两个仓库的读方法注释，这次是第四次，说明
> **注释挡不住它** —— 真正能挡的是"条件更新之后回读必须显式写 `populate_existing=True`"
> 这条**写法**，所以我把开关做成了默认关闭的显式参数。

### 3. 有没有留下"以后再说"的坑？

- **有意留的**：8.3（发票与三单匹配）、8.4（付款与归档）没做；
  状态机只加了 `ORDERED` / `RECEIVED`，`INVOICED / PAID / CLOSED` 用时再加。
- **真债两条**：
  1. **收货只支持整单**：要恢复部分收货，必须按实施计划 5.5 节 E 的四步
     把 `PARTIALLY_RECEIVED` 连同转移、主单判定、验收项**一起**加回来 ——
     而不是把 `receipt_problems` 里那一句拒绝删掉（删掉就会造出禁止状态）；
  2. **一笔申请只允许一张订单**（`UNIQUE(request_id)`）：与"定标只选一家供应商"自洽，
     但**拆单**（一张申请分给多家供应商）进的是"暂时砍掉"清单 ——
     那要同时改定标（多家 `SELECTED`）、订单、三单匹配的粒度，三处绑定。

### 4. 为什么使用这样的技术栈，它比别的好在哪？

- **订单明细是"快照复制"而不是外键**：`item_id` 刻意**不加外键** ——
  订单一旦生成就是独立凭证，申请明细被替换（M5 的换明细是覆盖式替换）
  不该带走历史订单，而订单可能已经付过款了。这在 ER 图里定死，代码里也写了原因。
- **金额只有一个入口**：`build_order_lines` + `order_amount_fen`。
  单价来源（询价取成交价 / 直采取申请价）集中在一处，
  写错一次就会让订单总额悄悄变回申请金额 —— 而三单匹配会跟着一起错，
  **两边都错就互相抵消，谁也不会报错**。
- **收货人角色（`RECEIVER`）与采购分离**：内控要求采购、验收、记录三方分离，
  所以"采购自己不能收货"是**403 的角色闸门**，不是界面上的一个隐藏按钮。

## M10 · 履约链 / 8.3 发票与三单匹配（2026-10-05 完成）

**一句话**：能登记发票（可多张）了，并且有了三单匹配的**只读预检** ——
订单 / 收货 / 发票三列对比 + 问题列表；真正的拦截点在 8.4 的"执行付款"。

### 1. 这个阶段实际学到了什么？

- **"派生状态的缓存列"是个反复出现的坑**：ER 图给 `invoices` 留了 `matched`
  （是否已匹配），我没加。理由与 8.1 的报告口径是同一件事 ——
  `matched` 只在"有人跑匹配"时才更新，而"没人跑"与"跑过且通过"在库里的样子
  可能一样。所以匹配结果**每次现算**（它本来就只是一个问题列表）。
  这已经是同一类问题第三次出现了（`EXPIRED` 的惰性结算、`received_quantity`、
  现在的 `matched`），我开始把它当成本项目的一条**固定检查项**：
  **"这一列是谁写的、谁读的、没人写的时候它撒谎吗？"**
- **"算得出错"的常量也要有测试**：容差是 `max(金额 × 2%, 50 元)`。
  写成 `int(amount * 0.02)` 在 `0.02 × 2500` 上等于 `50.000000000000007` ——
  恰好落在边界上。改成整数万分比之后，专门写一条用例把这个数钉住。
  这是"禁止 float"这条纪律**真正救到人**的一次，而不只是风格问题。
- **两层判定比一层更难写错**：`match_three_way`（标量对整单）与
  `precheck_three_way`（先判"够不够格对账"）分开之后，`NO_ORDER` 不再被
  误报成"金额差超容差"。**指错方向的报错比不报错更贵** ——
  它会让人去查一个不存在的问题。

### 2. 哪里卡了最久，为什么？

**卡在测试的第一版跑不起来**：`_approve_my_level(world.head, …)` 报
"这个账号的待办里没有这张单子"。原因是我的测试数据把金额定成 240 元，
而审批链的第二级门槛是 `gte: 100_000`（1000 元）—— **金额太小，链上只有一级**。

> 这不算 bug，但它让我把"测试数据也要满足链路前置条件"这件事写进了辅助函数的注释
> （金额必须 >= 10 万元才够得到第二级）。**顺带得到一个更好的用例**：
> 申请 5800 元、订单 240 元 —— 差额 24 倍，"订单金额 ≠ 申请金额"这件事一眼可见，
> 比我原先设计的数字更能说明问题。

另外一处小坑：autogenerate 之后**又一次**要手工补主单状态白名单
（加 `INVOICED`）。这已经是第三次（`AWARDED`、`ORDERED`/`RECEIVED`、`INVOICED`），
所以这次我在迁移的 docstring 里把"必须手工补"写成了固定段落 ——
Alembic **看不见 CHECK 约束的内容变化**，这是工具的能力边界，不是偶发失误。

### 3. 有没有留下"以后再说"的坑？

- **有意留的**：8.4（付款与归档）没做 —— 三单匹配的**真拦截**在那里；
  状态机只加了 `INVOICED`，`PAID / CLOSED` 用时再加。
- **真债一条**：**`INVOICED` 目前没有"取消/作废发票"的出口**。
  登记错了只能靠改库。第一版没有作废需求（发票是外部凭证，改错该重开），
  但**这条要写下来**：真出现"录错发票号"时，正确做法是加一个
  `void` 端点（作废 + 写事件），而不是删行 —— 删行会丢掉审计痕迹。

### 4. 为什么使用这样的技术栈，它比别的好在哪？

- **问题列表贯穿全链路**：`check_awardable`（8.1）、`receipt_problems`（8.2）、
  `precheck_three_way`（8.3）返回的是同一种形状（`code` + 人话 + `expected`/`actual`），
  所以前端可以**用同一个组件**渲染三种差异，而"哪里不对、差多少"始终说得清。
- **预检只读、拦截在动钱那一刻**：预检可以随便点（前端渲染对比页要用），
  它不写任何东西；真拦截在"执行付款" —— 那是唯一能保证
  "校验通过后没有再改单据"的时机。**把只读与写分清楚，比在一个接口里两头兼顾安全得多。**
- **容差用整数万分比**：不合 float，边界可解释。代价是代码里多一个 `TOLERANCE_BP`
  常量与一次整除 —— 换掉的是"差 1 分算不算超容差"这种没法向用户解释的问题。

## M10 · 履约链 / 8.3 补：发票作废 + `payments` 两处定死（2026-10-05）

**一句话**：发票可以作废了（改状态、留痕迹、号可复用）；`payments` 的
`FAILED` 与唯一约束之间的矛盾在开工前解决掉了。

### 1. 这个阶段实际学到了什么？

- **`UNIQUE` 加错了对象，会把"合法的重试"也防掉。** 文档一处写
  "`FAILED` 保留痕迹、允许重新发起"，另一处写"一笔申请只允许一笔付款：
  `UNIQUE(request_id)`" —— 两条直接冲突：第一次失败之后**连付款单都建不出来**，
  而它表现为一个数据库冲突，看起来像偶发故障。
  判据是：**这条约束防的是"同时存在两条"，还是"历史上出现过两条"？**
  前者用**部分唯一索引**（带状态条件），后者才用普通唯一约束。
  顺带发现：文档第 2484 行**已经给出了正解**（部分唯一索引），是我先前只读到 2463 行。
  **教训：文档里"自相矛盾"的两处，往往其中一处附近就写着解决办法 ——
  先把相关的几十行读完，再决定要问什么。**
- **"作废"这类功能的难点不在接口，在"金额口径只有一处"。**
  作废唯一的作用是"不再参与金额计算"。实现上真正要防的不是"忘了过滤"，
  而是过滤条件散在四五个查询里、早晚漏一处 —— 而漏掉的那处会
  **拿着含作废票的合计去付款**。所以我把 `_active_only(...)` 收成一处，
  让"只算有效"成为所有金额查询的必经之路。
- **纠错路径也是需求。** "录错发票号"是必然会发生的事。原来的普通唯一约束
  会让作废的那行一直占着号，于是**最正常的纠错路径被自己的约束挡住**。
  设计约束时要连着问一句：**"录错了怎么办？"**

### 2. 哪里卡了最久，为什么？

**卡在一个我自己造的小坑上，但它的性质值得记**：作废之后前端显示不出"已作废"，
因为 `invoice_payload` **没有 `status` 字段** —— 而发票列表默认**连作废票一起返回**
（那是刻意的：不显示会让人以为从没登记过）。于是测试里 `body["invoice"]["status"]`
直接 `KeyError`。

> 这不是打字错误，而是**"响应体构造只有一处"这个决定救了我**：
> 因为读写两条路共用 `invoice_payload`，补一个字段就两处都对了。
> 8.2 的 `fully_received` 是反例（两处各拼一份，于是读写各说一套）。

另一处：`_active_only(statement)` 这个辅助函数我一开始按"内部工具"写了
`def _active_only(statement):`，mypy 的 `disallow_untyped_defs` 直接报错。
补上 `Any` 之后 ruff 又提示 `type: ignore` 是多余的 —— **两个工具各纠了我一次**，
这正是"静态检查不是走过场"的样子。

### 3. 有没有留下"以后再说"的坑？

- **有意留的**：8.4（付款与归档）没做 —— 三单匹配的**真拦截**在那里；
  状态机只加了 `INVOICED`，`PAID / CLOSED` 用时再加。
- **真债一条（新）**：**作废没有"撤销作废"**。作废错了只能再登记一张 ——
  对发票来说这是对的（号可以复用，等于重录），但**如果将来要支持
  "作废需要审批"**，那要在 `void_invoice` 前面加一道待办，而不是改这里的判定。
  这条记下来，不做。

### 4. 为什么使用这样的技术栈，它比别的好在哪？

- **状态列 + 部分唯一索引，是"软删除/作废"这类需求的正确组合**：
  状态列让历史留着（可审计、可解释），部分索引让"有效的那一份仍受约束"
  （不会因为作废而出现两条有效记录）。两者缺一：只留状态 → 有效数据可能重复；
  只留索引 → 纠错路径被堵死。
- **判定进领域层，结论翻译在协调者**：`can_void_invoice` 只说
  "能不能作废、为什么不能"（纯函数，6 条单测覆盖），
  协调者把它的结论翻成 409 / 404。于是"规则"能被毫秒级测完，
  而"HTTP 语义"只有一处。

## M10 · 履约链 / 8.4 付款与归档（2026-10-05 完成）—— **M10 闭环**

**一句话**：能付款、能归档了；付款是这个系统里唯一真正动钱的操作，
所以它的顺序（先抢付款权、再动预算）和"差额显式释放"是这一段最要紧的两件事。

### 1. 这个阶段实际学到了什么？

- **"先抢权、再动钱"这个顺序，是并发正确性的全部。** 两个财务同时点"付款"，
  正确的做法是 `UPDATE payments SET status='PAID' WHERE id=? AND status='PENDING'`
  的 `rowcount` 判定，而且**必须在动预算之前**：
  抢输的一方在 `spend_budget` 之前就退出了，所以它根本没机会多记一笔。
  反过来的话（先动预算、再抢权），两个请求会**各动一次预算**，
  而回滚只能救其中一个 —— 这是"顺序即正确性"最直白的一次。
- **测试并发必须用真并发，而且幂等键要分开。** 顺序调用两次"付款"，
  第二次会被"付款单不是 PENDING"挡住 —— 那验证的是"第二次会失败"，
  **不是**"两个请求同时到达时只有一个赢"。而如果两个请求用**同一把幂等键**，
  第二个会被幂等层拦成"重放"（返回 200），于是条件更新那一层根本没被测到。
  所以验收项"两个人同时付款"必须写成：`asyncio.gather` + **不同 key**。
- **"失败"和"没成功"是两件事，得分开建模。** `FAILED` 要保留痕迹
  （财务要知道"试过一次、为什么失败"），而"没成功"只是还没做。
  这也正是那处 `UNIQUE` 冲突的根源：把"历史上出现过两条"和"同时存在两条"
  当成同一件事，就会把合法的重试一起防掉。

### 2. 哪里卡了最久，为什么？

**这一阶段没有卡很久**（23 条集成一次跑通），但有一处值得记：
`test_create_payment_before_invoiced_is_refused` 里我写了一句
`del driven  # 只是为了让 driven 的清理生效` —— 那是**凑出来的写法**：
`_drive_to_invoiced` 会往 `world.requests` 里登记申请，所以即使我不用它的返回值，
也**必须调用它**才能让清理逻辑覆盖到那张申请。写成 `del` 只是为了让变量名"被用到"。

> 更好的写法是让辅助函数自己登记、调用处不必假装使用返回值。
> 我保留了这个痕迹并写下它的原因 —— 因为**"为了通过 linter 而写的代码"**
> 是个信号：说明接口设计得不顺手。下次遇到同类情况，改接口而不是加噪声。

另外：autogenerate **第四次**漏了 CHECK 约束的内容变化（要加 `PAID` / `CLOSED`），
但这次它**正确生成了部分唯一索引**（`postgresql_where` 方言参数），
这是本项目第一次不用手工改索引 —— 说明模型层的 `Index(..., postgresql_where=...)`
写法与 Alembic 的映射是可靠的。

### 3. 有没有留下"以后再说"的坑？

- **有意留的（也是 M10 唯一剩下的）**：**前端页面全都没有**。
  后端 8.1–8.4 的 12 条路由都已可用并验收，但界面上还没有
  "下单 / 收货 / 收票 / 作废 / 三单匹配对比页 / 付款 / 归档"这些入口。
  这是**有意的分批**（后端先闭环，前端一次做），不是遗漏。
- **真债一条**：**`payments` 没有"退款 / 冲正"**。
  付错了只能靠线下处理，系统里没有反向流程。
  第一版没有这个需求（付款是终点），但**"付错了怎么办"迟早会被问到** ——
  到时要加的是一个新状态（`REFUNDED`）+ 反向流水，而不是改 `PAID` 的语义。
- **一处刻意的边界**：`pay` 里 `request.budget_id is None` 时**不报错**，
  把它当成"这笔钱不走预算"（M7 之前提交的历史单据）。
  这与 M7 的 `_release_all` 同一口径；但它也意味着**历史单据付款时不会有预算流水** ——
  测试里覆盖不到那条路径（需要造一张没有 `budget_id` 的单子），如实记下来。

### 4. 为什么使用这样的技术栈，它比别的好在哪？

- **部分唯一索引 + 条件更新，是"可重试的独占操作"的标准组合**：
  索引保证"至多一条有效记录"（数据层不变量），条件更新保证"同一行只被推进一次"
  （并发不变量）。两者职责不同、缺一不可，而且都**不依赖应用层的先查后写**。
- **`settle()` 是一个方法，而不是调用方写两次**：M7 就把
  "SPEND(实付) + RELEASE(差额)"封成了一个入口，8.4 只是调它。
  于是"差额必须显式释放"这条规则**在新的调用点自动成立** ——
  这是"把容易漏的两步封成一个不可分割的操作"带来的直接好处。
- **预算三个数（总额 / 已预留 / 已花）贯穿全部断言**：
  付款的验收不只看状态码，而是看这三个数的此消彼长。
  这类不变量"错了不会报错，只会让账慢慢不对"，所以只能用断言钉住。

## M10 前端 · 履约工作台（2026-10-06 完成）—— **M10 收口**

**一句话**：一页串起"询价定标 → 下单收货 → 收票匹配 → 付款归档"，
用真实浏览器跑通了从申请到归档的完整一笔，并顺手修掉一个后端真 bug。

### 1. 这个阶段实际学到了什么？

- **"验证"最贵的成本是定位，不是重跑。** 这一轮页面实测失败了很多次，
  每一次的现象都**长得像产品 bug**：点链接没反应、按钮找不到、第一次点付款没反应。
  真因全部在测试侧或测试数据侧：提交人选错导致自审、等了一个会消失的渲染状态、
  在列表还没渲染完时点它、或签级没先认领、选择器撞上两个同样的 placeholder、
  上一步没等完就点下一步。
  **真正的转折点是我让失败自己带证据**：`waitFor` 超时时打印
  「URL + 页面文字 + 按钮清单」，一次就把"页面上只有「认领这条任务」"摆出来了。
  > 教训：**测试脚本的报错质量，决定了调试速度的上限。**
  > 只报"等待超时：某标签"会让人反复重跑 —— 我为这一个脚本重跑了 6 轮。
- **同一件事写在三处，就一定有一处会漂。** 履约工作台的可见性同时写在
  侧边栏菜单、路由守卫、首页快捷入口。三处不一致的表现是"菜单上有、点进去说无权限"。
  所以加了三条浏览器断言专门守它 ——
  **当一件事必须在多处表达时，给"它们一致"写一条自动化断言**，比每处加注释有用。
- **相对断言 > 绝对断言。** 预算那条断言我写死 `已花 === 30000`，
  而那条预算会被多轮实测复用，库里还留着别的运行的预留 —— 于是失败在一个
  **与本次流程无关**的数字上。改成"进入这一段先记基线、之后比变化量"就稳了。
  这在"共享开发库 + 可重复运行的测试"里是必然要处理的问题。

### 2. 哪里卡了最久，为什么？

**卡在"第一次点执行付款没反应"，三轮才找到真因。** 现象是按钮在、点了、状态没变；
我用集成测试同样的数据直接调接口 → **200**；于是怀疑前端；写了 CDP 探针（没跑通）；
最后让页面实测"点两次并记录两次现场"，一次看清：**第一次点击时按钮还是 `创建中…`**
—— 我点的是上一步（创建付款单）还在进行中的页面。

> 根因是"我没等上一步结束就点了下一步"。但让我绕三圈的，是
> **"接口 200 而页面没动"**这个组合 —— 它天然指向"前端坏了"。
> 教训：**先怀疑测试的时序，再怀疑产品。** 脚本里"点 A 然后点 B"这种序列，
> 每一步都要以**那一步的完成信号**为准（按钮回到可点状态），
> 而不是以"某段文字出现"为准 —— 那段文字可能来自上一步的渲染。

### 3. 有没有留下"以后再说"的坑？

- **有意留的**：M11 还没开始；工作台**没做批量处理**（队列一次 50 条、逐笔打开）——
  一天几十笔够用，上百笔再谈。
- **真债两条**：
  1. **`payments` 没有退款/冲正**（8.4 已记）；
  2. **履约工作台的可见性判断写在三处**（菜单 / 路由守卫 / 首页入口）。
     现在有浏览器断言守着，但更好的做法是收成一处常量
     （例如 `lib/roles.ts` 导出 `FULFILLMENT_ROLES` 与 `canFulfill(roles)`）。
     这次没做，因为它属于"顺手重构"，不在点名的范围内。

### 4. 为什么使用这样的技术栈，它比别的好在哪？

- **一个页面 + 按角色出现的队列**，比"四个独立页面"少三样：
  少三次菜单跳转、少三次重复查询、**少三处权限判断**。
  代价是这个文件较长（1200 行），所以它按"队列卡片 / 链路面板 / 六个子面板"分段，
  每段都有说明**为什么这样分**。
- **API 层分部委**：`client.ts` 承担横向职责（续期、上传进度、统一错误体），
  M10 的 17 条路由是纵向业务，放进 `api/fulfillment.ts`——
  两个文件的读者关心的事不一样，这比"所有接口堆一个文件"更好找。
- **`useIdempotencyKey()` 把"什么时候换键"收成一个 hook**：
  这个时机很容易写错（每次渲染都换 = 没有幂等；永不换 = 失败重试撞 409），
  收成一处置之后，六个写操作都只需 `const [key, rotate] = useIdempotencyKey()`。

## M11 · AI 制度助手（2026-10-06 完成）

**一句话**：一套**先检索、后模型**的制度问答 —— 上传制度 → 切分 → 向量检索 →
阈值判定（没依据就不问模型）→ 回答必须标引用 → **引用再事后校验一遍** → 流式返回。

### 1. 这个阶段实际学到了什么？

- **"不编造"不是一句提示词，是三道闸门。** 这一阶段最值钱的不是接了模型，
  而是把"什么情况下**不许**答"写成了代码：
  ① 检索为空 → 不问模型；
  ② **检索有结果但全部低于阈值 → 也不问模型**（这条最容易被漏：检索永远返回 top-k，
     问一个制度里没有的问题时它会把最不相关的片段递上来，模型于是拿着不相干的材料硬答）；
  ③ 答完了还要校验引用是不是真的（引了不存在的编号、或者通篇断言却一个引用都没有）。
  **"有引用"不等于"引用是真的"** —— 这是相对原项目真正的增量。
- **判定要落在"实际发生了什么"，不是"打算做什么"。** `used_model` 我一开始写成
  `decision.use_model`（"可以问模型"），而它的语义是"**远端模型真的被调用了**"。
  本地兜底下一次网络调用都没发生，字段却是 `true` —— 于是"未调用模型"这条验收项
  永远显示错误。**字段名说的是"发生了什么"，就不能用"打算做什么"去填。**
- **"本地兜底"是一等公民，不是错误分支。** 没密钥时用抽取式回答（把最相关的
  制度原文摘出来并标引用）。它显然不如模型，但它让"检索 → 阈值 → 引用 → 校验 → 流式"
  这五件事**全都可离线验证**，而且让整套测试不依赖网络、不花钱。
- **测试脚本的报错质量，决定了调试速度的上限**（M10 的教训在这里又兑现一次）：
  这一轮我给两个子代理都明确要求"超时要打印 URL + 页面文字 + 按钮清单"，
  于是它们各自一次就把问题定位到了（一个找出前端 `done` 未回调，
  一个找出清理脚本会误删制度原文）。

### 2. 哪里卡了最久，为什么？

**卡在四个"看起来像别的毛病"的问题上**，每一个都值得记：

1. **重复版本报 503 而不是 409**：`UNIQUE(source_key, version)` 的异常被
   SQLAlchemy 推迟到了后面那条"插入片段"的 SQL 上才抛 —— 我的 `except IntegrityError`
   围的是 `create_doc`，于是异常一路冒到全局处理器，变成
   **"数据库暂不可用"**（数据库好得很）。修法两层：**显式查重**给一句人话的 409，
   同时在 `create_doc` 里**显式 flush**（让异常在最接近它原因的地方抛出）。
2. **所有 `.txt` 制度被 422 挡掉**：`httpx` 对 `text/plain` 的 multipart 部分
   **不发 `Content-Type`**，Starlette 给的是 `None`。加"按扩展名补全"之后我又**把优先级搞反**，
   于是"声明 `application/pdf` + 文件名 `.txt`"被当成纯文本收下
   （一条"应当被拒"的用例变成了 201）。**顺序必须是先看声明、只在声明缺失时补全。**
3. **测试隔离**：`World.purge` 只按 `uploaded_by` 删文档，而 admin 是**共享账号** ——
   等于"把所有用例的文档都当自己的"，漏删的表现是下一条用例看到上一条的数据
   （空库用例看到 1 条来源、版本过滤用例同时命中 1 和 2 两版）。
   修法：**两种条件都删**（按账号 + 按本用例的 `source_key`）。
4. **两条用例在并发下失败**：我一边跑全量 `pytest`、一边让子代理跑清理脚本 ——
   清理脚本把测试正在用的数据删了。**串行重跑全绿**。
   教训：**清理脚本与测试不能同时跑**，它们的判据天然冲突。

### 3. 有没有留下"以后再说"的坑？

- **有意留的**：只收 `.txt` / `.md`（PDF 要额外依赖）；本地 embedding 不做语义检索。
- **真债三条，都要写清楚**：
  1. **远端模型那条路没有被真实执行过**：本机没有密钥，`OpenAiCompatibleChat`
     只有单测级别的依据（协议公开稳定 + 对分片/非 JSON/缺 choices 都有处理）。
     它**不影响任何一条校验** —— `decide_grounding` 与 `check_citation_integrity`
     都在它之外，换模型绕不过去；
  2. **本地 embedding 不能用来评估效果**：它靠字面重合，"多少钱要招标"这种
     换个说法的问法检索不到。它能证明"链路通"，不能证明"RAG 设计好"；
  3. **收 PDF 时要补魔数校验**：现在只按声明类型 + 扩展名补全，**不校验文件内容**
     （制度文档不执行、不渲染，所以第一版没做；收了 PDF 就必须补）。

### 4. 为什么使用这样的技术栈，它比别的好在哪？

- **向量运算全在数据库里**（pgvector 的 `cosine_distance` + HNSW 索引），
  Python 侧只装一个**适配层**（`pgvector`，没有 numpy）——
  "怎么算距离"是数据库的强项，把它搬到 Python 只会多一份内存与一次全表搬运。
  代价是一处必须记住的细节：**查询里的算子要与索引的算子一致**
  （索引是 `vector_cosine_ops`，排序就必须用 `cosine_distance`），
  用错时查询照样能跑、**只是慢**，不报错。
- **版本过滤用一句 `DISTINCT ON` 表达**：按 `source_key` 分组、每组取版本最大且已生效的那一版。
  比"先查全部再在 Python 里筛"少一次全表搬运，而且**判据只有一处**——
  制度修订后新旧条文同时被检索到，比查不到更糟。
- **引用校验是纯函数**：`check_citation_integrity` 不碰数据库、不碰模型，
  所以"构造一段引用了不存在编号的回答"这种验收可以**毫秒级**跑，
  而且可以用一个假模型稳定复现（真模型只会偶尔这样）。
- **同一套流式协议对接任何兼容 OpenAI 的服务**：换供应商只改 `base_url` 与模型名，
  界面与 SSE 协议完全不动。

### 这十一个阶段真正学到的东西（按"不可替代性"排）

1. **并发只能靠条件更新，不能靠先查再写。** 审批决定、预算预留、付款——
   三处都是"改状态 + 判定胜负"的同一个套路。`rowcount != 1 → 409` 这一句
   在项目里出现了六次，而每一次它挡住的都是"重复扣款 / 重复付款"这类真事故。
2. **"不会报错、只会算错"的地方最值钱。** 项目里明确标出三条：
   审批链不许为空、预留与实付的差额必须**显式释放**、权限范围必须写进 `WHERE`。
   它们都不是靠"小心"能守住的，只能靠**主动去撞**（各自的回归探针）。
3. **派生状态是长期负债。** `EXPIRED` 的惰性结算、`received_quantity`、`matched`、
   `fully_received` —— 四个都出现过"列里的值落后于事实"，而且都不报错。
   项目最后形成的判据是：**这一列谁写、谁读、没人写的时候它撒谎吗？**
4. **测试脚本的报错质量决定调试速度。** M10 我为同一个脚本重跑了六轮，
   直到把 `waitFor` 改成"超时打印 URL + 页面文字 + 按钮清单"，问题一次就看清了。
   M11 把这个要求写进给子代理的任务书里，它们各自一次定位到真因。
5. **"砍功能"必须连状态一起砍。** 部分收货被砍掉，状态机里就没有
   `PARTIALLY_RECEIVED` —— 于是"收一半"无处安放，只能当场拒绝。
   留下一个走不到的状态，会让整批状态机测试失去意义。
6. **配置项是"制度参数"，不是"规则"。** 比价线、阈值这些从配置来，
   而"至少 3 家""容差 max(2%, 50 元)"留在纯函数里 ——

## M11+ · AI 模块增强（2026-10-14 完成）—— **把"能跑"推到"能衡量、能回归"**

**一句话**：M11 只做到"链路通"（哈希 embedding + 抽取式兜底）；
这一段给 AI 模块补上了**量化判据**与**回归门禁**，并把 embedding 换成真语义模型。

### 1. 这个阶段实际学到了什么？

- **评测要分层，否则永远说不清是谁的错。** RAG 出问题时只有两种可能：
  "该找的资料没进上下文"（检索问题）还是"资料进去了但答案还是错的"（生成问题）。
  只测"最终回答对不对"永远分不开这两者。所以指标拆成
  **检索层**（Recall/Precision/MRR/NDCG）与**生成层**（引用完整性 + 支撑率）。
- **"不适用"与"0"必须分开，这条纪律出现了四次。**
  `support_rate` 的 `None`（没有引用句）≠ `0.0`（引用全不可信）；
  检索指标对"无答案问题"要返回 `None` 而不是 0；
  MRR 要**剔除"没返回任何结果"的用例**（算进去 0.879、剔除后 0.977）；
  成本核算里"拿不到用量"是 `None`、"本地模型"是 `0`。
  **把不适用当 0，均值会被系统性压低，而没人知道为什么。**
- **污染的数字比没有数字更危险。** 评测第一次跑出 MRR 0.977，
  我照它把门禁阈值定成 0.90 —— 后来发现那 0.977 是**库里有上一轮残留文档**导致的
  （定位标记映射到了别的片段）。真实值 0.879，门禁一上线就红。
  **错误的数字会让你把阈值定在错误的位置上**，比没有数字糟得多。
- **阈值与 embedding 是一对，不能只换一个。** 换真 embedding 之后
  `min_score` 不动，会从"该答的不答"直接翻到"**不该答的全答了**"
  （5 条无答案问题全部越过 0.15）。阈值必须按**实测分数分布**重新标定。
- **`min_score` 这类"唯一判据"最值得写进文档**：它调错的表现是两个极端，
  而两端看起来都像"功能坏了"，与阈值本身无关。

### 2. 哪里卡了最久，为什么？

**"验证工具自己坏了"这一类问题，一共三处，累计花的时间最多。**

1. **三条分层自查一直是假通过**：`Select-String -Path app\**\*.py` 在 PowerShell 里
   **不递归**（`**` 只当一层通配），所以 `infrastructure/records/` 从没被扫过 ——
   而那里早就写了 `Mapped[float]`，自查却一直报"0 命中"。
   **修的时候顺手加了"自证探针"**：每次自查都造一个必然违约的临时文件，
   确认扫描器抓得到，抓不到就报错。没有这一步，"0 命中"可能只是"什么都没扫到"。
2. **用量帧被正文解析器丢掉**：OpenAI 流式的用量帧 `choices` 是**空数组**，
   正文解析器取不到 `choices[0]` 就返回空串 —— `prompt_tokens` 永远是 0，
   而"永远是 0"很容易被读成"模型不要钱"。
3. **`getattr(dict, "content", "")` 静默取空**：配额记账时来源是**序列化过的字典**
   而不是 `Source` 对象，于是每条来源都算成 0 token（实测该记 148、只记了 20），
   **配额上限形同虚设**。

这三处的共同点：**都不会报错，只会算错**。判据只能靠"实际取值对账"
（对着 `手工估算 vs 已记` 两个数才看出来），所以它们最后都进了**接缝探针**。

**另一件卡了很久的是环境**：Ollama 1.5 GB 安装包从 GitHub 各镜像下载都只有
3–37 KB/s；官方站也不行；本机没有 MSVC 编译器所以编译 `llama-cpp-python` 走不通。
最后是**浏览器下载**解决的。教训：**下载被限速时不要在命令行里硬扛**，
先量一遍各源的真实吞吐，再决定走哪条路。

### 3. 有没有留下"以后再说"的坑？

| 坑 | 类别 | 说明 |
| --- | --- | --- |
| **对话模型仍是本地抽取式兜底** | **真债（下一步第一件事）** | 所以"支撑率 1.000"是**兜底的数字**；接上真对话模型后一定会掉，那才是有意义的时刻。配置位（`KNOWLEDGE_LLM_*`）已留好 |
| **没有重排 / 混合检索** | 真债 | `Precision@5 = 0.500` 的靶子已立，对比基准就位 |
| **2 条无答案问题是阈值解决不了的** | 有意（属 Agent 层） | U-02/U-05 与制度语义高度相关、只是条文没那一档；要靠"回答前先反问"或更强模型 |
| **`bge-m3` 没拉下来** | 有意 | 1.1 GB，本机到 registry 只有 50–210 KB/s；中断后留下**无法完成**的 `-partial` 文件（白占 1.1 GB，已删）。换它还要把列维度迁到 1024 |
| **配额与限流是进程内字典** | 有意 | 单进程 uvicorn 够用；多实例部署时要换共享存储（这一点写进了模块注释） |
| **评测语料只有 3 份文档 / 27 个片段** | 有意 | Recall 1.000 建立在**小语料**上，规模一大就会掉 —— 文档里明确写了这条边界 |

### 4. 为什么使用这样的技术栈，它比别的好在哪？

| 选择 | 比什么好 |
| --- | --- |
| **pgvector + HNSW**（不引独立向量库） | 向量与业务数据在**同一个事务**里 —— 制度入库失败时不会留下"有片段没向量"的半截状态；少一个活动部件（Milvus/Qdrant 要单独维护、单独备份） |
| **Ollama**（不引 LangChain/独立推理服务） | 它提供 **OpenAI 兼容 + 原生 `/api/embed`** 两套接口，所以后端 `OpenAiCompatibleChat` **一行没改**就换上了真模型；它同时管模型下载与 GPU 运行时，比"自己装 llama.cpp + 自己写包装"少两个活动部件 |
| **`EmbeddingPort` 抽象 + 维度注册表** | 换个 embedding 只改一处配置；而"没登记的模型直接报错"把维度不符的失败**提前到应用层**（数据库只会说 `expected 512 dimensions`，不会说"是哪个模型"） |
| **评测集用"定位标记法"** | 期望命中的片段靠制度文本里的 `[[c2]]` 标记自动解析成 chunk id —— **改切分参数不用改评测集**；写死 chunk 编号的评测集改一次切分就全废 |
| **质量门禁进回归入口** | 与其它 14 步同一个纪律（**不接受任何开关**）。"这次时间紧、少跑一项"这条路被堵死了 |
| **成本用整数微元、`BIGINT`** | 与"金额用整数分"同一条纪律。`Integer` 上限只有 2147 元，一个月的 token 费用很容易超 —— 而 PostgreSQL 溢出会**直接报错**，于是成本统计会在某个不起眼的时刻开始写不进去 |
| **配额按 token 而不按请求数** | AI 接口的滥用成本在 token 上：1 秒 10 次 × 6000 token 上下文，账单按 token 涨而"请求数"看起来正常 |

## M12+ · Function Calling 与最小 ReAct（2026-10-14 完成）—— **让 Agent 以调用者身份动真实数据**

**一句话**：这是 JD 里权重最高、也是之前**唯一完全空白**的一项。
做完之后，模型能自己决定去查真实业务数据，而**权限、事务、审计全部复用既有那套**。

### 1. 这个阶段实际学到了什么？

- **Agent 的安全边界不该建在提示词上，要建在身份上。**
  "不要越权"写在提示词里是**请求**；而工具以调用者的 `Principal` 走同一批用例、
  参数里**根本没有"以谁的身份"这个字段**，那是**结构**。
  两者的差别在被提示注入时才会显出来：前者靠模型自觉，后者模型想越权也没有那条路。
- **写操作必须两段式。** 模型自作主张建了十几张草稿，人只能一张张删 ——
  而"草稿"看起来无害，实际会占单号、出现在列表里、被同事当真需求去审批。
  所以"模型说要做"与"真的做了"之间必须有人。
- **护栏要能确定性造出来。** 轮次上限、连续失败、坏 JSON 参数这三条，
  用真模型去碰是碰运气（今天不循环不代表明天不循环）。
  所以用**按剧本走的假模型**把每一种失控都造出来，测试才算真的守住了。
- **"两条路共用一段逻辑"这句话，要靠代码结构保证，不能靠自觉。**
  实测踩到：Agent 分流只加在流式那条路，非流式照旧回"制度中没有找到相关规定"，
  而 curl 与集成测试打的偏偏是非流式 —— **功能写了却像是没效果**。
  改成 `_should_use_agent` 一个方法、两条路都调它之后，这种不一致才不可能发生。
- **审计字段说谎比没有字段更糟。** `used_model` 只判"是不是本地兜底实现"，
  而 Agent 走的是另一个方法（`stream_turn`）—— 于是一个花了几秒模型时间的回答
  被记成"未调用模型"。**一个错的字段会让人得出反向的结论。**

### 2. 哪里卡了最久，为什么？

**最久的是"协议装不下工具调用"这件事。**

`ChatModelPort.stream()` 只 yield 文本，而工具调用是结构化对象。
三个选项：① 把工具调用塞进文本流（要解析特殊标记，脆弱且会污染现有契约）；
② 改成一个"既可能是文本也可能是工具调用"的事件流（**每个**消费方都要写分派，
写错的表现是"工具调了但没人执行"，静默）；③ 加一个**新方法**，两条路在协调者汇合。

选 ③。代价是模型适配器有两个方法，收益是**现有的 54 条浏览器断言与 25 条集成测试
一条都不用改** —— 而"为了加功能把既有验证全改一遍"的风险远比多一个方法大。

**第二个卡点**：Ollama 的工具调用格式与 OpenAI 不一样
（NDJSON vs SSE、`arguments` 是**对象** vs **分片拼接的字符串**、一帧给完 vs 多帧）。
所以工具回合走**原生 `/api/chat`**，文本流走 `/v1/chat/completions` ——
两条端点、各用各的长处，而不是把解析写成"猜格式"。

**第三个卡点**：`ToolSpec.required` 写成了 `field(default_factory=frozenset)`
而 `__post_init__` 没算它 → **必填变成空集，模型不给参数也能通过校验，还不报错**。
这类"默认值恰好是空集"的错读代码时完全不可疑，只能靠测试撞。

### 3. 有没有留下"以后再说"的坑？

| 坑 | 类别 | 说明 |
| --- | --- | --- |
| **前端还没渲染 Agent 步骤** | **真债（本轮收口最后一件）** | 后端已在推"正在查 XX"，界面还只显示转圈 —— 用户看不到它在干什么 |
| **写工具的确认入口没接** | 真债 | 后端能生成确认令牌，还没有"确认即执行"的端点 |
| **3B 模型在"该不该调工具"上会摇摆** | 有意（换模型即可） | 同一个问题有时调、有时直接答。换 `qwen2.5:7b-instruct` 更稳；**`Coder` 系是代码微调版，tool calling 不是它的长项，不建议当主力** |
| **没有任务规划（只有逐步反应）** | 有意 | 现在是"走一步看一步"，不是"先订计划再执行"。它是 Agent 与"会调工具"之间最后那一段 |
| **没有跨会话记忆** | 有意 | 会话历史已在库里，对当前场景够用 |
| **没有 MCP / 插件机制** | 有意 | 工具是**代码内注册**的（Schema + 校验 + 权限都在仓库里），可控性优先于扩展性 |

### 4. 为什么使用这样的技术栈，它比别的好在哪？

| 选择 | 比什么好 |
| --- | --- |
| **自研最小 ReAct（不引 LangChain / AutoGPT）** | 循环只有 100 行，三条护栏一目了然、可确定性测试；引框架的话，"它默认重试几次、超时怎么算"都得去读它的源码，而**这些正是会烧钱的参数** |
| **工具复用 `RequestScope`（不新建 Agent 权限体系）** | 权限判定只有一处，工具与接口不可能不一致；**被提示注入时模型也拿不到调用者本来没有的数据** —— 这不是靠提示词，是靠身份 |
| **`stream_turn` 新方法（不改 `stream`）** | 既有 54 条浏览器断言与 25 条集成测试一条都不用改；文本流与工具调用在协议层形状本来就不同 |
| **工具回合走 Ollama 原生 `/api/chat`** | 一帧给完整调用、`arguments` 是对象 —— 聚合逻辑比解析 OpenAI 的分片 JSON 简单得多，也更不容易错 |
| **JSON Schema 自己校验（不引 `jsonschema`）** | 契约面窄（7 个关键字）但**语义完全可控**：未知关键字、未知参数、`bool` 不是整数，都是显式规则。引库意味着"它多支持一种写法，我们的校验行为就跟着变"，而这条路径的失败是静默的 |
| **发给模型的 schema 与校验用的 schema 是同一份** | 分成两份迟早不一致，而"模型以为正确的调用被自己的校验拒掉"看起来像模型不会用工具 |
| **写工具两段式 + `uuid5` 确认令牌** | 令牌绑定"谁 + 要做什么"、可重复确认而不重复建单；真正的安全边界仍是"确认之后走的还是同一个用例、还是确认者的身份" |
| **Agent 轨迹并进 `support_details`（不加新列）** | 轨迹是诊断信息、查询方式未定，为一个用途未定的东西加一列（还要一条迁移）不划算；用 `kind="agent"` 显式区分，不靠位置 |
