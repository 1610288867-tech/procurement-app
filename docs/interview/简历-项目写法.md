# 一、先想清楚：这个项目在简历上属于哪一类

## 它是什么

| 维度 | 事实 |
| --- | --- |
| 客户 | **没有真实客户**（个人项目） |
| 用户量 | **0**（没上线） |
| 盈利点 | **无** |
| 代码量 | 后端 1.7 万行 / 85 文件；前端 8.9 千行；测试 1.03 万行；脚本 5.1 千行；文档 1.06 万行 |
| 数据模型 | **26 张表 / 19 个迁移 / 66 条 HTTP 路由** |
| 验证强度 | **635 条后端用例**（纯函数档约 1 秒 + 集成档约 3 分钟）**+ 94 项真实浏览器实测**，14 步回归入口一条命令跑完 |
| 真实踩坑 | 五个"不会报错只会算错"的设计缺陷，每个都有复盘记录 |

## 所以它该怎么定位

> ❌ **不能**按阿里云那篇里的"公司业务系统"模板写（"支撑 1500 万人口数据"那种）——
> 那种写法靠**规模和用户量**建立可信度，而本项目这两项都是 0，**一追问就崩**。
>
> ✅ **应该**按"**一个人从零设计并完成的高严谨度后端系统**"写，
> 可信度来自**可复核的工程数字**和**能讲清楚的取舍**：
> - 数字都是**你自己能跑出来**的（`pytest -m ""` → 635 passed）；
> - 取舍都是**有代价、有替代方案**的（工作流引擎 vs 自研规则引擎）；
> - **踩过的坑能讲出根因**（身份映射、CHECK 白名单、PowerShell 作用域）。
>
> **这套打法在个人项目上是最高效的**：面试官对个人项目的"业务真实性"预期本来就低，
> 但对"**你是不是真的自己写过、想过边界**"的检测一点都不会放松。
> 而后者正好是本项目的强项。

# 二、⚠️ 写之前必须决定的两件事

## ① 开发周期：实测只有 6 天，怎么处理

**事实**（`git log` 可查）：`2026-10-01` M0 第一提交 → `2026-10-06` M11/M10 收口，**共 6 天**。

阿里云那篇明确说：**"开发周期是面试官评估项目难度、稳定性的一个关键要素，一般建议半年以上"** ——
理由很实际：**6 天的项目，无论代码多少，都会让人怀疑深度**。

**两条路线，你自己选**（我不替你决定）：

| 路线 | 做法 | 优点 | 风险 |
| --- | --- | --- | --- |
| **A. 延长真实建设期（推荐）** | 把周期写成 **2026.09 ~ 至今**，并在简历投递前**继续真实推进**：补失败尝试留痕、退款/冲正、离职转办、压测与慢查询优化、报表模块 | 周期真实、内容更厚、**面试时不怕查 git** | 需要真的花时间做 |
| **B. 如实写短周期** | 写 `2026.10` 月内完成，并在"项目描述"里主动说"**这是一次集中攻坚**（约 6 天完成 11 个阶段）" | 完全诚实、**反而显得执行力强** | 会被追问"这么短是不是抄的"，需要用 544 条测试 + 26 张表证明 |

> **我的建议是 A，并且 A ≠ 撒谎** —— 它是"**继续把这个项目做下去，然后把真实周期写上**"。
> 而且 A 顺带解决了本项目的另一处硬伤：**功能再多一层，简历上的职责条目就有真东西可写**。
>
> ⚠️ **绝对不要**写"2024.03 ~ 至今"这种凭空拉长的周期：
> **git 提交时间、`package-lock` 的时间戳、依赖版本都会对得上**，
> 而且面试官很可能会让你**打开仓库看**

## ② 要不要明说"个人项目"

**要，而且主动说。** 理由：

- 阿里云那篇点名了"不知道是不是培训项目、毕设项目"是**减分信号** ——
  那你主动说清"这是个人项目"，就**把这个疑虑提前消掉了**；
- 更关键的是：**"个人项目"这四个字会重置面试官的预期** ——
  他不会再问"你们 QPS 多少、日活多少"，而会问"**你为什么这么设计**" ——
  **那正是你准备最充分的部分**（见 `面试.md`）。
- 反过来，如果你含糊其辞、让他自己发现"没有用户"，那才是真正的减分。

**写法**：在项目名后面用括号标注，例如
`企业采购审批系统（个人项目 · 独立完成）`

# 三、项目标题怎么写

阿里云那篇给的差例子是 `学生在线考试系统`、`吃得香在线点餐小程序`，
不好在：**业务简单、真实性欠缺、受众不清**（"点餐有美团饿了么，还需要你们开发？"）。
好例子是 `杭州公安局基础管控系统 4.0`、`浙江电信营业厅受理系统-BSS3.0` ——
**公司信息 + 业务描述**。

既然我没有公司，就要用**另外三个信号**补上：
**① 受众明确 ② 业务链完整 ③ 有制度依据**。

| | 写法 | 评价 |
| --- | --- | --- |
| ❌ | 采购管理系统 | 太泛，像课程作业，没有任何信号 |
| ❌ | 基于 FastAPI 的企业采购系统 | **把技术栈当标题是减分项**（面试官想看业务） |
| ❌ | 我的第一个全栈项目 | 主动示弱 |
| ✅ | **企业采购审批系统（个人项目 · 独立完成）** | 稳。信息量够、不吹 |
| ✅ | **企业采购审批与履约系统 —— 预算管控 · 动态多级审批 · 三单匹配**（个人项目） | 更好：**副标题直接给出三个技术亮点**，面试官一眼知道值得深挖 |
| ✅ | **企业采购内控平台：预算占用、动态审批链与三单匹配**（个人项目 · 后端独立完成） | 偏"内控"角度，适合投财务/企业服务方向的团队 |

**推荐用第 5 条**（带副标题那条）—— 它把三个可深挖点放进了标题，
面试官扫简历时就有话题可问。

# 四、五要素填空模板

阿里云那篇的要素是：**项目名称 / 开发周期 / 团队成员 / 核心业务 / 负责模块**。
个人项目按下面这样填：

```markdown
### 企业采购审批与履约系统 —— 预算管控 · 动态多级审批 · 三单匹配
个人项目 · 独立完成 · 2026.09 ~ 至今

技术栈：Python 3.12 / FastAPI / SQLAlchemy 2.0(async) / PostgreSQL 16(+pgvector) /
        React 18 + TypeScript / Docker；pytest + 无窗口浏览器端到端实测

核心业务：覆盖"预算占用 → 按金额生成多级审批链 → 询价定标 → 下单收货 →
          发票三单匹配 → 付款结转 → 归档"完整链路，按财政部《企业内部控制应用指引
          第 7 号》的口径落地分级授权、职责分离与可追溯要求。

个人职责：
1. …
2. …
```

**"个人职责"的黄金句型**（这是全篇最该记的一句）：

```
【模块名】：【用什么技术】解决【什么具体问题】，（【可核对的结果】）
```

- **模块名**在前（面试官按模块扫）；
- **技术必须挂在一个具体问题上**（不是"用了 Redis"，而是"用 Redis 解决高并发下的频繁写"）；
- **有结果就写数字**，没有就不写（**不要编**，见第十节）。

# 五、个人职责逐条改写（10 条，按需挑 4–6 条）

> 阿里云那篇说"一般写 **4 个左右**就好，不要太多也不要太细"。
> 下面是 10 条候选，**按"这个岗位看重什么"挑 4–6 条**。
> 每条都附**对应证据**（面试时能打开给他看）和**面试官会追问什么**。

### ① 分层架构与基础设施

> **架构与基础设施**：设计并落地"边界 / 用例 / 领域 / 基础设施"四层架构，
> **把 `domain/` 约束为不依赖任何框架的纯函数层**，并写成可执行的自查
> （回归入口第一步三条 `Select-String` 检查，要求零输出）。
> 领域规则测试因此**毫秒级**反馈（34 条用例 0.18 秒），而集成测试要 3 分钟。

- **证据**：`backend/app/domain/*.py` 17 个文件；三条自查命令。
- **会追问**：分层是不是过度设计？（答：是有一点，我会合并用例层与边界层 —— 见 `面试.md` Q7）

### ② 动态审批引擎（最值钱的一条）

> **动态审批引擎**：把"多少钱需要谁批"从代码搬到品类策略 JSON，
> 自研**受限规则 DSL**（11 个操作符、字段白名单、禁止 eval）替代工作流引擎，
> 解决"改审批规则要发版"的问题；并设计**保存时四层校验**
> （字段白名单 / 兜底步骤 / 阈值整数 / **用探测金额反推每一级是否可达**），
> 把"规则配错导致审批层级静默降低"从运行期问题提前到保存期拦截。

- **证据**：`domain/approval_engine.py`、`domain/rules.py`；《金额-审批链对照表》（500/5000/50000/200000 元 → 1/2/4/5 级）。
- **会追问**：为什么不用 Flowable/Camunda？（答：链是算出来的不是画出来的，见 `面试.md` Q8/Q16）
- **为什么这条放前面**：它是**可迁移**的能力（规则引擎、数据驱动），不只属于采购域。

### ③ 预算并发控制

> **预算并发管控**：用**数据库条件更新**（守卫条件写进 `UPDATE ... WHERE`）
> 替代"先查余额再扣减"，解决并发提交下的**超额占用**问题 ——
> 该缺陷不报错、账面正常，只表现为预算被超占；
> 配合 `UNIQUE(request_id, kind)` 流水唯一约束兜底重复记账，
> 并用 `asyncio.gather` 并发用例断言"**恰好一笔成功 + 失败方整体回滚**"。

- **证据**：`repositories/budget_repo.py`（20 处 `.returning()` 条件更新）；`test_api_budget.py` 并发用例。
- **会追问**：为什么不用悲观锁/Redis？（答：见 `面试.md` Q24、Q15）

### ④ 履约链与三单匹配

> **采购履约与结算**：实现订单 → 收货 → 发票 → 付款的端到端链路，
> 并用**条件更新抢付款权**保证重复付款不可能发生；
> 三单匹配以订单金额为基准、容差 `max(2%, 50 元)` 用**整数基点**实现（全程无浮点）；
> **付款时显式释放"预留与实付的差额"**，避免可用额度虚低且长期累积。

- **证据**：`coordinators/fulfillment.py`、`settlement.py`、`domain/settlement_policy.py`。
- **会追问**：为什么有差额？订单金额≠申请金额正常吗？（答：见 `面试.md` Q44）

### ⑤ 金额口径（写这条会显得"稳"）

> **金额一致性**：全链路以**整数「分」**存储与计算（数据库 `BIGINT` / Python `int`），
> 元⇄分转换收敛到**单一入口**，并把"禁止浮点金额列"写成回归入口的自查项；
> 引入 Alembic 管理 **16 个数据库迁移**。

- **会追问**：为什么不直接存 `Decimal`？（答见下："Decimal 也能，但我要求**跨语言一致**"）

### ⑥ 职责分离与数据级权限（内控向，投企业服务/金融尤其该写）

> **职责分离与数据级权限**：按内控要求实现"**提交人不得审批自己的申请**"，
> 落到建链剔除 / 待办过滤 / 决定接口 SQL 守卫**三层拦截**（缺一层就留越权口子）；
> 数据可见范围以 `RequestScope` 对象**强制写入 `WHERE`**（而非查后过滤），
> 并按"可见范围外 404、可见但无权 403"的口径避免资源枚举。

- **证据**：`domain/permissions.py`、`domain/approval_engine.exclude_requester`；相关 404/403 测试。
- **会追问**：为什么不是 403？（答：403 会泄露"这个 id 存在"，见 `面试.md` Q45）

### ⑦ 验证体系（**个人项目最该写的一条**）

> **测试与验证体系**：建立五层验证 —— 领域纯函数单测 / 集成测试（真 PostgreSQL）/
> 对真实服务打 HTTP 的冒烟 / 静默失败探针 / **无窗口 Edge 的端到端实测**，
> 累计 **635 条后端用例 + 94 项浏览器断言**，并收敛为一个
> **14 步回归入口（一条命令、退出码即结论）**；
> 其中主动构造用例去撞三类"**不会报错、只会算错**"的约束（空审批链 / 差额未释放 / 权限漏过滤）。

- **为什么这条在个人项目里分量最重**：**它是"我真的在乎正确性"的唯一硬证据** ——
  没有用户量可吹时，**验证强度就是可信度的替代品**。
- **会追问**：覆盖率多少？（**答"没接 pytest-cov，所以不知道"** —— 见第十节）

### ⑧ 静默失败排查（体现调试能力，适合放"技术难点"里）

> **疑难问题定位**：定位并修复五个"**不报错、只算错**"的缺陷，例如
> ORM 身份映射导致批量更新后响应返回旧值（同一类问题在五个模块复现）、
> 幂等键校验被推迟到无关 SQL 上导致错误码从 409 退化为 503、
> 以及**回归入口本身因 PowerShell 作用域问题把失败判成通过**（修复后补入
> "验证工具自身必须能被验证"的断言）。

- **会追问**：怎么定位的？（答：`面试.md` Q26/Q75/Q70）

### ⑨ AI 制度助手（投 AI 应用岗放前面）

> **AI 制度助手（RAG）**：实现"制度文档上传 → 切分 → 向量检索 → 引用校验 → SSE 流式回答"，
> 用 pgvector + HNSW 做向量检索，**真语义 embedding 模型**（bge 中文检索模型，512 维；
> 另有哈希实现作为离线退路，两者通过端口隔离、按模型名过滤向量，绝不混用）；
> 把"**问不到就不回答**"做成**阈值判定 + 提示词约束 + 事后两层引用校验**四道闸门
> （第一层查引用编号是否真实存在，第二层查**被引片段是否真的支撑那句话** —— 数字、否定、错位）；
> 支持制度**版本与生效时间**，检索只取当前生效版本，避免新旧条文混引。
>
> **有可回归的评测体系**：27 条 Golden QA（事实/条件/跨版本/口语化/无答案五类），
> 分层出指标（检索层 Recall@K / MRR / NDCG@K；生成层引用完整性 + 支撑率 +
> **实际回答成功率**），并作为**硬门槛接进回归入口**。
> 换 embedding 前后有量化对比：MRR 0.879 → **0.932**、"能答却被拒答" 3 条 → **0 条**、
> 实际回答成功率 0.864 → **1.000**；`min_score` 阈值是按**实测分数分布**标定的（0.50），
> 不是拍的 —— 这一步量化验证了"**阈值必须与 embedding 配套**"。

- **证据**：`domain/grounded_answer.py`、`domain/chunking.py`、`domain/embedding.py`、
  `domain/citation_support.py`、`domain/retrieval_metrics.py`；`scripts/knowledge_eval.py`、
  `scripts/eval/knowledge_eval_cases.json`；`docs/AI-评测baseline.md`。
- **会追问**：embedding 是自己写的吗？（**答**：不是 —— 用 Ollama 跑 bge 中文检索模型；
  **项目里另有一个 256/512 维哈希实现，它是"没有模型时也能跑通链路"的离线退路**，
  默认配置用的是真模型。哈希的局限我量化过：对口语化问法只有 0.025 的相似度，

# 十、数字使用指南：能用 / 不能用

## ✅ 可以直接写（都是你能当场跑出来的）

| 数字 | 精确口径 | 怎么复核 |
| --- | --- | --- |
| **635 条后端用例** | `pytest -m ""` 的用例数（含 unit + integration） | 跑一次即得 |
| **94 项浏览器断言** | 四个脚本的 `check()` 条数之和：17 + 51 + 6 + 20 | 每个脚本跑完打印 `N/M 项通过` |

| **85 个源文件 / 1.7 万行** | `backend/app` 下 `.py` 的文件数与行数 | `Get-ChildItem` 统计 |

| **20 处条件更新** | 仓库层 `.returning(...)` 的出现次数 | `grep` |
| **26 个文件 43 处 `populate_existing`** | 身份映射问题的修复点 | `grep` |
| **四档金额 → 1/2/4/5 级审批** | 参数化测试的输入与断言 | 跑测试 |

**这些数字的共同特点**：**它们是"工程事实"，不是"业务成绩"** ——
面试官没法质疑"635 条？那覆盖率多少"，而只能问"你为什么这么测"，

## ❌ 绝对不能写（没有真凭实据）

| 不能写 | 为什么 | 被追问时的下场 |
| --- | --- | --- |
| ~~日活 X 用户 / 支撑 X 万数据~~ | 没上线、没用户 | 要你给截图/链接，当场崩 |

| ~~节省成本 X 万~~ | 编的 | 崩 |
| ~~服务 X 家企业~~ | 编的 | 崩 |
| ~~精通 / 深入理解~~（放技能栏） | 主观且是靶子 | 会被往死里问 |

> ⚠️ **上表里"RAG 准确率"这一条的处境变了（2026-10-14）**：
> 之前不能写是因为**没有评测基准集**；现在有了 27 条 Golden QA + 分层指标 + 硬门槛。

> | --- | --- |
> | 检索排序 MRR 0.879 → 0.93~0.96、NDCG 0.910 → 0.95~0.97 | 27 条 Golden QA 两次运行对比 |

> **想写"效果"但没有数据时，改写"设计"与"代价"。**
