# 金额 → 审批链对照表

> M0 产物之一。这张表是**需求文档 + 测试用例 + 验收标准**三合一。
> 实施计划 M0 第 6 步说得很直白：**现在花 20 分钟写清楚，M5 能省两天。**

## 一、四笔基准申请

| 金额 | 申请人 | 部门 | 应走的审批级 | 审批任务数 |
| --- | --- | --- | --- | --- |
| **500 元** | 张三 | 行政部 | 部门主管 | **1** |
| **5,000 元** | 张三 | 行政部 | 部门主管 → 部门负责人 | **2** |
| **50,000 元** | 张三 | 行政部 | 部门主管 → 部门负责人 → 采购 → 财务 | **4** |
| **200,000 元** | 张三 | 行政部 | 部门主管 → 部门负责人 → 采购 → 财务 → 总经理 | **5** |

**这四行就是 M5 的验收基准**（实施计划第六节和 M5 验收项都用它）。
对应 `tests/test_approval_engine.py` 里的参数化测试。

## 二、金额门槛（阈值一律写"分"）

| 审批级 | 角色 | 触发条件（分） | 折合元 |
| --- | --- | --- | --- |
| 1 | `DEPT_MANAGER` | `amount_fen >= 0` | 0（兜底，任何金额都要走） |
| 2 | `DEPT_HEAD` | `amount_fen >= 100_00` | **100 元** |
| 3 | `PROCUREMENT` | `amount_fen >= 500_000` | **5,000 元** |
| 4 | `FINANCE` | `amount_fen >= 500_000` | **5,000 元** |
| 5 | `GM` | `amount_fen >= 20_000_000` | **200,000 元** |

### ⚠️ 与领域设计文档的一处刻意偏离

领域设计 6.4 节给的阈值是 `DEPT_HEAD ≥ 1,000 元`、`PROCUREMENT/FINANCE ≥ 10,000 元`。
**那两个数字与本文档第一张表对不上**：

| | 会导致的矛盾 |
| --- | --- |
| `DEPT_HEAD ≥ 1,000` | 500 元的申请会**多出**一级部门负责人，任务数变 2，而不是 1 |
| `PROCUREMENT/FINANCE ≥ 10,000` | 50,000 元的申请只有 3 级，而不是 4 级 |

**本表以"1 / 2 / 4 / 5"为准**（这是 memory.json、实施计划第四节和第六节共同确认的验收基准），
所以阈值按上表取值。领域设计那两行是早稿，写代码时以本表为准。

> 顺带说明为什么这不算"改需求"：**阈值本来就该是数据，不是代码**。
> 这张表的真正意义不是"记下四个数"，而是**证明审批链是数据驱动的**——
> M5 验收里那条"改品类策略（不改代码）审批链跟着变"测的就是这件事。

## 三、每级在审什么（为什么是这几级）

| 级 | 角色 | 关切的业务问题 |
| --- | --- | --- |
| 1 | 部门主管 | 这个需求真实吗？现在必须要买吗？ |
| 2 | 部门负责人 | 金额是否在部门承受范围内？优先级对不对？ |
| 3 | 采购专员 | 能不能并单？有没有合格供应商？要不要走比价？ |
| 4 | 财务 | 预算够不够？科目对不对？付款节奏怎么安排？ |
| 5 | 总经理 | 金额重大，需要经营层决策 |

**每一级都对应一个真实的业务关切**，不是为了凑层级。写 M5 的时候如果发现某一级"不知道它在审什么"，那说明这条规则该删。

## 四、对应到策略 JSON（M2 存进 `purchase_categories.approval_policy`）

```json
{
  "steps": [
    { "order": 10, "role": "DEPT_MANAGER", "mode": "SINGLE", "when": { "gte": ["amount_fen", 0] } },
    { "order": 20, "role": "DEPT_HEAD",    "mode": "SINGLE", "when": { "gte": ["amount_fen", 10000] } },
    { "order": 30, "role": "PROCUREMENT",  "mode": "SINGLE", "when": { "gte": ["amount_fen", 500000] } },
    { "order": 40, "role": "FINANCE",      "mode": "SINGLE", "when": { "gte": ["amount_fen", 500000] } },
    { "order": 50, "role": "GM",           "mode": "SINGLE", "when": { "gte": ["amount_fen", 20000000] } }
  ],
  "skip_when_framework_contract": true,
  "urgency_extra_step": { "role": "DEPT_HEAD", "when": { "eq": ["urgency", "URGENT"] } }
}
```

**三条必须遵守的书写规矩**（M2 的语义校验会强制检查这三条）：

1. **路径名是 `amount_fen`，不是 `amount`**。写成 `amount` 不会有任何报错——
   `rules.py` 对"缺字段"的语义是**返回 False（不满足）**，于是整条规则**静默失效**，
   申请会以**更低的审批层级被批准**。这是审批系统里最严重的失败模式。
2. **阈值是整数"分"**，禁止浮点。`100_00` = 100 元，`20_000_000` = 20 万元。
3. **必须有一条零阈值兜底步骤**（`amount_fen >= 0`）。少了它，某些金额区间会算出**空审批链
   = 无人审批直接通过**。

## 五、会签（`ALL`）模式怎么算任务数

上表四笔申请用的都是 `SINGLE`（或签）——**同一角色下无论几个人，只生成 1 条任务**。

如果改成 `ALL`（会签），任务数会变：

| 场景 | `SINGLE` | `ALL`（假设该角色有 3 人） |
| --- | --- | --- |
| 5,000 元申请 | 2 条 | 5 条（主管 1 + 负责人 3 + …） |

**验收时要分别测两种模式**：
- `SINGLE`：只生成 1 条任务，该角色的人都能在待办里看到，**任一人认领并通过**即完成该级
- `ALL`：生成 N 条任务，**建任务时就预分配** `assignee_id`（会签不能抢单），**全部通过**才算完成

## 六、异常情形（M5 必须处理）

| 情形 | 期望行为 |
| --- | --- |
| 某级解析出 **0 个审批人** | 提交时直接 **422**，并说明是哪一级缺人——**不允许生成"没人能审"的任务**（否则单据永久卡死且无人知情） |
| 同一角色被策略写了两次 | `resolve_approval_chain` **去重**，只保留 `order` 靠前的那个 |
| 某步骤在任何金额下都不被触发 | 保存策略时 **422**（`check_reachability`） |
| 申请金额为 0 或负数 | 提交时 422（业务上不存在 0 元采购） |

## 七、这张表怎么用

| 阶段 | 怎么用 |
| --- | --- |
| M2 | 把第四节那段 JSON 存进一个测试品类，验证语义校验通过 |
