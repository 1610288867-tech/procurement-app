# 权限矩阵（M3 起，2026-10-03 收口）

> **用途**：判断"这个角色能不能用这个接口""能看到哪些行"时读这一份。
> 它是**权限口径的唯一权威**；[README.md](../../README.md) 只留摘要与链接。
>
> 相关：[业务规则.md](../业务规则.md)（第 9 条职责分离）、[采购内控对照.md](../采购内控对照.md)（外部依据）
>
> 最后核实：2026-10-14

## 一、两套权限是**分开**的，缺一不可

| 问题 | 由谁回答 | 代码位置 | 越界的表现 |
| --- | --- | --- | --- |
| **能不能用这个接口** | 角色依赖 | `boundaries/deps.py` 的 `require_roles(...)` | **401**（没登录）/ **403**（角色不够） |
| **能看到哪些行** | 数据级可见范围 | `domain/permissions.py` 算出的范围，**写进 `WHERE`** | **404**（查不到） |

**为什么必须两套**：只挡"谁来敲门"不够 —— 数据级漏掉**不会报错**，
只会安静地把别人的数据查出来。所以它必须做成**能直接塞进 `WHERE` 的条件函数**，
而不是"先查出来再判断能不能看"。

**判据的唯一落点**是 `domain/permissions.resolve_request_scope`：
申请列表、待办、审批决定三处**同源**（抄一份就会漂移，而漂移出来的越权最难发现）。

## 二、角色可见范围

| 角色 | 可见范围 | 典型用途 |
| --- | --- | --- |
| `REQUESTER` | 只看**自己提的**申请 | 我的申请、进度、驳回原因 |
| `DEPT_MANAGER` / `DEPT_HEAD` | **本部门（含子部门）** | 待我审批、部门预算 |
| `PROCUREMENT` / `FINANCE` / `RECEIVER` / `GM` | **跨部门看全公司**（职责要求） | 询价、付款、收货、大额审批 |
| `ADMIN` | 全部（含配置） | 品类与审批规则、供应商准入、账号 |

> ⚠️ **部门级角色的"建"与"办"必须用同一套判据**。
> 这里曾经出过一个**真实越权面**：建链时按部门挑人，**办事时只校验角色名** ——
> 于是财务部的部门负责人能批掉行政部那张单子的「部门负责人」那一级。
> 它平时不现形，只因为开发库里恰好没有"另一个部门停在同一级"的单子
> （**可见性依赖数据巧合**，而不是依赖任何一道防线）。
> 现已修：`list_todo` 与 `_assert_can_act` 都补上部门范围。
> **会签（`MODE_ALL`）那一支刻意不加** —— 候选人本来就是建链时按部门挑的，
> 再卡一次只会制造"被指派了却批不了"的死结。

## 三、接口级权限（2026-10-03 收口后的实际状态）

| 接口组 | 谁能用 |
| --- | --- |
| `GET /health/*` | 任何人（公开，排查用） |
| `POST /api/v1/auth/login` | 任何人 |
| `GET /api/v1/suppliers`、`/departments`、`/categories`、`/categories/{id}`、`/budgets/mine` | **登录用户**（只读；`/budgets/mine` 的部门**只从登录态推导**，没有部门的账号返回空列表） |
| `POST /api/v1/auth/refresh`、`/logout`、`GET /me` | 登录用户 |
| `/api/v1/requests/*`、`/api/v1/approvals/*` | 登录用户（**创建与提交申请还要求账号有部门**；具体行是否可见由数据级权限决定：范围外 404、可见但无权 403） |
| `/api/v1/budgets`、`/api/v1/budgets/transactions` | **`FINANCE` 或 `ADMIN`**（**只读**看板；改预算走 `/admin/budgets`，仅 `ADMIN`） |
| `/api/v1/admin/*` | 仅 `ADMIN` |
| `/api/v1/chat/*`（含 `/confirm-draft`） | 登录用户（会话**只列自己的**；确认创建用**确认者自己的身份**执行） |

**三个刻意的取舍**：

1. **主数据接口也要求登录**（2026-10-03 改动）：它们原来匿名可读，
   其中 `/api/v1/categories/{id}` 还会把**整份审批策略**（金额阈值 + 各级角色）带出来。
   `only_active` 这类"要不要过滤"的开关也从客户端参数里**收掉了** ——
   过滤条件写死，要看全部走 `/api/v1/admin/*`。
2. **看钱与改钱分开**：`GET /api/v1/budgets` 给 `FINANCE` + `ADMIN`（只读），
   `POST /api/v1/admin/budgets` 只给 `ADMIN`。把 `/admin/budgets` 放宽成"财务也能看"
   就等于把改钱也一起放开了。
3. **菜单/按钮权限由前端自判**（`App.tsx` 用 `me.roles.includes(...)`）：
   **后端始终是最终边界**，前端只是体验优化。角色复杂度明显上升时再改成一处常量。

## 四、演示账号（`scripts/seed.ps1` 生成）

**8 个角色 / 7 个人**，`GM` 由 `ADMIN` 兼任：

| 用户名 | 角色 | 部门 |
| --- | --- | --- |
| `admin` | `ADMIN` + `GM` | —（**没有部门，所以看不到「我的申请」**） |
| `requester` | `REQUESTER` | 行政部 |
| `dept-manager` | `DEPT_MANAGER` | 行政部 |
| `dept-head` | `DEPT_HEAD` | 行政部 |
| `procurement` | `PROCUREMENT` | 采购部 |
| `finance` | `FINANCE` | 财务部 |
| `receiver` | `RECEIVER` | 行政部 |

口令统一 `Dev-Passw0rd!`。**仅本地合成数据**，换任何真实环境都必须改掉。

> ⚠️ **"有没有部门"是一个独立的判据**（不是"是不是管理员"）：
> 部门决定预算归属与审批链，没有它连草稿都建不出来（后端 `NO_DEPARTMENT`）。
> 而**审批入口所有人都有**（含 `admin`）—— 审批与部门无关，GM 要审大额单。

## 五、认证机制（双令牌）

| 项 | 取值 | 为什么 |
| --- | --- | --- |
| access token | 15 分钟 | 短寿命，泄露面小 |
| refresh token | 7 天，`Path` **限定到** `/api/v1/auth/refresh` | 它就再也不会出现在别的请求里，泄露面当场变小（代价只是 `set_cookie` 一行参数） |
| 存放方式 | **httpOnly Cookie** | JS 读不到令牌，XSS 能拿走的东西少一半 |
| 冻结账号 | `token_version += 1` → **旧令牌立即失效** | 一个整数字段替掉黑名单表 + refresh rotation 两套机制 |
| 登录失败 | 连错 5 次 → **429**，窗口过后恢复 | 限流在**进程内存**里（单进程够用；多实例要换共享存储） |
| 登录失败的响应 | **必须一模一样** | 区分"用户不存在"与"密码错误"等于免费提供账号枚举接口 |

前端拿到 **401 时会自动续期一次并重放请求**（并发的多个 401 只续一次），
所以令牌过期不会把正在用的人踢回登录页。

## 六、与授权失败留痕的关系（**尚未落地**）

[业务规则.md](../业务规则.md) 第 10 条要求"**授权失败要留痕**"（越权、越级、无权操作记安全审计事件）。
现状：**只有 403 状态码，没有审计记录**。这是一条**真债**，见 [RISKS.md](../../RISKS.md) 第一节第 3 项。
落地时要新增**独立**的审计事件表，**不要混进 `request_events`**（那是申请人看的时间线）。
