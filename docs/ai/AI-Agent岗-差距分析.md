## 一、4 个必修项（按"性价比"排序）

### ✅ 已完成（2026-10-14）· 必修 1：把"引用溯源"从**格式校验**升级为**支撑性校验**（实际 0.5 天）

**你现在的实现有一个必须知道的弱点。**

`check_citation_integrity(answer, sources)` 目前只校验三件事：
① 引用的编号是否存在；② 有实质内容却零引用；③ 检索到来源却完全不用。

**它校验的是"引用的编号真不真"，但没校验"引用的内容撑不撑得住这句话"。**

举个必然发生的例子：

```
来源 [1]：《采购管理办法》第十二条 —— "采购金额超过 10 万元的，应当公开招标。"
模型回答："根据[1]，采购金额超过 50 万元的应当公开招标。"   ← 编号是真的、内容是错的
```

你的校验会**放行**它。而这**正是 JD 里"引用溯源"要防的事**，也是 RAG 评测里的
**Faithfulness（忠实度）** 指标要量化的事（见 [RAG 评测体系](https://developer.aliyun.com/article/1759127)）。

**补法（不用引大模型）**：

1. **纯函数层加"关键事实比对"**：从回答里抽出**金额、期限、比例、否定词**这类硬事实，
   逐个检查是否能在被引用的片段里找到（允许"十万元/100000 元/10 万元"这类归一化）；
   对不上的报 `CITATION_UNSUPPORTED_FACT`；
2. **加一条"编号—句子"对齐**：现在 `[n]` 只要出现在回答任意位置就算数；
   改成**要求它出现在它支撑的那句话附近**（同一句或前一句），否则报 `CITATION_MISPLACED`；
3. **把两类问题分别落库**（现在是同一个 `citation_problems` 字段），
   这样统计时能区分"编号造假"和"内容不支撑"——后者更隐蔽、更危险。

> **为什么这一条性价比最高**：它**直接命中 JD 的"引用溯源"**，
> 而且它把你的诚实边界（"我只校验了编号"）**变成一个已解决的问题**。
> 面试时这是一个标准的"我发现我的方案有个盲区，于是我补了 X"的加分故事。

### ✅ 已完成（2026-10-14）· 必修 2：建一个评测集 + 指标计算（实际 1 天）

**这是你最大的空白，也是这份 JD 第 5 条的全部内容。**

你的项目当时**完全没有评测**（→ 2026-10-14 已补上，见文首进度更新）：
- 没有 Golden Dataset（我甚至在 `面试.md` Q61 里承认过："我没有评测基准集"）；
- 没有 Recall / MRR / NDCG；
- 没有 Faithfulness / Correctness / Relevance；
- 没有延迟与 token 成本统计。

而 [那篇 RAG 评测体系](https://developer.aliyun.com/article/1759127) 的第一句话就是：
**"RAG 进入企业生产后，最大的挑战不是模型能力，而是缺乏量化评测体系。"**
一个 AI 实习岗问"你怎么知道你的 RAG 效果好不好"，**当时的答案是"我没有评测手段"** —— 这是会在面试里直接失分的。**现在有答案了**：27 条 Golden QA + 分层指标 + 硬门槛，以及换 embedding 前后的实测对比。

**补法（这是你最能发挥优势的地方，因为你有 544 条测试的功底）**：

1. **造 20–30 组 Golden QA**（不用多，但要**覆盖类型**）：
   事实查询 / 条件查询 / **无答案问题** / **版本问题**（新旧制度）/
   多跳问题 / 模糊口语化问题。
   数据来源就是你现有的制度文档 —— **每组标"期望命中的 chunk_id"和"标准答案"**；
2. **实现检索指标**（纯函数，几十行，正好符合你"领域层纯函数"的习惯）：
   `recall_at_k` / `reciprocal_rank` / `mrr` / `precision_at_k` / `ndcg_at_k`。
   **用你的哈希 embedding 先跑一遍** —— 分数会很难看，**但那正是重点**：
   它给了你一个 baseline，而且能证明"哈希 embedding 只验证链路、不评估效果"这个判断；
3. **实现生成指标**：Faithfulness / Correctness / Relevance / Completeness。
   先用**规则法**（关键事实覆盖率）跑，再可选地接 **LLM-as-a-Judge**（要结构化 JSON 输出）；
4. **把评测接进你已有的回归入口**：加一步 `评测集回归`，
   **并设 Hard Gate**（比如 Recall@5 < 0.7 或 Faithfulness < 0.9 就失败）。
   这一步会让面试官眼睛一亮 —— 因为"**评测进 CI**"正是那篇文章强调的成熟度标志；
5. **分桶报告**：按"问题类型"和"文档版本"分组出指标（不要只看平均值）。

> **配套要改的简历措辞**：现在不能写"效果良好"，要写
> "建立 Golden Dataset（N 组，含无答案与跨版本问题）与检索/生成两层指标
> （Recall@K / MRR / Faithfulness），并接入回归入口做质量门禁"。
> **这条会比"我做了 RAG"有说服力得多** —— 因为它证明你知道**怎么证明效果**。

### ★ 必修 3（**仍未做，下一步第一件事**）：Function Calling 与工具调用（3–4 天，**这是"Agent 岗"的门槛**）

JD 第 1、3 条直接点名：**Function Calling、工作流编排、工具调用、任务规划、MCP**。
你现在**一项都没有** —— 这是 RAG 助手和 Agent 的**分界线**。

**但你的项目有一个别人没有的起点：你有一个权限严密、状态机完整的业务系统让 Agent 去调。**
这是巨大的差异化优势 —— 大多数人的 Agent demo 是调天气 API，
而你可以做"**让 Agent 在权限边界内、幂等地操作真实的采购单据**"。

**补法（先做最小闭环，别一上来做框架）**：

1. **定义 3–5 个工具，用 JSON Schema 描述**（这正是 Function Calling 的核心）：
   ```json
   { "name": "query_request_status",
     "description": "查询采购申请的状态与当前审批级",
     "parameters": { "type": "object",
       "properties": { "request_id": {"type": "string"} },
       "required": ["request_id"] } }
   ```
   候选工具（都要**只读**起步）：查申请状态 / 查我的待办 / **查制度（复用现有 RAG 检索）** /
   查预算余额 / 查三单匹配结果；
2. **实现一个最小 ReAct 循环**：调模型 → 解析 `tool_calls` → 执行工具 → 把结果回灌 →
   再调模型 → 直到给出最终回答。**循环要有最大步数与超时**（否则会死循环烧 token）；
3. **写出"哪一步该用工具、哪一步不该"的判据**（这是面试官爱问的）：
   - 制度问题 → 必须先检索（不许凭先验答）；
   - 单据状态 → 必须走工具（数据库是唯一真相）；
   - 涉及**写操作**（提交/审批/付款）→ **第一版一律不做**，只回答
     "这需要你在系统里操作，步骤如下……"；
4. **加权限与幂等约束**（**这是你最值钱的部分，务必讲出来**）：
   - 工具执行时**沿用已有的 `RequestScope`** —— Agent 与用户看到同一套可见范围，
     **不给 Agent 任何额外权限**；
   - 写工具若要做，必须**复用已有的幂等键机制**，因为 LLM 会重复调用同一工具；
   - **工具调用必须留痕**（谁、什么参数、什么时候）—— 这是审计要求，你已有事件流可挂靠；
5. **可选加分：把工具暴露成 MCP server**（1 天）。
   MCP 就是"把工具/资源用统一协议暴露给模型"，你已有的 FastAPI 路由**几乎可以直接映射**。
   面试时能说出"我理解 MCP 解决的是**工具集成的标准化**问题（M×N → M+N）"就够了。

> ⚠️ **一个必须防的坑**：Agent 动了钱和单据就是**事故**。
> 你的项目里已有"条件更新防并发"和"幂等键防重放"，
> **这两条正好是 Agent 工具调用最缺的东西** —— 把这个联系讲出来，是这份 JD 最亮的一击。

### ★ 必修 4（**仍未做**）：Prompt 工程与结构化输出（1–2 天）

JD 第 1 条点名 "Prompt 设计"。你现在只有一个写在 `grounded_answer.py` 里的
**四句话 system prompt**，没有版本、没有对比实验、没有结构化输出。

**补法（工作量小，但面试必问）**：

1. **把 prompt 抽成带版本的模板**（比如 `SYSTEM_PROMPT_V1/V2`），
   并在消息表里**记录这条回答用了哪一版** —— 这样"A/B 两版哪个好"才有数据；
2. **做一次真实的 A/B**：用必修 2 的评测集跑两版 prompt，给出指标差异
   （"V2 强制要求引用编号后，Faithfulness 从 X 提到 Y"）；
3. **结构化输出**：让模型返回 JSON（`{"answer": "...", "citations": [1,3]}`），
   用 Pydantic 校验，**校验失败要有重试或降级**；
   这一步同时解决了"引用校验靠正则"的脆弱性；
4. **把 `temperature`、`max_tokens`、超时、重试写成显式配置**（现在只有一个 `temperature=0.2`）。

## 二、2 个加分项（有余力再做）

### 加分 1：检索重排 + 混合检索（2–3 天）

JD 第 2 条明确写了"**检索重排**"。你现在是单路 top-k。

- **先做评测（必修 2），再做优化** —— 这个顺序本身就是加分项
  （"我先建了 baseline，才知道混合检索有没有用"）；
- 实现 **BM25（Postgres `tsvector`）+ 向量 + RRF 融合**，用同一套评测集对比；
- **重排**可以先做**规则重排**（同文档相邻 chunk 聚合、按生效时间加权），
  再考虑接一个 rerank 模型。

### 加分 2：Docker 化 + 限流 + 可观测（2 天）

JD 第 6 条：Docker、云服务、日志、限流、缓存。你现在只有 compose（只跑了数据库）。

- **后端也进 Docker**（多阶段构建）+ 一条 `docker compose up` 起全栈；
- **限流**：登录接口（防撞库）+ **问答接口**（防刷 token）；
  这个必须自己做 —— LLM 接口被刷直接变账单；
- **可观测**：结构化日志（你已有 `request_id` 串联）+ 记录每次问答的
  `检索耗时 / 模型耗时 / token 数 / 估算成本`；
  **token 成本是这份 JD 第 5 条明确点名的**（"延迟、成本、稳定性"）。

## 五、一句话总答（回答你最初的问题）

> **"能否满足？"—— 写这份分析时约 35–40%；到 2026-10-14 约 **65–70%**。
> 补上的恰好是 JD 权重最高的那两项：**评测与优化**（5% → 80%）
> 与 **Function Calling**（0% → 75%），另有真语义 embedding、
> 引用支撑性校验、可观测与限流。**
>
> **剩下的缺口**：Prompt 版本化与 A/B（35%）、任务规划与记忆（35%）、
> 重排与混合检索（0%）、Docker 全栈化。
> 其中**「任务规划」是 Agent 与"会调工具"之间最后那一段** ——
> 现在它是"逐步反应"（走一步看一步），不是"先订计划再执行"。
>
> **好消息是：剩下的每一项都是"加法"而不是"重做"**，
> 而且你已有的三块东西（权限/事务约束、幂等与条件更新、五层验证体系）
> 在 Agent 接上之后**立刻变成了差异化的能力** ——
> 工具复用 `RequestScope` 的权限（不额外提权）、
> 写工具走"两段式 + 幂等键"（LLM 会重复调用，重复付款是真实事故）。
> **这两点是绝大多数 Agent demo 没有的，也是它们最容易出事的地方。**
