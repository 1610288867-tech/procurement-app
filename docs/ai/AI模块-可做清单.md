# 让 AI 模块够上「AI Agent 实习」岗：可做清单

> **这份文档回答一个问题**：JD 里那么多要求，**哪些是我真能做的**？
>
> **判断依据（先说清前提）**：
> - 硬件实测：**RTX 4070 Laptop 8GB 显存** / i7-14700HX（20 核 28 线程）/ 15.8 GB 内存 / D 盘剩 266 GB
> - 无任何大模型 API key，**但本地能跑 7B 模型**（见第零节）
> - 一个人、业余时间做；目标不是"做完所有事"，而是"**让简历和面试经得起追问**"
>
> **三条结论先行**：
> 1. **JD 第 5 条（评测）必须做** —— 它是唯一"不做就在面试里直接答不出"的一项，而且**它不需要模型**；
> 2. **装 Ollama 是性价比最高的一步**（约 1 小时）—— 它一次性解锁"真模型 + Function Calling + 真实评测数字"三件事；
> 3. **不要做的有 3 项**（第 5 节），做了既费时间又不加分。

---

## 零、先做这一步：装 Ollama（约 1 小时，解锁后面一半的活）

**你的显卡能本地跑 7B 模型**（8GB 显存跑 4-bit 量化的 7B 大约占 4–5 GB，
剩下给 KV cache 够用，预计 **40–60 tokens/s**，对评测和 Agent 循环完全够）。

**为什么这一步优先级最高**：

| 解锁了什么 | 说明 |
| --- | --- |
| **真模型**（不再是"没真跑过"） | 你的 `OpenAiCompatibleChat` **本来就是按 OpenAI 兼容协议写的** —— Ollama 也提供 `/v1/chat/completions`，**只需把 `base_url` 指到 `http://localhost:11434/v1`**，代码一行不用改 |
| **真 Function Calling** | Qwen2.5 7B 支持工具调用（Ollama 支持 `tools` 参数），Agent 循环才有意义 |
| **真 embedding**（可选，很值） | 拉一个 `bge-m3` 或 `nomic-embed-text`，**语义检索立刻可用**，能直接对比你那套哈希 embedding |
| **零成本** | 评测集跑几百次也不花钱 —— 这对"要反复调参"的评测工作**是决定性的** |

**具体动作**：
```powershell
# 1. 装 Ollama（官网下载 Windows 版，或用 winget）
winget install Ollama.Ollama

# 2. 拉模型（7B 对话模型 + 一个 embedding 模型）
ollama pull qwen2.5:7b
ollama pull bge-m3              # 中文语义检索效果好

# 3. 验证 OpenAI 兼容层可用
curl http://localhost:11434/v1/models
```

**接入你的项目**（改 `.env` 或 `config.py`，**不用改代码** —— 这正是当初按"OpenAI 兼容"写的好处）：
```env
KNOWLEDGE_LLM_BASE_URL=http://localhost:11434/v1
KNOWLEDGE_LLM_API_KEY=ollama      # Ollama 不校验，随便填
KNOWLEDGE_LLM_MODEL=qwen2.5:7b
```

> ⚠️ **一句话要写进真债清单**：本地 7B ≠ 生产模型。
> 面试时主动说："我用本地 7B 完成了真实链路与评测的验证；
> 换更大模型只需改 `base_url` 与模型名，评测集会立刻给出差异。"

## 一、能做的清单（按"先做哪个"排序）

### 🥇 第 1 件：评测集 + 指标 + 接进回归入口（3–5 天）

**不需要模型，纯规则法就能做出真实数字。** 这是 JD 第 5 条的全部内容。

| 做什么 | 怎么做（贴着现有代码） |
| --- | --- |
| **Golden QA 20–30 组** | 吃你现成的制度文档。**必须覆盖 4 类**：事实查询 / **无答案问题**（制度里没有的）/ **跨版本问题**（新旧制度）/ 口语化模糊问题。每组标 `期望命中的 chunk_id` + `标准答案` |
| **检索指标**（纯函数） | `recall_at_k` / `reciprocal_rank` / `mrr` / `precision_at_k` / `ndcg_at_k` —— 放 `domain/`，几十行，正好符合你的纯函数习惯 |
| **生成指标**（先规则法） | `Faithfulness`：把回答拆成"原子事实"（金额/期限/比例/否定词），逐个检查能否在被引用的片段里找到 —— **这一步和下面第 2 件是同一份代码** |
| **接进回归入口** | 在 `回归验收.ps1` 加一步"评测集回归"，**设 Hard Gate**（如 `Recall@5 < 0.7` 或 `Faithfulness < 0.9` 就失败）—— 这是"评测进 CI"，**成熟度的标志** |
| **分桶报告** | 按"问题类型 / 文档版本"分组出指标（**不要只看平均值** —— 平均值会掩盖"某一类特别差"） |

**产出（可直接写简历/面试讲）**：
> "建立 28 组 Golden QA（含无答案与跨版本问题），实现检索层（Recall@5 / MRR）
> 与生成层（Faithfulness 事实支撑率）指标，并接入回归入口做质量门禁。"

**为什么它排第一**：
- **它是后面所有优化的前提** —— 没有 baseline，"混合检索更好""prompt V2 更好"全是感觉；
- 你有 **544 条测试的功底**，这件事对你来说是把已有能力换个场景用；
- 面试官问"你怎么知道效果好"，你终于有答案了。

---

### 🥈 第 2 件：把"引用溯源"从格式校验升级为支撑性校验（0.5–1 天）

**这是你现在的真实缺陷，必须修。** JD 第 2 条点名"引用溯源"。

现在 `check_citation_integrity` 只查编号真不真，**下面这种会被放行**：
```
来源[1]："采购金额超过 10 万元的，应当公开招标"
回答  ："根据[1]，采购金额超过 50 万元的应当公开招标"    ← 编号真、内容假
```

| 补什么 | 具体做法 |
| --- | --- |
| **关键事实比对** | 从回答中抽出金额 / 期限 / 比例 / 否定词，检查是否能在**被引用的那个片段**里找到（做归一化："十万元" = "100000 元" = "10 万元"） |
| **编号就近对齐** | 现在 `[n]` 出现在任意位置都算数 —— 改成**必须出现在它支撑的那句话附近**（同句或前一句），否则报 `CITATION_MISPLACED` |
| **两类问题分开落库** | 现在都塞进同一个 `citation_problems` 数组 —— 拆成"编号造假"与"内容不支撑"两类，**后者更隐蔽也更危险** |

**产出**：`Faithfulness` 指标（和第 1 件共用代码）+ 一句很有分量的面试话术：
> "我发现我的引用校验有个盲区：它只验证编号存在，不验证内容支撑 ——
> 所以我加了关键事实比对与引用就近对齐，并把两类问题分开统计。"

---

### 🥉 第 3 件：装完 Ollama 后做 **Function Calling + 最小 ReAct 循环**（3–5 天）

**这是"AI 实习生"和"RAG 实习生"的分界线**，也是这个 JD 最看重的（第 1、3 条）。

**你有一个别人没有的起点**：你有一个权限严密、状态机完整的**真实业务系统**让 Agent 去调。

| 做什么 | 具体做法 |
| --- | --- |
| **工具定义（JSON Schema）** | 先做 **4 个只读工具**：`查申请状态` / `查我的待办` / `查制度`（复用现有 RAG 检索）/ `查预算余额`。每个工具带 `description`（模型靠它决定调不调） |
| **ReAct 循环** | 调模型 → 解析 `tool_calls` → 执行 → 结果回灌 → 再调 → 直到给最终回答。**必须有最大步数与超时**（否则死循环烧时间） |
| **工具执行的权限约束** ⭐ | 工具内部**沿用调用者的 `RequestScope`** —— Agent **不获得任何超出该用户的权限**；查别人的单子一样返回 404 |
| **工具调用的幂等** ⭐ | 写工具（第一版**不做**）若要做，必须复用你已有的幂等键 —— **因为 LLM 一定会重复调同一个工具** |
| **工具调用留痕** | 挂到你已有的事件流上：谁、什么参数、什么时候、结果如何 |
| **"该不该调工具"的判据** | 制度问题 → 必须先检索；单据状态 → 必须走工具（数据库是唯一真相）；**写操作 → 第一版一律不做**，只回答"这需要你在系统里操作，步骤如下…" |

**⭐ 这两条（权限 + 幂等）是你最值钱的差异化，务必主动讲**：
> "我的 Agent 是挂在**真实业务系统**上的：工具沿用用户的可见范围、写操作走幂等键与条件更新、
> 每一步留痕。**大多数 Agent demo 不需要考虑'工具调用失败会不会重复付款'，
> 而我的项目里这是第一优先级。**"

**⚠️ 一个必须处理的矛盾**：你的 system prompt 第 4 条写着
"你是解释工具，不能执行任何采购操作" —— 加了工具之后**这句话要改**，
要改成"**写操作需要用户在系统里确认，你只负责解释与只读查询**"。
否则 prompt 与实现就矛盾了（而面试官会读你的 prompt）。

### 4️⃣ 第 4 件：Prompt 版本 + A/B（1–2 天，**必须在有真模型之后**）

JD 第 1 条点名 "Prompt 设计"。你现在只有一个硬编码的四句话 prompt。

| 做什么 | 做法 |
| --- | --- |
| **prompt 抽成带版本的模板** | `SYSTEM_PROMPT_V1` / `V2`，并在 `chat_messages` 里**记录这条回答用了哪一版** |
| **真实 A/B** | 用第 1 件的评测集跑两版，给出指标差异（"V2 强制要求引用编号后 Faithfulness 从 X→Y"）—— **Y 必须真跑出来** |
| **结构化输出** | 让模型返回 `{"answer": "...", "citations": [1,3]}`，用 Pydantic 校验，失败可重试或降级。**这同时解决了"引用校验靠正则"的脆弱性** |
| **参数显式化** | `temperature / max_tokens / 超时 / 重试` 从硬编码变成配置 |

---

### 5️⃣ 第 5 件：检索重排 + 混合检索（2–3 天，**在第 1 件之后做**）

JD 第 2 条明确写了"**检索重排**"。你现在只有单路向量 top-k。

| 做什么 | 做法 |
| --- | --- |
| **先测 BM25 单路** | PostgreSQL 原生 `tsvector` + `ts_rank`（**不引 ES**）。中文要用 `simple` 配置 + 你已有的**按字切分**思路，或者干脆用 `pg_trgm` |
| **混合检索 + RRF 融合** | 两路各取 top-k，用 Reciprocal Rank Fusion 合并。**用同一套评测集对比** —— 这就是第 1 件的价值兑现 |
| **重排** | 先做**规则重排**（同文档相邻 chunk 聚合、按生效时间加权、去重），再考虑接 rerank 模型 |
| **换真 embedding 再测一遍** | Ollama 拉一个 `bge-m3`，**同一评测集对比"哈希 embedding vs 真 embedding"** —— 大概率是一次**很大的**提升，而且这是**真实的、可量化的**数字 |

**产出**：
> "用 Golden QA 量化对比：哈希 embedding Recall@5 = X% → bge-m3 = Y%；
> 加入 BM25 混合检索（RRF 融合）后 Z%。"

---

### 6️⃣ 第 6 件：延迟与成本可观测（1 天）

JD 第 5 条明确点名"**延迟、成本、稳定性**"。你现在**一点都没记录**。

| 记什么 | 记在哪 |
| --- | --- |
| 检索耗时 / 模型耗时 / 总耗时 | `chat_messages` 加列，或单独一张 `chat_metrics` |
| **prompt_tokens / completion_tokens** | OpenAI 兼容响应的 `usage` 字段（流式要加 `stream_options`，或末尾单独统计） |
| **估算成本** | 按 token 数 × 单价（本地模型则为 0，但**代码要能算** —— 面试时能讲"我算了成本模型"） |
| 工具调用次数 / 轮数 | Agent 循环里统计 |

**然后把这些数字接进第 1 件的评测报告** —— 一份报告同时给"质量 + 延迟 + 成本"，正是 JD 第 5 条要的样子。

---

### 7️⃣ 第 7 件：限流 + 全栈 Docker（1–2 天）

| 做什么 | 为什么对手项目值钱 |
| --- | --- |
| **问答接口限流** | LLM 接口被刷直接变账单（即使是本地模型，也会打满显存）—— **这是"成本意识"的体现** |
| **登录接口限流** | 防撞库，老生常谈但 JD 第 6 条点名"限流" |
| **后端也进 Docker** | 现在 `docker-compose` 只跑数据库。多阶段构建 + 一条 `docker compose up` 起全栈，JD 第 6 条点名 Docker |
| 结构化日志 | 你已有 `request_id` 串联，补上 JSON 格式即可 |

## 三、做完之后，简历上的 AI 部分可以这么写

```markdown
### 企业采购制度助手（RAG + Agent）· 个人项目 · 独立完成
Python / FastAPI / PostgreSQL + pgvector（HNSW）/ Ollama（本地 Qwen2.5-7B）/ SSE / pytest

· 检索增强问答：制度文档切分（600 字 / 100 重叠 / 尾片合并）→ 向量检索（pgvector + HNSW）
  → 带引用流式回答（SSE 四事件协议，前端手写分帧解析）；
  按 version + effective_from 只检索当前生效版本，避免新旧条文混引。

· 引用溯源双层校验：① 引用编号真实性；② **引用内容支撑性**（关键事实比对 +
  引用就近对齐），并把"编号造假"与"内容不支撑"分开统计 —— 只做前者会放行
  "编号真、内容假"的回答。

· 量化评测与质量门禁：建立 28 组 Golden QA（含无答案与跨版本问题），
  实现检索层 Recall@5 / MRR 与生成层 Faithfulness 指标，
  接入回归入口做 Hard Gate；据此量化对比哈希 embedding 与 bge-m3（Recall@5 X% → Y%）、
  单路向量与 BM25+向量混合检索（RRF 融合，Z%）。

· 带安全边界的工具调用 Agent：实现只读工具（查申请状态 / 待办 / 制度 / 预算）的
  ReAct 循环（含最大步数与超时）；**工具沿用调用者的数据可见范围，
  不授予额外权限**；工具调用全量留痕；写操作仅返回操作指引，
  需用户在系统内确认（复用已有的幂等键与条件更新防重复执行）。

· 工程与成本：记录检索/模型耗时与 token 用量用于成本核算；
  问答与登录接口限流；全栈 Docker 化。
```

> **注意最后两条里的加粗部分** —— 那是你相对其他候选人**唯一难以复制**的东西。

## 四、优先级判断表（时间不够时砍哪个）

## 五、明确**不要做**的（做了费时间还不加分）

| 不要做 | 为什么 |
| --- | --- |
| ❌ **自研 Agent 框架 / 多 Agent 协作** | 这个 JD 是**实习岗**，要的是"能跑通 + 懂原理"，不是造框架。而且自研框架的代码面试官不会细看 |
| ❌ **引入 LangChain / LlamaIndex 重写** | 你已经用最朴素的方式实现了一遍，**这本身是加分项**（"我知道框架里那几行在干什么"）。重写等于把优势变成"我会用框架" |
| ❌ **微调（LoRA / SFT）** | 与 JD 的 7 条职责**一条都不对应**，而且你的数据量根本不够 |
| ❌ **接付费 API 做"更大模型对比"** | 除非你已经有一个免费额度。本地 7B 已经能做出所有需要的数字；**"我用的本地模型"不丢分，"我没有数字"才丢分** |
| ❌ **做压测 / 云部署 / K8s** | 实习岗不问这个，而且你没有真实流量，压出来的数字没有意义 |
| ❌ **为"多语言/多租户"重构** | 与本 JD 无关 |
| ❌ **把 embedding 写成"自研语义模型"** | **这是简历造假**。它是哈希投射，没有语义能力 —— 老实说反而加分（见下） |

## 六、诚实边界：这些事**做完也不算解决**

| 边界 | 面试怎么说 |
| --- | --- |
| **本地 7B ≠ 生产模型** | "我用本地 Qwen2.5-7B 完成了链路与评测的真实验证；上层校验与评测都不依赖具体模型，换模型只需改两个配置，评测集会立刻给出差异。" |
| **哈希 embedding 无语义能力** | "它只用于验证链路；**我用同一套评测集量化了它与 bge-m3 的差距**（这才是真话该有的样子）。" —— 换真 embedding 后，这句话就变成优势了 |
| **评测集只有 28 组** | "规模小但**覆盖了无答案、跨版本、口语化模糊**这几类最容易出错的；它是我做后续优化的 baseline，不是产线级基准集。" |
| **Agent 只做只读工具** | "写操作我没让 Agent 做 —— 因为它会动钱和单据。**要做的话我会复用已有的幂等键与条件更新**，这样 LLM 重复调工具不会造成重复付款。" |
| **没上过线** | 照旧直说，然后用"评测 + 回归门禁"证明可验证性 |

## 七、一句话总结

> **能做的有 7 件，但真正的分水岭只有 3 件**：
> **① 装 Ollama（1 小时，解锁真模型）→ ② 建评测集与指标（3–5 天，JD 权重最高）→ ③ Function Calling + ReAct 循环（3–5 天，Agent 岗门槛）**。
>
> 做完这 3 件（约 **1.5 周**），你就从"做过 RAG 的后端"变成
> "**有量化评测、能安全地让 Agent 调真实业务工具的工程实习生**" ——
> 后者对这个岗位值钱得多，而且**你的权限模型、幂等键、条件更新、五层验证，
> 恰好是绝大多数 Agent demo 完全缺失的部分**。
