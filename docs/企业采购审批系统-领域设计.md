## 一、先澄清一件事：采购审批不等于报销审批

这两个经常被混为一谈，但流程长度差很多。选错了会直接影响你的学习收获。

| | 报销审批 | 采购审批 |
| --- | --- | --- |
| 起点 | 钱已经花了 | 钱还没花 |
| 核心问题 | 这笔记账能不能报 | 这东西该不该买、跟谁买、多少钱 |
| 流程长度 | 短（提交 → 审批 → 打款） | 长（申请 → 审批 → 询价 → 定标 → 下单 → 收货 → 付款） |
| 独有机制 | 发票校验、费用标准 | 多级动态审批、预算预留、比价、三单匹配 |
| 学习价值 | 中 | 高 |

**采购审批明显更适合你**，因为它多出来的每一个环节都是值得学的工程问题：按金额动态决定审批链、预算的并发预留与释放、多家供应商报价比较、订单与收货与发票三者对账。

下面全部围绕采购审批展开。

## 二、角色与职责

一共 **8 个角色**（原政务项目只有 3 个），而且角色的视角差异更大，这正好让你练多角色后台设计。

| 角色 | 代码 | 核心职责 | 主要看什么 |
| --- | --- | --- | --- |
| 申请人 | `REQUESTER` | 提采购需求、补充材料、撤回 | 我的申请、进度、被驳回原因 |
| 部门主管 | `DEPT_MANAGER` | 一级审批（需求是否真实合理） | 待我审批 |
| 部门负责人 | `DEPT_HEAD` | 二级审批（金额较大时） | 待我审批、部门预算 |
| 采购专员 | `PROCUREMENT` | 询价、比价、定标、下单、跟进到货 | 待处理采购单、供应商库、比价表 |
| 财务 | `FINANCE` | 预算校验、付款审批、执行付款 | 待付款、预算看板、三单匹配异常 |
| 总经理 | `GM` | 五级审批（金额重大时的经营层决策） | 待我审批（仅大额） |
| 收货人 | `RECEIVER` | 收货验收、登记实收数量 | 待到货、验收登记 |
| 管理员 | `ADMIN` | 品类配置、审批规则、供应商准入、用户、审计 | 全部配置与报表 |

**`GM` 是第二轮补齐的角色**：金额 ≥ 20 万元的申请需要经营层决策，原角色表漏了它。实际使用中 **`GM` 由 `ADMIN` 兼任**（一个用户可持多个角色），所以 M3 的验收写"8 个角色"，而初始化数据里是 7 个人。

**候选人的解析范围不同**（M6 要用）：`DEPT_MANAGER` / `DEPT_HEAD` 按申请人部门（含子部门）解析；`PROCUREMENT` / `FINANCE` / `GM` 从全局解析。

设计要点：不要做成"角色决定看什么页面"，而要做成"角色决定能看到哪些待办和操作按钮"。原项目在这一点上做得很好，它的 `PortalCommandPolicy` 是把角色和命令组合起来判定，不是简单的前端隐藏。

### 2.1 职责分离（SoD）——2026-10-03 补入

**这一节是后来补的。** M0 定稿角色表时，只回答了"**谁能做什么**"（角色 → 权限），
没有回答"**谁不能做什么**"（不相容职务分离）。后者才是采购内控里出事最多的地方。

**依据**（原文见 [`采购内控对照.md`](采购内控对照.md)）：

- 财政部《企业内部控制应用指引第 7 号》第五条：**"企业除小额零星物资或服务外，不得安排同一机构办理采购业务全过程"**；
- 上市公司制度范本的**五条不相容岗位**：请购与审批／询价与核价、确定供应商／合同订立与审核／
  采购验收与会计记录／付款申请、审批与执行；
- Oracle Procurement 的 **Prohibit User Self-Approval**：把提交人从审批链里 **skip 掉**，任务顺延下一人；
- OWASP：最小权限、默认拒绝、每个请求都校验。

**本项目现状（如实记录）：**

| 不相容岗位 | 现状 | 状态 |
| --- | --- | --- |
| **请购与审批** | **已落地**（2026-10-03）：建链时剔除提交人；或签任务另在待办查询与决定接口各拦一层 | ✅ |
| 询价与确定供应商 | v1 **刻意不分离**（同一采购角色），靠"≥3 家有效报价 + 供应商合格 + 报价完整 + 记录成交单价"兜底 | 🟡 已定稿取舍 |
| 采购、验收与会计记录 | `PROCUREMENT` / `RECEIVER` / 系统记录，三方分离 | ✅ |
| 付款的申请、审批与执行 | v1 **刻意不拆出纳**（`FINANCE` 同时审核与付款），靠"三单匹配 + 状态机"兜底 | 🟡 已定稿取舍 |

**自审拦截为什么是三层（少一层就有口子）：**

| 层 | 挡的是 |
| --- | --- |
| 建链时剔除提交人 | **会签**（预分配人）、以及"该级只剩提交人"（→ 提交时 422） |
| 待办查询加 `requester_id != actor_id` | **或签**：或签任务 `assignee_id` 为 NULL、只按角色可见，第一层挡不住 |
| `decide`/`claim` 的 SQL 守卫 + 403 | 直接用 id 打接口（Postman 绕过界面） |

**两条边界（已定稿）**：不引入"发起人自选审批人"；**不做委托/转办**——
审批任务只允许符合候选条件的人认领或处理。将来要做委托时，
一次把"转派后重新校验权限、角色、范围、历史责任链"设计进去。

## 四、审批流引擎（这是整个系统的核心）

原项目是单级审批（工作人员认领后直接决定）。采购系统必须做多级动态审批，这是你能比原项目做得更深的地方，也是最有学习价值的模块。

### 4.1 核心思路：审批链是一个纯函数

```
resolve_approval_chain(request) -> list[ApprovalStep]
```

输入是品类、金额、部门、是否紧急、是否走框架协议；输出是一个有序的审批步骤列表。这个函数不碰数据库、不碰 HTTP，是纯计算，所以可以单独写单元测试，测试成本极低。

### 4.2 规则怎么存：复用原项目的受限 DSL 思路

原项目的资格预检用了一套受限 JSON DSL（`eq / ne / in / exists / lt / lte / gt / gte / all / any / not`），按点路径取值，不求值、不执行代码。这套 DSL 完美适合表达"金额达到多少就加一级审批"。

把审批规则挂在采购品类上：

```json
{
  "steps": [
    { "order": 10, "role": "DEPT_MANAGER", "mode": "SINGLE", "when": { "gte": ["amount_fen", 0] } },
    { "order": 20, "role": "DEPT_HEAD",    "mode": "SINGLE", "when": { "gte": ["amount_fen", 100_000] } },
    { "order": 30, "role": "PROCUREMENT",  "mode": "SINGLE", "when": { "gte": ["amount_fen", 1_000_000] } },
    { "order": 40, "role": "FINANCE",      "mode": "SINGLE", "when": { "gte": ["amount_fen", 1_000_000] } },
    { "order": 50, "role": "GM",           "mode": "SINGLE", "when": { "gte": ["amount_fen", 10_000_000] } }
  ],
  "skip_when_framework_contract": true,
  "urgency_extra_step": { "role": "DEPT_HEAD", "when": { "eq": ["urgency", "URGENT"] } }
}
```

**路径名必须用 `amount_fen`，不能用 `amount`。** 审批引擎按点路径从 `request_context` 里取值，而上下文里放的是 `amount_fen`（单位：分）。写成 `amount` 的后果特别隐蔽：`rules.py` 对"缺字段"的语义是**返回 False（不满足）**而不是报错，所以整条规则会**静默失效**——策略看起来配得好好的，审批链却算出来是空的。这类错误不会抛异常，只会让你怀疑人生。

顺便再强调一次阈值单位：`100_000` 是 **1000 元**，`10_000_000` 是 **10 万元**。策略 JSON 里永远写"分"。

一个申请提交时，引擎按 `order` 依次评估每个步骤的 `when`，条件为真就加入审批链。按上面这份策略：金额 5000 元的申请会产生 **2 个**审批任务（部门主管 + 部门负责人），金额 50000 元的会产生 **4 个**。四档金额 500 / 5000 / 50000 / 200000 元对应 **1 / 2 / 4 / 5** 个任务——这就是 M6 的验收基准，附录 A.6 的参数化测试用的也是这四个数。

### 4.3 审批模式

| 模式 | 含义 | 实现要点 |
| --- | --- | --- |
| `SINGLE` 或签 | 该角色任一人通过即可 | 同一步骤下任一任务通过，该步骤即完成 |
| `ALL` 会签 | 该角色所有人都要通过 | 同一步骤下全部任务通过，该步骤才完成 |

> **M6 实际只实现上面两种**（数据库 `mode IN ('SINGLE','ALL')`）。
> 第三种的**委托**（审批人临时委托他人代审，记录 `delegated_from` / `delegated_to`）
> **已定稿不做**（2026-10-03）—— 见第十二节「第一版先砍掉这些」表与
> [`业务规则.md`](业务规则.md) 第 9 条。
> 理由与"不给任务状态加 `WAITING`"同源：**没有触发路径的状态与列，加了也测不到**，
> 还会让 `mode` 的取值域从"两种确定的语义"变成"两种 + 一个空壳"。

### 4.4 审批任务状态

```
PENDING  ->  APPROVED（通过）
         ->  REJECTED（驳回）
         ->  SKIPPED（因规则变化被跳过，要留原因）
         ->  CANCELLED（申请被驳回时，同级与后面几级未处理的任务一并取消）
```

> **实际是五档**（`PENDING / APPROVED / REJECTED / SKIPPED / CANCELLED`），
> 上面那张图里没有画 `DELEGATED`：委托这一档随委托功能一起推迟，理由见 4.3 的说明。
> 状态词表写在 `backend/app/domain/enums.py`，数据库上还有一条 CHECK 兜着。

**这五档里没有"还没轮到"。** 这是刻意的，也是 2026-10-02 专门澄清的一点：

一次提交会把审批链上每一级的任务**全部建出来**（这样审批链进度能一眼看全），
所以第 3/4/5 级的任务在库里确实是 `PENDING` —— 但**"现在轮到谁"不属于任务状态**，
它属于**审批流**：`approval_flows.current_step_order`（唯一事实来源）。

不把"未轮到"塞进任务状态的理由：那样同一件事会同时存在两处（流的指针 + 任务的 `WAITING`），
**两份状态一定会漂移** —— 推进流的那一步若漏改任务，就会出现"流说第 3 级、任务说自己在等"
这种自相矛盾的数据。一个概念只存一处。

由此推出三条硬规矩：

1. **待办查询**：`status = 'PENDING'` **且** `step_order = current_step_order`；
2. **认领 / 通过 / 驳回**：同样要校验"属于当前级"，不属于 → **403**
   （任务对他可见，只是还没轮到他；可见但无权是 403，不在可见范围才是 404）；
3. **某一级完成后**推进 `current_step_order` 时**必须条件更新**，
   否则两人同时通过同一级的不同任务会把指针推进两次、**跳过一整级**。


### 4.5 驳回策略

驳回是最容易做错的地方，先想清楚三种策略，选一种：

| 策略 | 行为 | 适合 |
| --- | --- | --- |
| 终止式（建议先做这个） | 任一步驳回，整个申请变 `REJECTED` | 简单、可预测 |
| 回退式 | 驳回后回到上一级或指定步骤重走 | 复杂，要处理已通过步骤是否作废 |
| 补充式 | 驳回但允许申请人修改后从原步骤继续 | 最贴近真实业务，但状态管理最复杂 |

建议：第一版只做终止式，把状态机做扎实；等阶段 5 稳定了再考虑补充式。

### 4.6 审批与业务状态的关系

一个容易踩的坑：不要把审批链的状态和主单状态混在一起。

正确做法是两层：

- `purchase_requests.status` 是业务状态（`IN_APPROVAL`、`ORDERED` 等）
- `approval_flows` 与 `approval_tasks` 是审批子状态

主单进入 `IN_APPROVAL` 时创建一条 `approval_flow` 和 N 条 `approval_task`；当所有任务都通过时，由审批模块发布一个"审批完成"事件，主单状态机才推进到 `SOURCING`。两个状态机通过事件解耦，不要互相直接改字段。

## 五、关键业务规则（这个领域的精华）

这些规则才是采购系统真正值得学的地方。左边是规则，右边标注了它是锻炼什么能力的。

### 5.1 预算预留与释放（并发核心）

**规则**：申请提交时从部门预算里"预留"这笔钱；驳回或撤回时释放；付款成功时转为"已花"。

预算表三个字段：`amount_total`（总额）、`amount_reserved`（已预留）、`amount_spent`（已花）。可用余额 = 总额 − 已预留 − 已花。

**关键**：不能写成"先查询再更新"。两个人同时提交两笔申请，先查后写会导致预算被超额占用。要用**条件更新**：

```sql
UPDATE budgets
   SET amount_reserved = amount_reserved + :amount
 WHERE id = :budget_id
   AND amount_total - amount_reserved - amount_spent >= :amount;
```

受影响行数为 0 就说明预算不足，直接返回业务错误。**并发安全，不需要加锁，不需要事务隔离级别调优。**

这个模式和原项目"工作人员认领任务"用的是同一个套路（文档里写的"待办认领使用条件更新，并发时只有一个工作人员成功"）。把它迁移到预算场景，你会真正理解条件更新的价值。

**实现落点（M7，2026-10-04 已落地）**：

| 关注点 | 落在哪 |
| --- | --- |
| 可用额、结转差额、预算年度 | `domain/budget_policy.py`（纯函数 + 14 条单测，毫秒级） |
| 条件更新与**自带流水的四个方法** | `infrastructure/repositories/budget_repo.py`：`reserve / release / spend / settle` |
| 什么时候预留 / 释放 | `coordinators/purchase.py`（提交、撤回）、`coordinators/approval.py`（驳回） |
| 结清 | `BudgetRepository.settle()` —— **M10 的付款接口直接调它，不要再写第二份算术** |
| 账本 | `budget_transactions`：`UNIQUE(request_id, kind)` + `amount > 0`，只追加 |

三条口径（写死在代码里，改口径要一起改文档）：

1. **超预算 → 422**（`BUDGET_INSUFFICIENT`），文案带"可用 / 需要 / 还差"三个数；
2. **没有预算行（计划外）→ 422**（`NO_BUDGET`），处置同样是"先配 / 调预算再重新提交"；
3. **付款时 `SPEND(实付) + RELEASE(预留 − 实付)`**——差额必须显式释放，否则额度永久虚低。

### 5.2 审批阈值（动态多级审批）

金额决定审批层级，规则用 4.2 的 DSL 存在品类上。金额 500 元和 500000 元的申请，走完全不同的审批链，但**代码只有一份**。

### 5.3 三家比价

**规则**：金额超过阈值（比如 10000 元）的采购，必须有至少 3 家供应商的有效报价才能定标。

实现要点：定标接口里校验 `quotations.count(valid) >= 3`，不足时返回 422 并说明还差几家。这条规则让你必须认真设计"报价"这个从属实体的状态（`DRAFT` / `SUBMITTED` / `EXPIRED` / `SELECTED`）。

### 5.4 供应商准入

**规则**：只能选合格供应商库里的、且未被禁用的供应商。

供应商需要有资质有效期，过期自动不可选。这条规则适合用定时任务或查询时过滤实现——**建议先用查询时过滤**，简单且不会有状态漂移。

### 5.5 禁止拆分申请（进阶规则）

**规则**：同一个申请人、同一个品类、同一个需求，在短时间内拆成多笔小额申请来规避审批，是典型舞弊手法。

检测方式：提交时检查"该部门 + 该品类 + 最近 7 天 + 状态未终结"的申请总金额是否异常。

**这条属于进阶功能，第一版可以只做一个 warning 提示，不做拦截。** 但它是采购系统里非常有代表性的风控规则，值得写进作品集说明。

### 5.6 三单匹配（Three-way Match，最经典）

**规则**：付款前，必须比对三份单据：

| 单据 | 来源 | 关键字段 |
| --- | --- | --- |
| 采购订单 PO | 采购专员下单 | 数量、单价、金额 |
| 收货单 GR | 收货人验收 | 实收数量 |
| 发票 Invoice | 供应商开具 | 发票号、金额、税额 |

**匹配粒度定死：第一版按「订单级」**（第二轮修正）。表结构里订单有明细行、收货有多行、发票可以有多张，而 `match_three_way` 的入参全是标量——所以**先求和，再比**：

| 匹配项 | 取自哪里 |
| --- | --- |
| `ordered_qty` | `SUM(purchase_order_lines.quantity)` |
| `ordered_amount_fen` | `purchase_orders.amount`（订单总额） |
| `order_supplier_id` | `purchase_orders.supplier_id` |
| `accepted_qty` | `SUM(goods_receipt_lines.accepted_quantity)`（**所有收货单求和**） |
| `invoice_amount_fen` | `SUM(invoices.amount)`（**所有发票求和**） |
| 发票供应商一致性 | **所有**发票的 `supplier_id` 都等于订单供应商，才判一致 |

**明细行级匹配进"暂时砍掉"清单**（M10 之后按需）：它能发现"甲行多收、乙行少收"这类对不上的情况，但要求三张表逐行对齐、还要处理行与行之间的数量拆分，是另一个量级的活。先订单级跑通，M10 不会在"该按行还是按单"上耗掉两天。

**匹配跑在「执行付款」这一步**，不是创建付款单时：

| 时机 | 做什么 |
| --- | --- |
| 创建付款单（`PENDING`） | 只校验"主单 = `RECEIVED`、且至少有一张发票" |
| **执行付款（`pay`）** | **在这里跑三单匹配**，通过才 `spend_budget` |
| 预检接口 `GET /requests/{id}/match` | 只读展示，给前端渲染对比页，**不做任何状态变更** |

放在执行付款，是因为那是唯一真正动钱的时刻，也是唯一能保证"校验通过后单据没再被改"的时机。

匹配逻辑：

1. 收货数量 ≤ 订单数量（超收要人工确认）
2. 发票金额与订单金额的差异在容差内：**`max(金额 × 2%, 50 元)`**——比例与绝对值取较大者，否则小额单永远匹配不上
3. 发票上的供应商与订单供应商一致

全部通过 → 允许付款；否则 → 付款被拒绝（422 并返回问题列表），由采购或财务修正后重试。

**第一版就按"拒绝 + 返回问题列表"做，不要一上来就做"挂起 + 异常任务"。** 后者要引入一个额外的任务类型、额外的状态和额外的分配逻辑（该派给采购还是财务？谁负责关闭？），是一整套独立的小流程；而它的业务价值是"不阻塞、可跟踪"，等你 M10 主链路跑顺了再补，收益更清楚。**"返回问题列表"这条路已经能让你把三单匹配的价值演示完整**——差异看得见、看得懂，这就够了。

**这是采购系统最著名也最有学习价值的机制**，原项目里没有对应物。做出来就是你相对原项目的增量。

### 5.7 收货完成才能付款

顺序约束，在状态机里强制：`RECEIVED` 之前的申请不允许创建付款单。不要靠前端按钮控制。

### 5.8 金额一律用整数分存储

**不要用 float 存金额。** 在 PostgreSQL 里用 `BIGINT` 存"分"，或者用 `NUMERIC(18,2)`。Python 侧对应 `int` 或 `Decimal`。

这条看着简单，但很多人在第一个项目里用 float 存钱，后面全部对不上账。**第一天就做对。**

### 5.9 幂等与乐观锁（照搬原项目的做法）

所有写操作要求 `Idempotency-Key`，记录 `(actor, scope, key, payload_hash)`；同键同载荷返回原结果，同键不同载荷返回冲突（`409`）。

**`scope` 的定义不能含糊**，建议就用**端点标识**（如 `POST:/api/v1/requests/{id}/submit`）。留空或随手写会让同一把 key 在不同接口之间互相污染——第二次请求会拿到第一次的响应，而且看起来一切正常。

**"查不到就执行"是不完整的，缺了并发占位这一环。** 两个请求带同一个 key **同时**到达时，双方都查不到记录，于是双方都执行了操作——幂等失效，且失效得悄无声息。正确流程：

```
1. 独立事务：插入占位行 (actor_id, scope, key, payload_hash, status=IN_PROGRESS)
   ├─ 撞唯一索引 → 已有同 key 请求，再查它的状态
   │    ├─ COMPLETED 且 payload_hash 相同 → 返回它存下的响应
   │    ├─ payload_hash 不同              → 409
   │    └─ IN_PROGRESS                    → 409（"正在处理中，请稍后重试"）
2. 业务事务：执行操作 → 回填响应与 status=COMPLETED → commit
3. 业务失败：回滚业务事务，占位行标记 FAILED（或删除），让客户端可以重试
```

**占位行必须用独立事务提交**，否则业务回滚会把它一起带走，第 1 步就永远查不到它。

因此 `idempotency_records` 需要这几列：`actor_id / scope / key / payload_hash / status(IN_PROGRESS/COMPLETED/FAILED) / response / created_at`，外加 `(actor_id, scope, key)` 唯一索引。

主单和明细的每次变更推进 `version`，客户端提交旧版本返回 `409`。

**`payments.status` 值域（第二轮定死）**——原来文档里只出现过一次 `PAID`，没定义过：

```
PENDING  ->  刚创建，还没付
PAID     ->  已执行付款
FAILED   ->  付款尝试失败（保留痕迹，允许重新发起）
```

**一笔申请第一版只允许一笔付款**，靠 `UNIQUE(request_id)` 兜底。这条与主单状态机只有 `INVOICED -> PAID` 一次转移是自洽的；**部分付款 / 分次付款进"暂时砍掉"清单**——要改的话，`UNIQUE` 约束、状态机、以及 M7"一次性结清"的假设必须一起改，三处是绑定的。

**订单金额口径（2026-10-02 定死）**——原来只说了"把申请明细复制成订单明细、带上单价"，没说订单总额以谁为准：

```
purchase_orders.amount = Σ(purchase_order_lines.amount) = Σ(明细行单价 × 数量)
```

| 场景 | 明细行单价取谁 | 与申请单价的关系 |
| --- | --- | --- |
| **询价**（走过 `quotations`） | **定标报价单价** | 通常低于申请单价（比价压价），订单总额因而**小于**申请总额 |
| **直采**（没走询价） | **实际成交单价**：默认等于申请单价；有议价则取议价后价 | 可低可高（高于申请额属于例外，需有审批依据） |

两条由此推出的规矩：

1. **订单金额是"实际要付多少"的唯一基准**：三单匹配里的"发票金额 vs 订单金额"、
   预算结转里的"实付 vs 预留"，都以它为准，**不是以申请金额为准**。
   `purchase_requests.amount_total` 与订单金额不一致是**正常现象**（差额由"实付小于预留则显式释放"处理）。
2. **订单金额由后端按明细重算**，与 M5 的 `amount_total` 同一条纪律：只接受逐行单价与数量，不接受客户端传总额。

### 6.2 三条关系约束

1. `purchase_requests.budget_id` 在**提交时**认领并固定下来，此后不再改（防止中途换预算）。
   提交的那一刻就把这一列写死，是为了让"这笔申请当初占的是哪条预算"成为**事实**而不是推断 ——
   部门调整、品类变更、预算被重建都不该影响已经提交的单子。
   （M5 建表时这一列已存在但恒为 NULL；**M7 的预算预留落地时，在同一事务里认领并写入**。）
2. `purchase_order_lines.item_id` 必须属于同一个 `request_id`（跨单引用要报错）。
3. `payments` 只能在 `purchase_requests.status = RECEIVED` 之后创建。
4. **`budget_transactions` 上对 `(request_id, kind)` 建唯一约束**，让"同一笔申请被重复预留"直接暴露。
5. **`payments` 上对 `request_id` 建唯一约束**（或对 `paid_at` 建部分唯一索引），保证一笔申请只能付款一次——付款接口还必须有条件更新，两条一起用。

### 6.2.1 数据级权限：谁能看到哪些行

领域设计第 8 页的角色矩阵只回答了"谁能用哪些接口"，**没有回答"谁能看到哪些数据"**。后者才是采购系统里最容易出事的地方，必须在 M3 就定下来：

| 角色 | 可见范围 |
| --- | --- |
| `REQUESTER` | 只看自己提的申请 |
| `DEPT_MANAGER` / `DEPT_HEAD` | 本部门（含子部门）的申请 |
| `PROCUREMENT` / `FINANCE` / `RECEIVER` | **跨部门看全公司**（这是它们的职责） |
| `ADMIN` | 全部 |

实现上只有一条纪律：**把这个范围做成一个可以直接塞进 `WHERE` 的条件函数，所有"按 id 取单条"的接口都必须带上它**，查不到就是 404。**不要把权限写成"先查出来、再判断能不能看"**——那样漏一处就是越权，而且漏了不会报错。把权限写进查询，是让你不可能忘记加权限的唯一办法。

配套的错误码语义：资源在他的可见范围内但没权限操作 → **403**；资源根本不在可见范围内 → **404**（不告诉他这东西存在）。

## 附录：核心模块参考实现

这一节把上面最难、最值钱的几个模块写成可直接照抄的 Python。**建议你手敲一遍，不要复制。**

注意单位：**金额统一用"分"（int）**，所以策略里的阈值也必须是分。第四节示例里的 1000/10000/100000 是为了可读性写的"元"，真实策略文件里请写 `100_000` / `1_000_000` / `10_000_000`。

**并且路径名要用 `amount_fen`**（`request_context` 里放的就是这个键），不是 `amount`。写错不会报错——`evaluate` 对缺字段返回 False，于是整条规则静默失效、审批链算成空的。第四节已经按这个改正了。

### A.1 受限规则 DSL 求值器（`domain/rules.py`）

```python
from __future__ import annotations

from typing import Any


class RuleError(ValueError):
    """规则结构非法。"""


_OPERATORS = {"eq", "ne", "in", "exists", "lt", "lte", "gt", "gte", "all", "any", "not"}


def read_path(data: dict[str, Any], path: str) -> tuple[bool, Any]:
    """按点路径取值，返回 (是否存在, 值)。不抛异常，缺路径就是不存在。"""
    current: Any = data
    for part in path.split("."):
        if not isinstance(current, dict) or part not in current:
            return False, None
        current = current[part]
    return True, current


def evaluate(rule: Any, context: dict[str, Any]) -> bool:
    """求值一个受限规则。不求值字符串，不执行任何代码。"""
    if not isinstance(rule, dict) or len(rule) != 1:
        raise RuleError("每个规则对象必须且只能包含一个操作符")

    operator, operand = next(iter(rule.items()))
    if operator not in _OPERATORS:
        raise RuleError(f"不支持的操作符: {operator}")

    if operator == "all":
        return all(evaluate(item, context) for item in operand)
    if operator == "any":
        return any(evaluate(item, context) for item in operand)
    if operator == "not":
        return not evaluate(operand, context)

    if not isinstance(operand, list) or not operand:
        raise RuleError(f"{operator} 需要一个非空数组")
    path, *rest = operand
    exists, value = read_path(context, path)

    if operator == "exists":
        return exists
    if not exists:
        return False  # 缺字段一律判为不满足，不做猜测

    expected = rest[0] if rest else None
    if operator == "eq":
        return value == expected
    if operator == "ne":
        return value != expected
    if operator == "in":
        return value in expected
    if operator == "lt":
        return value < expected
    if operator == "lte":
        return value <= expected
    if operator == "gt":
        return value > expected
    if operator == "gte":
        return value >= expected
    raise RuleError(f"未实现的操作符: {operator}")
```

三个关键点：**每个对象只能有一个操作符**（避免歧义）；**缺字段返回 False 而不是抛异常**（业务上"没填"就是"不满足"）；**永远不 eval**。

### A.2 审批链解析（`domain/approval_engine.py`）—— 整个系统的核心

```python
from __future__ import annotations

from dataclasses import dataclass
from typing import Any

from app.domain.rules import evaluate


@dataclass(frozen=True)
class ApprovalStep:
    order: int
    role: str
    mode: str      # SINGLE（或签） / ALL（会签）
    source: str    # POLICY / URGENCY


def resolve_approval_chain(
    policy: dict[str, Any],
    request_context: dict[str, Any],
) -> list[ApprovalStep]:
    """纯函数：根据品类审批策略与申请上下文，算出这条申请要走几级审批。

    没有数据库、没有 HTTP、没有全局状态，所以可以脱离环境直接单测。
    """
    steps: list[ApprovalStep] = []

    for item in policy.get("steps", []):
        if evaluate(item["when"], request_context):
            steps.append(
                ApprovalStep(
                    order=int(item["order"]),
                    role=str(item["role"]),
                    mode=str(item.get("mode", "SINGLE")),
                    source="POLICY",
                )
            )

    urgency = policy.get("urgency_extra_step")
    if urgency and evaluate(urgency["when"], request_context):
        steps.append(
            ApprovalStep(
                order=int(urgency.get("order", 5)),
                role=str(urgency["role"]),
                mode=str(urgency.get("mode", "SINGLE")),
                source="URGENCY",
            )
        )

    # 走框架协议的品类跳过询价环节，不需要采购专员审批
    if policy.get("skip_when_framework_contract") and request_context.get("framework_contract"):
        steps = [step for step in steps if step.role != "PROCUREMENT"]

    # 按顺序排；同一角色只保留最靠前的一级，避免同一个人被要求审两次
    steps.sort(key=lambda step: step.order)
    seen: set[str] = set()
    unique: list[ApprovalStep] = []
    for step in steps:
        if step.role in seen:
            continue
        seen.add(step.role)
        unique.append(step)
    return unique
```

**"同一角色去重"这一行很容易被忽略，但很关键**：如果规则写得不小心，同一个部门主管可能被插入两次，用户会在待办里看到两条一模一样的审批，体验很差。

### A.3 主单状态机（`domain/state_machine.py`）

```python
from __future__ import annotations


class InvalidTransition(Exception):
    def __init__(self, current: str, target: str) -> None:
        super().__init__(f"不允许从 {current} 迁移到 {target}")
        self.current = current
        self.target = target


TRANSITIONS: dict[str, set[str]] = {
    "DRAFT":              {"IN_APPROVAL", "DISCARDED"},
    "IN_APPROVAL":        {"SOURCING", "REJECTED", "WITHDRAWN"},
    "SOURCING":           {"AWARDED", "WITHDRAWN"},
    "AWARDED":            {"ORDERED", "WITHDRAWN"},
    "ORDERED":            {"RECEIVED"},   # 第一版只做整单收货，不写 PARTIALLY_RECEIVED
    "RECEIVED":           {"INVOICED"},
    "INVOICED":           {"PAID"},
    "PAID":               {"CLOSED"},
    "REJECTED":           set(),
    "WITHDRAWN":          set(),
    "DISCARDED":          set(),
    "CLOSED":             set(),
}


def can_transition(current: str, target: str) -> bool:
    return target in TRANSITIONS.get(current, set())


def assert_transition(current: str, target: str) -> None:
    if not can_transition(current, target):
        raise InvalidTransition(current, target)
```

> **注意：第一版没有 `PARTIALLY_RECEIVED`。** 状态机里留一个永远走不到的状态，会让"合法转移通过、非法转移抛异常、终态无出口"这三组测试失去意义——你测的那个状态根本进不去。要做部分收货时再按实施计划 5.5 节 E 的四步把它加回来，这与 M5 那条"每次只加当前阶段用得到的转移"是同一个原则。
>
> 另外，注意 `ORDERED` 之后**没有** `WITHDRAWN` 出口：货已经下了，不能随便撤。这是业务规则直接长在状态机表里的体现。

**用一张表描述状态机，而不是写一堆 if/else。** 好处是：想加状态只改表、想画图可以直接从表生成、写测试可以把所有非法组合跑一遍。

### A.4 预算并发预留（`infrastructure/repositories/budget_repo.py`）

> **这一节是 M0 时的参考实现；M7 落地后代码与它有三处出入，以代码为准：**
>
> 1. 三个函数变成了 `BudgetRepository` 的**方法**，而且**自带流水** ——
>    `reserve / release / spend` 各自在条件更新之后写一条 `budget_transactions`，
>    这样"每次金额变动都留痕"就不可能被调用方漏掉；
> 2. 判定与解释**分开**：条件更新负责判定，失败后用
>    `domain/budget_policy.check_reservable()` 把"还差多少"算成人话
>    （并且必须**强制重读**当前值，否则并发失败方会读到请求开始时的快照）；
> 3. 多了一个 `settle()`：`SPEND(实付) + RELEASE(预留 − 实付)`，
>    差额释放的算术在 `domain/budget_policy.settlement()` 里（纯函数，有单测）。
>
> 下面的 `result.rowcount` 也已经换成了 `.returning(id)`：SQLAlchemy 异步 `Result`
> 的类型标注里没有 `rowcount`（mypy 会报），用 `RETURNING` 既类型干净又少一次查询。

```python
from __future__ import annotations

from sqlalchemy import update
from sqlalchemy.ext.asyncio import AsyncSession

from app.infrastructure.records.catalog import BudgetRecord


async def reserve_budget(
    session: AsyncSession, budget_id, request_id, amount_fen: int
) -> bool:
    """条件更新预留预算。返回是否预留成功——不要先查再写。

    ⚠️ 这里的写法有一个必须避开的坑，见下方「为什么不能写成 available >= amount_fen」。
    """
    guard = (
        BudgetRecord.amount_total
        - (BudgetRecord.amount_reserved + BudgetRecord.amount_spent)
    ) >= amount_fen

    statement = (
        update(BudgetRecord)
        .where(BudgetRecord.id == budget_id, guard)
        .values(amount_reserved=BudgetRecord.amount_reserved + amount_fen)
        .returning(BudgetRecord.id)
        .execution_options(synchronize_session=False)
    )
    result = await session.execute(statement)
    return result.scalar_one_or_none() is not None


async def release_budget(
    session: AsyncSession, budget_id, request_id, amount_fen: int
) -> bool:
    """驳回或撤回：释放预留。

    request_id 不是摆设：释放前要确认这笔申请确实有一条 RESERVE 流水，
    否则说明有释放入口被漏掉了——宁可在这里抛异常，也不要静默地把账弄乱。
    """
    statement = (
        update(BudgetRecord)
        .where(
            BudgetRecord.id == budget_id,
            BudgetRecord.amount_reserved >= amount_fen,
        )
        .values(amount_reserved=BudgetRecord.amount_reserved - amount_fen)
    )
    result = await session.execute(statement)
    return result.rowcount == 1


async def spend_budget(
    session: AsyncSession, budget_id, request_id, amount_fen: int
) -> bool:
    """付款成功：已预留转已花，总占用不变。"""
    statement = (
        update(BudgetRecord)
        .where(
            BudgetRecord.id == budget_id,
            BudgetRecord.amount_reserved >= amount_fen,
        )
        .values(
            amount_reserved=BudgetRecord.amount_reserved - amount_fen,
            amount_spent=BudgetRecord.amount_spent + amount_fen,
        )
    )
    result = await session.execute(statement)
    return result.rowcount == 1
```

#### 为什么不能写成 `available >= amount_fen`

下面这种写法是**新手最容易写出来、而且一跑就崩**的版本：

```python
available = (
    BudgetRecord.amount_total
    - BudgetRecord.amount_reserved
    - BudgetRecord.amount_spent
)
statement = (
    update(BudgetRecord)
    .where(BudgetRecord.id == budget_id, available >= amount_fen)  # ← 抛异常
    .values(amount_reserved=BudgetRecord.amount_reserved + amount_fen)
)
```

在 SQLAlchemy 2.0 上实跑，报错是：

```
TypeError: Boolean value of this clause is not defined
```

原因有两层，值得记住，因为它会在别处反复出现：

1. `amount_total - amount_reserved - amount_spent` 拿到的**不是整数，而是一个 SQLAlchemy 表达式对象**（SQL 的列相减）；
2. `表达式 >= amount_fen` 生成的是"**表达式 ≥ 表达式**"的比较子句，而这个子句被 `where(...)` 的第二个位置参数当成 Python 条件判断真值——SQLAlchemy 对子句取布尔值时会**主动抛 `TypeError`**（`ClauseElement.__bool__`）。

**正确做法是把整个减法写进守卫条件里，让数据库去做算术**（就是上面 `reserve_budget` 的写法）。实测结果：

```
SQL: UPDATE budgets SET amount_reserved = budgets.amount_reserved + :x
     WHERE budgets.id = :id
       AND budgets.amount_total - (budgets.amount_reserved + budgets.amount_spent) >= :y

available=5000 时：
  reserve 8000 -> rowcount 0   （正确拒绝）
  reserve 5000 -> rowcount 1   （正确通过）
  reserve 1000 -> rowcount 0   （已占满，正确拒绝）
```

这个写法还顺带解决了一个隐患：**减法留在数据库里，金额就始终是 `bigint` 运算**。如果在 Python 侧做减法，哪天金额列改成 `NUMERIC`，你拿到的就是 `Decimal`，再和 `int` 参数混算、比较，语义就容易出问题。**钱的算术尽量交给数据库。**

#### 两个必须一起加的约束

1. **`request_id` 要落进 `budget_transactions`**，并对 `(request_id, kind)` 建唯一约束。这样"同一笔申请因重试被预留两次"会直接撞唯一索引暴露出来，而不是悄悄多占一份预算。
2. **`budgets` 上加一条 CHECK 约束**作为兜底：`amount_reserved >= 0 AND amount_spent >= 0 AND amount_reserved + amount_spent <= amount_total`。应用层的判断总有一条路径是你没想到的，数据库这条兜底不算多余。

**三个必须遵守的约束**：

1. `reserve_budget` 必须和"创建申请 + 写事件 + 写幂等记录"在**同一个事务**里，任何一步失败整体回滚。
2. 每次调用都要往 `budget_transactions` 写一条流水（`RESERVE` / `RELEASE` / `SPEND`），否则以后对不上账说不清原因。
3. **绝对不要**写成先 `SELECT` 查余额、再判断、再 `UPDATE`。那样两个人同时提交就会超额占用。

### A.5 三单匹配（`domain/settlement_policy.py`）

```python
from __future__ import annotations

from dataclasses import dataclass

TOLERANCE_RATIO = 0.02        # 2%
TOLERANCE_ABS_FEN = 5_000     # 或 50 元，取两者较大值


@dataclass(frozen=True)
class MatchIssue:
    code: str
    message: str
    expected: int | None = None
    actual: int | None = None


def match_three_way(
    *,
    ordered_qty: int,
    ordered_amount_fen: int,
    order_supplier_id: str,
    accepted_qty: int,
    invoice_amount_fen: int,
    invoice_supplier_id: str,
) -> list[MatchIssue]:
    """返回所有不匹配项。空列表表示三单匹配通过，可以付款。"""
    issues: list[MatchIssue] = []

    if accepted_qty > ordered_qty:
        issues.append(MatchIssue(
            code="OVER_RECEIPT",
            message="实收数量超过订单数量",
            expected=ordered_qty,
            actual=accepted_qty,
        ))

    tolerance = max(int(ordered_amount_fen * TOLERANCE_RATIO), TOLERANCE_ABS_FEN)
    if abs(invoice_amount_fen - ordered_amount_fen) > tolerance:
        issues.append(MatchIssue(
            code="AMOUNT_MISMATCH",
            message=f"发票金额超出容差 {tolerance} 分",
            expected=ordered_amount_fen,
            actual=invoice_amount_fen,
        ))

    if invoice_supplier_id != order_supplier_id:
        issues.append(MatchIssue(
            code="SUPPLIER_MISMATCH",
            message="发票供应商与订单供应商不一致",
        ))

    return issues
```

**返回"问题列表"而不是返回布尔值**，这是有意的设计：布尔值只能告诉用户"失败了"，问题列表能告诉他"哪里不对、差多少"。前端拿这个列表直接渲染三列对比页的差异高亮。

这也是这套代码最好测的地方——纯函数、无依赖、输入输出都是基本类型，一个参数化测试就能覆盖几十种组合。

**⚠️ 粒度说明（第二轮补）**：`match_three_way` 的入参**全是标量**，它并不知道明细行的存在。所以**把明细"压平"是调用方（`coordinators/settlement.py`）的责任**：

- 第一版按**订单级**：收货数量取 `SUM(goods_receipt_lines.accepted_quantity)`，发票金额取 `SUM(invoices.amount)`，订单数量取 `SUM(purchase_order_lines.quantity)`、订单金额取 `purchase_orders.amount`。
- **多张发票时必须先校验"全部发票的供应商都等于订单供应商"**，再传一个标量进来——否则签名里的 `invoice_supplier_id` 根本表达不了"三张发票里有一张是别家"这种情况。
- 明细行级匹配（能发现"甲行多收、乙行少收"）进"暂时砍掉"清单。

签名刻意保持标量，是为了让**粒度成为一个可以被替换的决策**：将来要做行级匹配，改的是调用方与一个新的行级函数，而不是把这个纯函数改成接收一大坨 ORM 对象。

### A.7 这四个文件的关系

```
domain/rules.py            <- 通用规则求值，不认识"采购"
domain/approval_engine.py  <- 用 rules 算出审批链，不认识数据库
```

注意上面**四个 domain 文件没有一行 import 数据库、FastAPI 或任何框架**。这就是原项目 `domain/` 层的价值：它们可以在毫秒级跑完几百个测试，而且将来你换 Web 框架、换 ORM、换数据库，这四个文件一行都不用改。
