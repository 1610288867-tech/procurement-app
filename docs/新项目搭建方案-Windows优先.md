## 一、先说三个结论

**结论 1：你的平台选择不是妥协，而是回到了这个项目的原生形态。**

原项目的 Android 端本来就是一个 WebView 装本地 SPA——`index.html` + `portal-app-v2.js`（69 KB）+ `style.css` 这套前端代码，骨子里就是写给浏览器看的。只有"JS Bridge 那一层"是 Android 特有的。所以你做 Windows 浏览器端，等于把原项目的一个原生适配层去掉，前端代码思路几乎可以照搬。

**结论 2：领域换什么，其实没那么重要。**

这套骨架的领域耦合度很低。真正通用的部分是：目录（可申请的东西）、资格预检、动态表单、材料上传、审批状态机、幂等、乐观锁、审计、AI 问答加溯源。换成任何领域，这些都不变。真正要改的只有四样：种子数据、表单 Schema、角色名、前端文案。

**结论 3：不要先做 AI。**

AI 是这套系统里最容易做、最容易做错、学习价值最低的部分。真正值钱的是业务骨架（状态机、幂等、乐观锁、审计、权限）。把 AI 放到最后做。

## 二、业务领域建议

### 2.1 先看原项目的模块能映射成什么

选领域的唯一标准：这套骨架里的模块，有多少能在新领域里一一对应上。对应得越多，你越是在学架构，而不是在重新造轮子。

| 原政务模块 | 抽掉领域后的通用能力 |
| --- | --- |
| 事项目录 + 事项版本 | 可申请的服务/品类目录（带版本管理） |
| 资格预检（JSON DSL） | 申请前置条件校验（额度/权限/身份/时段） |
| JSON Schema 动态表单 | 可配置的申请表单 |
| 材料上传 + SHA-256 | 凭证/附件上传 |
| 办件状态机 | 审批流 |
| 工作人员认领 + 审批 | 处理人接单 + 多级审批 |
| 预约 | 时段预约 |
| 缴费 | 支付/结算/打款 |
| 身份核验 | 实名/资格验证（模拟） |
| 邮寄 | 履约与交付 |
| AI 咨询 + 知识库 + 溯源 | 智能客服 / 知识助手 |
| 转人工工单 | 人工客服 |
| 审计 + 指标 | 运营后台 |

### 2.2 三个强映射领域（推荐）

#### 推荐 ① 校园/企业「设备与场地申领预约系统」　映射度约 90%

| 原模块 | 新领域对应 |
| --- | --- |
| 事项目录 | 可申领设备 / 可预约场地目录 |
| 资格预检 | 学生或员工身份、信用分/黑名单、时段冲突、借用额度 |
| 动态表单 | 申领单 / 预约单（设备类型决定字段） |
| 材料上传 | 申请表、承诺书、押金凭证 |
| 审批状态机 | 提交 → 导师/管理员审批 → 领用 → 归还 / 逾期 |
| 预约 | 核心模块，时段 + 场地 + 冲突检测 |
| 缴费 | 押金 / 超时罚金（模拟） |
| 履约 | 归还验收 |
| AI 助手 | 怎么借用、押金多少、逾期怎么办 |
| 转人工 | 找管理员 |

为什么排第一：预约模块在这里是天然核心（原项目有完整预约状态机可以学），资格预检有真实含义（额度、时段冲突），数据全合成没有风险，而且做出来很好看。

#### 推荐 ②「企业费用报销 / 采购审批系统」　映射度约 90%

| 原模块 | 新领域对应 |
| --- | --- |
| 事项目录 | 报销类型 / 采购品类目录 |
| 资格预检 | 预算余额、报销标准、单据时限 |
| 材料上传 | 发票、凭证、比价单 |
| 审批状态机 | 提交 → 直属主管 → 财务 → 打款 / 驳回 |
| 缴费 | 打款（模拟） |
| 履约 | 实物采购的收货 |
| AI 助手 | 财务制度问答（最能体现 RAG 加溯源的价值） |

为什么好：这是最"业务真实"的选择，审批流天然是多级的（比原项目的单级审批更有学习价值），而且是企业里最常见的系统之一，写进作品集很有说服力。

#### 推荐 ③「IT 服务台 / 内部工单系统」　映射度约 85%

| 原模块 | 新领域对应 |
| --- | --- |
| 事项目录 | 服务类型（开权限、装软件、报修、领设备） |
| 资格预检 | 资产归属、权限等级、审批人规则 |
| 材料上传 | 截图、错误日志 |
| 审批状态机 | 提交 → 主管确认 → IT 处理 → 关闭 |
| 预约 | 上门服务时段 |
| AI 助手 | 核心模块，IT 知识库 + 溯源 + 转人工 |

为什么好：原项目最复杂的"AI 咨询 + RAG + 溯源 + 转人工"在这里是主角而不是配菜，可以直接复用整套设计思路。

### 2.3 其他候选（简表）

| 领域 | 映射度 | 特点 |
| --- | --- | --- |
| 宠物寄养 / 家政预约 | 约 70% | 预约+缴费+履约强，审批弱；容易做得有趣 |
| 场馆 / 健身房会员与预约 | 约 70% | 预约 + 缴费 + 核销 |
| 图书馆荐购与借阅 | 约 65% | 结构简单，适合当第一个练手项目 |
| 留学/签证材料代办 | 约 85% | 映射很高，但涉及真实敏感信息 |
| 保险理赔申请 | 约 90% | 映射极高，但强监管领域 |
| 打卡学习 + 证书颁发 | 约 70% | 证书生成正好用原项目的 DOCX 模块 |

### 2.4 我的建议

**首选：校园/企业「设备与场地申领预约系统」。**

理由排序：预约状态机在原项目里最完整，你能学到最多；资格预检在这个场景下有真实意义（不像图书馆荐购那样可有可无）；数据全合成，零合规负担；做出来的界面好看、演示效果好，适合放进作品集。

**备选：企业费用报销审批。** 如果你更想往企业级业务系统方向发展（就业面更广），选这个。

### 2.5 不建议选的领域

- 医疗、金融、真实身份认证：你不可能做到合规，学习价值也不增加，纯给自己找麻烦。
- 纯 CRUD 的领域（比如简单的博客、待办清单）：学不到这套骨架的价值，等于浪费了这个项目。

## 三、目标形态与平台路线

### 3.1 三个阶段的演进

```
阶段 1：Windows 浏览器访问
        FastAPI + PostgreSQL + pgvector  <-->  React SPA (localhost:5173)

阶段 2：Windows 独立窗口
        同一套前端代码 -> Tauri / pywebview 打包成 .exe

阶段 3：Android
        同一套前端代码 -> Capacitor 打包成 APK
```

关键洞察：三个阶段共用同一套前端代码。这是 Web 优先路线的最大优势。原项目为了 Android 造了一整套 Java 原生层（约 60 个类），而 Web 优先路线只需要一份 SPA。

### 3.2 从原项目到浏览器端：需要替换的边界

这是最实用的一张表。原项目的每个 Android 原生边界，在浏览器里都有对应的 Web API：

| 原 Android 组件 | 浏览器端对应物 | 说明 |
| --- | --- | --- |
| `PortalJsBoundary`（JS Bridge） | 直接 `fetch` + `EventSource` | 不需要 Bridge 了，前端直接调 HTTP |
| `OkHttp*Gateway`（6 个网关） | 一个 `src/api/client.ts` | 统一封装 fetch，自动带 token、处理 401 刷新 |
| `AndroidKeystoreSessionStore` | `httpOnly` Cookie（推荐）或 localStorage | httpOnly Cookie 更安全，且前端不用管 token |
| `SecureSessionBrokerProvider` | 删除 | 那是跨进程共享 token 用的，浏览器没有这个概念 |
| `DocumentPickerBoundary` | `<input type="file">` | 原生能力 |
| `MaterialDocumentSaveBoundary`（SAF） | 浏览器下载 / File System Access API | 原生能力 |
| `VoiceCaptureBoundary` | MediaRecorder + Web Speech API | 原生能力 |
| `TextToSpeechBoundary` | Web Speech API（speechSynthesis） | 原生能力 |
| `ServiceNavigationBoundary`（HMS 导航） | 删除，或换成高德/百度 Web 地图 | 你没有华为账号 |
| `PortalCoordinatorViewModel` | React 状态管理（Context / Zustand / TanStack Query） | ViewModel 变成 Hook |

一句话：原项目 Android 端约 60 个类，浏览器端需要的不到 10 个文件。

### 3.3 Windows 独立窗口的四种做法

| 方案 | 体积 | 需要学 | 上手难度 | 适合 |
| --- | --- | --- | --- | --- |
| Edge/Chrome `--app=` 模式 | 0 | 无 | 最低 | 只想有个独立窗口，一行 .bat 搞定 |
| PWA | 0 | Service Worker 基础 | 低 | 想要"安装"体验和离线能力 |
| pywebview | 几 MB | 只要会 Python | 低 | 你会 Python，不想学新语言 |
| Tauri | 5-10 MB | Rust（少量） | 中高 | 想要现代桌面开发经验，作品集加分 |
| Electron | 约 150 MB | Node | 低 | 生态最全，但最重 |

推荐顺序：阶段 1 结束时先用 .bat 启动浏览器 app 模式（零成本验证形态）；需要正式打包时上 Tauri（如果你愿意碰一点 Rust）；如果完全不想碰 Rust，用 pywebview，因为它和你现有的 Python 技能栈一致。

不推荐 Electron：150 MB 的体积对个人项目是纯负担，而且学不到新东西。Tauri 的"Web 前端加原生后端"思路和这套项目本身的架构思路是同构的。

### 3.4 后面上 Android 的路径

| 方案 | 复用程度 | 说明 |
| --- | --- | --- |
| Capacitor | 最高（约 95%） | 直接把你写好的 React SPA 打包成 APK，原生能力用插件或少量自写 |
| React Native / Flutter | 0% | 前端要重写 |
| 原项目的方式（WebView + Java Bridge） | 中 | 你已经有参考实现，但工作量大 |

强烈推荐 Capacitor。理由：你的前端已经是 Web SPA，Capacitor 只是给它套一个 Android 壳；需要原生能力（相机、文件、推送）时再加插件。这比原项目"Java 写 60 个类加 JS Bridge"的做法轻一个数量级。

## 四、推荐技术栈（Windows 优先版）

### 4.1 保留 / 替换 / 删除一览

| 层 | 原项目 | 你的项目 | 理由 |
| --- | --- | --- | --- |
| 后端框架 | FastAPI 0.141 | 保留 | 学习价值高，生态好 |
| ORM | SQLAlchemy 2.0 async | 保留 | async 是现代做法 |
| 迁移 | Alembic | 保留 | 必须学 |
| 校验 | pydantic 2 | 保留 | FastAPI 默认 |
| 鉴权 | PyJWT + Argon2 | 保留 | 自己实现一遍收获很大 |
| 数据库 | PostgreSQL 16 | 保留 | 一条 Docker 命令就有 |
| 向量检索 | Milvus 2.6 + etcd | 换 pgvector | 省掉两个容器、3 GB 内存 |
| 缓存/额度 | Redis 7 | 先不要 | 阶段 1-4 用不到；额度表直接用 PG，需要时再加 |
| 对象存储 | MinIO | 换本地目录 | 开发期用 pathlib 就够，以后再说云 OSS |
| LLM 接入 | langchain-deepseek | 换 httpx 直连 | 少两个依赖，流式就是 SSE |
| MCP 服务 | Node + Express | 删除 | 工具调用直接写在 FastAPI 里 |
| Mock 政务 API | Node + Express | 删除 | 种子数据直接写进 PG |
| 前端 | Android WebView + 原生 JS | Vite + React + TypeScript | 就业价值最高 |
| 样式 | 手写 CSS | Tailwind CSS | 开发速度快 |
| 数据请求 | OkHttp 手写网关 | TanStack Query | 缓存/重试/失效自动处理 |
| 桌面壳 | 无 | Tauri（或 pywebview） | 见 3.3 |
| Android | Java + AG Connect + HMS | Capacitor（以后） | 复用前端 |
| 部署 | Nginx + lego + 27 个脚本 | 1 份 docker-compose.yml | 个人项目不需要灰度/候选/证书自动化 |
| 脚本 | PowerShell 10 个 | 2-3 个 或 Makefile | 只留启动/迁移/测试 |

### 4.2 前端框架怎么选

| 选项 | 上手难度 | 就业价值 | 建议 |
| --- | --- | --- | --- |
| React + Vite + TS | 中 | 最高 | 推荐，思维方式最通用 |
| Vue 3 + Vite + TS | 低 | 高（国内尤其） | 如果想更快出成果 |
| 继续用原生 JS | 最低 | 低 | 可先把原项目 SPA 搬到浏览器跑通找感觉，但不建议作为最终形态 |

折中做法：第一阶段先用原生 JS 把原项目的 `portal-app-v2.js` 改造成浏览器版跑通（1-2 天，快速建立信心），第二阶段再用 React 重写。这样你能直观感受到框架解决了什么问题。

### 4.3 最终容器数量对比

| | 原项目 | 你的项目 |
| --- | --- | --- |
| 容器 | PostgreSQL、Redis、etcd、MinIO、Milvus、API、Worker、MCP、Mock API，共 9 个 | PostgreSQL 加 pgvector、API，共 2 个 |
| 内存上限 | 约 8.2 GB | 约 1 GB |
| 仓库体积 | 62.8 MB | 预计小于 5 MB |

## 五、从原项目里该删掉什么

因为你是从零搭建、不是 fork，所以更准确的说法是：原项目里哪些东西不要学。

| 不要学的部分 | 原因 |
| --- | --- |
| 整个 `android/` 模块（含 59.9 MB MetaStudio 资产） | 你用 Web 前端加 Capacitor，Java 那套用不上 |
| 华为 MetaStudio / 视觉 / HMS 导航 | 你没有华为账号，且复杂度极高（视觉测试 3,172 行） |
| 团队 RAG 加 DashScope 付费导入 | 个人项目不需要，而且要花钱 |
| 材料 DOCX Worker（LibreOffice + Qwen VL） | 需要 1.5 GB 镜像；想保留类似功能就用纯 python-docx 模板填充 |
| 4 份 compose + `deploy/` 27 个脚本 + Nginx/lego | 个人项目 docker compose up 就够了 |
| `repositories.py` 一个文件 3,589 行的写法 | 从第一天就按聚合拆成多个文件 |
| `coordinators.py` 一个文件 2,698 行的写法 | 同上 |
| 60 多个环境变量 | 一开始 10 个以内 |
| MCP / Mock API 两个 Node 服务 | 合并进 FastAPI |

要重点学的部分（这才是你想要的）：

| 必须学的部分 | 位置 |
| --- | --- |
| BCE 分层思路 + 端口抽象 + 组合根 | `domain/`、`application/ports.py`、`infrastructure/runtime.py` |
| 业务策略与状态机 | `domain/policies.py` |
| 幂等实现 | `IdempotencyCoordinator` |
| 乐观锁版本号 | `Application.version` |
| 审计只追加 | `ApplicationEvent` / `BusinessAuditEvent` |
| 溯源强制策略 | `GroundedAnswerPolicy` |
| 受限规则 DSL（不用 eval） | `domain/policies.py` 的资格引擎 |
| 缓存键设计（含 dataset 版本隔离） | `cache.py` 的 `key_for` |
| 就绪检查设计 | `main.py` 的 `/health/ready` |

## 六、从零搭建的学习路线（7 个阶段）

每个阶段都有明确产出和验收方式。不要跳阶段，尤其是阶段 3。

### 阶段 0：准备（3-5 天）

- 选定领域，画出 ER 图（实体 + 关系），纸笔或 draw.io 就行。
- 装好：Python 3.13、Node 20、Docker Desktop、VS Code、Git。
- 起一个带 pgvector 的 PostgreSQL 容器。
- 读一遍原项目的 `docs/business-design.md`（17 KB），只看状态机那几段。

产出：一张 ER 图，加一份"我这个系统有几种角色"的清单。

### 阶段 1：最小闭环（1 周）

- FastAPI + SQLAlchemy async + Alembic + Pydantic 跑通。
- 建 1 张业务表（比如"可申领物品"）。
- 写 3 个接口：列表、详情、创建。
- 前端：Vite + React 起一个页面，调通列表接口。
- 第一个 Alembic 迁移。

验收：浏览器里能看到列表，能新增一条数据，重启后数据还在。

### 阶段 2：用户与角色（1 周）

- 账号表 + Argon2 口令哈希。
- JWT 签发与校验 + refresh token（只存哈希）。
- 角色：申请人 / 审批人 / 管理员。
- FastAPI 依赖注入做权限校验。

验收：三个角色登录后能看到不同菜单；越权访问返回 403。

### 阶段 3：主流程，最有价值的一阶段（2 周）

- 申请状态机（草稿 → 提交 → 审批中 → 通过/驳回 → 完成）。
- 乐观锁版本号：提交旧版本返回 409。
- 幂等键：同一个 Idempotency-Key 加相同载荷返回原结果，不同载荷返回冲突。
- 审批人认领（条件更新，并发只有一人成功）。
- 事件表 + 审计表，只追加。

验收：写脚本并发提交同一个幂等键，验证只产生一次副作用；并发认领只有一个成功。

这一阶段做的两件事（幂等加乐观锁）看着抽象，但正是这套项目最值钱的部分。做完这一阶段，你对"后端系统为什么这么设计"的理解会有一个台阶式的提升。

### 阶段 4：文件上传（1 周）

- 上传到本地目录（后期换对象存储）。
- 限制类型和大小、算 SHA-256、存元数据。
- 下载走鉴权接口，不暴露物理路径。

验收：上传一个文件，数据库里能查到哈希；越权下载返回 403。

### 阶段 5：审批工作台（1-2 周）

- 审批人待办列表。
- 认领 → 通过 / 驳回 / 要求补充。
- 时间线展示。
- 管理员后台：事项配置、审计、指标。

验收：完整走完一条申请的端到端流程，时间线正确。

到这里业务骨架就完整了。先别急着做 AI，把上面五步做扎实。

### 阶段 6：AI 助手（2 周）

顺序很重要：

1. 先做知识库：管理员上传文档 → 切分 → embedding → 入库。
2. 再做检索：查询 → 向量检索 → 返回来源。
3. 再做回答：把问题和来源交给 LLM，必须要求它引用来源。
4. 最后做流式：SSE 逐字返回。
5. 加上溯源策略：没有来源就不调模型。

验收：提问返回的答案带来源；问知识库里没有的东西时明确说未找到。

### 阶段 7：桌面壳 + Android（按需）

- Tauri 或 pywebview 打包成 .exe。
- 之后用 Capacitor 打包 APK。

## 八、容易走弯路的九个点

1. 别先做 AI。它是最好做的部分，先把业务骨架做扎实，AI 最后加。
2. 别一上来就上微服务、消息队列、K8s。个人项目单进程加一个数据库足够，加这些只会让你卡在运维上。
3. 别照抄 4 层分层的全部形式。个人项目可以简化成 3 层，但 `ports.py` 端口抽象加 `runtime.py` 组合根这两个要保留，它们决定了你将来换技术时痛不痛。
4. 别把 repository 写成 3,589 行的一个文件。一个聚合一个文件，从第一天就这样。
5. 别一开始就搞 60 个环境变量。10 个以内，用到再加。
6. 别用 Milvus。pgvector 足够，还省 3 GB 内存。
7. 浏览器端不要用原有的 JS Bridge 模式。Bridge 是给 WebView 用的，浏览器直接 fetch。
8. Token 存 httpOnly Cookie，不要存 localStorage。前者 XSS 偷不到，这是个很实际的加分点。
9. 幂等和乐观锁一定要亲手实现一遍。抄代码学不到东西，这两个是最有价值的部分。

## 九、建议的执行顺序（接下来两周做什么）

| 时间 | 做什么 |
| --- | --- |
| 第 1 天 | 定领域（建议设备与场地申领预约），画 ER 图，装环境 |
| 第 2-3 天 | 起 PG 加 pgvector 容器；FastAPI 骨架，第一个接口能返回 JSON |
| 第 4-5 天 | Vite + React 起前端，调通第一个接口，配好 CORS |
| 第 6-7 天 | 加 SQLAlchemy + Alembic，第一张表落库 |
| 第 2 周 | 用户与角色（阶段 2） |

两周后你会有一个能跑的最小全栈骨架，然后再进入阶段 3（状态机加幂等），那是真正的分水岭。

原项目怎么用：把它当成一本参考书，不要改动它。遇到具体问题时去翻对应文件（比如"幂等到底怎么写"就去读 `coordinators.py` 里的 `IdempotencyCoordinator`）。你亲手写一遍，再对照它的实现，收获最大。

## 十、一句话总结

领域选「设备与场地申领预约」，平台走"浏览器 → Tauri → Capacitor"三步，技术栈砍到 FastAPI + PostgreSQL（加 pgvector）+ React 这四个东西。
