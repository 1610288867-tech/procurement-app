## 1. 预算预留与释放（并发核心）

**规则**：申请提交时从部门预算"预留"这笔钱；驳回或撤回时释放；付款成功时按**实付金额**转为"已花"，
并**显式释放预留与实付之间的差额**。

```
可用余额 = amount_total − amount_reserved − amount_spent
提交        → RESERVE(申请金额)
驳回/撤回   → RELEASE(申请金额)
付款成功    → SPEND(实付金额) + RELEASE(预留 − 实付)
```

**关键**：绝不"先查余额再更新"。两个人同时提交必须只有一个成功。

```sql
UPDATE budgets
   SET amount_reserved = amount_reserved + :amount
 WHERE id = :budget_id
   AND amount_total - (amount_reserved + amount_spent) >= :amount;   -- 受影响行数为 0 = 预算不足
```

**三条必守**：

- 守卫条件**整个写在 `where()` 里**——在 Python 里做减法再比较会抛
  `TypeError: Boolean value of this clause is not defined`
- 预留必须带 `request_id`，并给 `budget_transactions` 加 `UNIQUE(request_id, kind)`，
  否则**重试会重复扣钱**
- 每次变动都写流水（`RESERVE` / `RELEASE` / `SPEND`），否则事后对不上账

**超预算的口径（2026-10-03 定稿）**：

**可用预算不足 → 直接 422，不自动放行、不生成"预算调整"流程。**

- 预算调整是**独立的管理员/财务操作**；调整完成后由申请人**重新提交**；
- **不采用"超预算强制加一级审批"** —— 那会让"预算不足"这个事实被审批意见掩盖掉；
- 内控指引第 7 号第六条要求的正是"**先履行预算调整程序**，
  由具备相应审批权限的部门或人员审批后，再行办理请购手续"，与这条一致。

> **本条在 M7 落地**（M7 之前 `budget_id` 恒为 NULL，没有预算可查）。
> 提交/预留走**同一条条件更新**，受影响行数为 0 就说明预算不够 → 422。

**"计划外"的口径（2026-10-03 定稿，M7 实现）**：

**该部门 × 品类 × 年度压根没有预算行 → 同样直接 422**（提示先配置预算），
不按"没配预算就放行"处理。

- 判据是「**这条预算存不存在**」，而不是金额大小：没配预算就等于**没有控制依据**，
  放行等于把"计划外采购"变成一条无人知晓的通道；
- 年度取**提交时刻所在年度**（UTC），与预算唯一键 `(department_id, year, category_id)` 对齐；
- 与内控指引第六条一致 —— "超预算和**预算外**采购项目，应先履行预算调整程序"，
  所以"超预算"与"没预算"走**同一个处置**：先配 / 调预算，再由申请人重新提交；
- 这是**失败关闭**（fail-closed）的取舍：宁可挡住并说清原因，也不留一条静默的豁免路径。

## 2. 按金额分级审批（动态多级）

**规则**：金额决定审批层级，规则存在**采购品类**的 `approval_policy` 上。
**改规则不改代码**——这是整个 M6 存在的意义。

对照表见 `金额-审批链对照表.md`：500 / 5,000 / 50,000 / 200,000 元 → **1 / 2 / 4 / 5** 级。

**两条必须做对的**：

- 规则里的路径名是 **`amount_fen`**（不是 `amount`）。写错**不会报错**，只会让规则静默失效、
  **申请以更低的审批层级被批准**
- 策略必须有**零阈值兜底步骤**，否则某些金额区间会算出**空审批链 = 无人审批直接通过**

## 3. 三家比价

**规则**：金额超过比价线的采购，必须有至少 **3 家有效报价**才能定标。

- 报价状态：`DRAFT / SUBMITTED / EXPIRED / SELECTED`
- "有效" = `SUBMITTED` 且未过期（`valid_until >= now()`）
- 不足时返回 **422** 并说明还差几家（不是简单说"不满足条件"）
- 定标后：选中者 `SELECTED`，其余 `NOT_SELECTED`，主单 `SOURCING → AWARDED`

**职责分离口径（2026-10-03 定稿：v1 不分离）**：

v1 **由同一个采购角色完成询价与定标**，不新增第二个审批角色 ——
不为职责分离把流程复杂度抬高。改由**四条硬控制**兜底：

1. 至少 **3 家**有效报价；
2. 供应商**本身合格**（未停用、资质未过期）；
3. 报价**完整**（状态与有效期都满足）；
4. 定标结果记录**实际成交单价**，并据此生成采购订单。

> 这是**有意识的取舍**：制度范本的不相容岗位第（二）条要求"询价与核价、确定供应商"分离，
> 本项目在此让位于"≥3 家比价 + 留痕"这组补偿性控制。
> 若将来要分离，就在 M10 加一个"定标确认"角色/节点，而不是现在预留空壳。

## 4. 供应商准入

**规则**：只能选**合格且未禁用**的供应商。

- 资质有效期 `qualification_expires_at` 过期即不可选
- **用查询时过滤实现，不用定时任务** —— 简单且不会出现状态漂移
- 禁用要留 `disabled_reason`（审计需要）

**可见性口径（2026-10-03 收口）**：

- `/api/v1/suppliers` **要求登录**，且**过滤条件写死**（只返回合格项）。
  原先它完全公开、并带一个客户端可控的 `only_active` 参数（传 `false` 即可索取已停用供应商）——
  违反内控指引第 7 号第七条（合格清单是采购/管理职能的资产）与 OWASP 最小权限。
- 需要看**全部**（含停用、含资质过期）请走 `/api/v1/admin/suppliers`，那里要求 `ADMIN`。
- **申请人不需要浏览供应商主数据**：选谁是采购的职权（制度范本不相容岗位第（二）条
  "询价与核价、确定供应商"）。将来若要做"内部目录"（已谈好价格的可买清单），
  那是**另一个只读视图**，不是把供应商主数据摊开。

**预算可见性口径（2026-10-03 收口）**：

- `GET /api/v1/budgets/mine` **要求登录**，且**部门只从登录态推导**，客户端不能指定。
  它原来是 M2 留下的公开接口 + `department_id` 查询参数（传任意部门就能看别人有多少钱）。
- **没有部门的账号返回空列表**（他本来就不属于任何部门）；要看全部走 `/api/v1/admin/budgets`。
- 预算是财务数据，内控指引第 7 号把"审核采购预算"列为付款前置，所以它不该匿名可读。

**预算看板口径（2026-10-04 补，M7）**：

`GET /api/v1/budgets` 与 `/api/v1/budgets/transactions` 要求 **`FINANCE` 或 `ADMIN`**，**只读**。

- **"看钱"与"改钱"是两个可以分别收紧的动作**：看板让财务看到部门 × 品类的
  总额 / 已预留 / 已花 / 可用与流水；而**改预算仍然只走 `POST /api/v1/admin/budgets`（仅 ADMIN）**。
  把管理员那个接口的权限放宽成"财务也能看"，等于连"改"一起放开了 —— 这是不做的理由。
- 看板行里的部门名与品类名由**后端一起带出**：财务没有"列出全部部门 / 品类"的权限
  （那两条是管理员接口），不该为了一个只读页面把口子开大。

**主数据可见性口径（2026-10-03 收口完毕）**：

| 接口 | 现在 | 为什么 |
| --- | --- | --- |
| `/api/v1/suppliers` | 要求登录，只返回合格项 | 合格清单是采购/管理职能的资产 |
| `/api/v1/departments` | 要求登录，只返回启用中的 | 部门树是内部信息；`only_active` 客户端参数已收掉 |
| `/api/v1/categories` | 要求登录，只返回启用中的 | 同上 |
| `/api/v1/categories/{id}` | 要求登录 | **它会把整份 `approval_policy` 带出来**（金额阈值 + 各级角色）—— 那是"多少钱需要谁批"的内控结构信息 |
| `/api/v1/budgets/mine` | 要求登录，部门只从登录态取 | 预算属财务数据 |
| `/api/v1/budgets`、`/budgets/transactions` | 要求 **`FINANCE` / `ADMIN`**，只读 | 看钱与改钱分开（见上面「预算看板口径」） |
| `/api/v1/admin/*` | 要求 `ADMIN` | 管理端 |

**统一判据**：这些接口只在**登录后的界面**里用得到，公开没有任何收益 —— 所以一律要求登录。
需要看"全部（含停用/过期）"的，走 `/api/v1/admin/*`。**前端隐藏入口不等于权限**，
这一层只是少暴露一点内部结构；真正的边界始终在后端。

## 5. 禁止拆分申请（第一版只做 warning）

**规则**：同一申请人、同一品类、短期内拆成多笔小额申请来规避审批，是典型舞弊手法。

- 检测口径：同部门 + 同品类 + 最近 7 天 + 状态未终结的申请总额
- **第一版只 warning，不拦截** —— 它是采购系统里很有代表性的风控规则，但不影响主链跑通
- 归入"暂缓清单"：M10 之后按需

## 6. 三单匹配（最经典）

**规则**：付款前比对三份单据。

| 单据 | 来源 | 关键字段 |
| --- | --- | --- |
| 采购订单 PO | 采购专员下单 | 数量、单价、金额 |
| 收货单 GR | 收货人验收 | 实收数量 |
| 发票 Invoice | 供应商开具 | 发票号、金额、税额 |

**匹配逻辑（第一版按"订单级"粒度）**：

1. 收货数量 ≤ 订单数量（超收要人工确认）
2. 发票金额与订单金额的差异在容差内：**`max(金额 × 2%, 50 元)`**
   —— 比例和绝对值**取较大者**，否则小额单永远匹配不上
3. 发票供应商与订单供应商一致

**粒度定死**：发票金额与收货数量都**求和**后再比（多张发票 / 多张收货单）；
明细行级匹配进"暂缓清单"。

> **"订单金额"是匹配基准，不是申请金额**（2026-10-02 定死口径）：
> `purchase_orders.amount = Σ(订单明细行金额) = Σ(单价 × 数量)`，由后端按明细重算。
> 询价场景取**定标报价单价**（通常低于申请单价），直采场景取**实际成交单价**
> （默认等于申请单价，有议价取议价后价）。所以订单总额与申请总额不一致**是正常的**：
> 付款按实付结转，预留与实付的差额显式释放（见规则 1）。

**返回"问题列表"而不是布尔值** —— 前端拿它渲染三列对比页的差异高亮。
第一版做"**拒绝 + 返回问题列表**"，不做"挂起 + 异常任务"。

## 7. 收货完成后才能付款

**规则**：`RECEIVED` 之前的申请不允许创建付款单。

**在状态机里强制**（`RECEIVED` 之前没有通向 `INVOICED` 的转移），**不要靠前端按钮控制**。

**财务角色口径（2026-10-03 定稿：不拆出纳）**：

`FINANCE` **同时负责财务审核与付款执行**，不新增"出纳"角色。
付款本身仍必须**四道条件全满足**才允许：

```
审批完成 → 订单/收货/发票条件满足 → 三单匹配通过 → 才可支付
```

> 这是**有意识的取舍**：制度范本不相容岗位第（五）条要求"付款的申请、审批与执行"分离。
> 本项目让位于"三单匹配 + 状态机强制"这组补偿性控制 —— 三单匹配本身就是最强的付款校验。

## 8. 金额一律整数「分」

**规则**：数据库 `BIGINT`，Python `int`，**禁止 float**。

- 界面显示"元"，传输和存储全程"分"
- "元 → 分"的转换**只在一个文件里发生**（前端 `src/lib/money.ts`，后端只在边界层做一次）
  —— 转换写错 1000 倍是这类系统最经典的线上事故
- 自查命令（应无输出）：`Select-String -Path backend\app\**\*.py -Pattern "Float|: float"`

> **这一条是后来补的，而且是"整整一类要求"，不是细节。**
> 起因：实跑发现**申请人可以批掉自己的申请**。回去查外部依据才发现，
> 法规与真实系统都把"不相容职务分离"当作采购内控的骨架，而本文档最初 8 条里**一条都没有**。
> 完整的依据、原文引用与逐条对账见 [`采购内控对照.md`](采购内控对照.md)。

### 依据（都是可点开核对的原文）

| 出处 | 关键原文 |
| --- | --- |
| 财政部《企业内部控制应用指引第 7 号——采购业务》第五条 | **"企业除小额零星物资或服务外，不得安排同一机构办理采购业务全过程"** |
| 上市公司《采购与付款内控制度》范本第五条 | 不相容岗位至少包括：**（一）请购与审批；（二）询价与核价、确定供应商；（三）采购合同的订立与审核；（四）采购、验收与相关会计记录；（五）付款的申请、审批与执行** |
| Oracle Procurement | **Prohibit User Self-Approval** —— 把"提交人"从审批链里 **skip 掉**，任务顺延给下一人 |
| OWASP 授权清单 | **最小权限**、**默认拒绝**、**每个请求都校验**；客户端校验只可为体验，**绝不能作为放行依据** |

### 本项目的落地状态（逐条，带代码位置）

| 不相容岗位 | 本项目 | 状态 |
| --- | --- | --- |
| 请购与审批 | **已落地（2026-10-03 修复）**：建链时剔除提交人；或签任务另在待办查询与决定接口三重拦截 | ✅ |
| 询价与确定供应商 | **v1 不分离**（同一采购角色），以"≥3 家有效报价 + 供应商合格 + 报价完整 + 记录成交单价"兜底 | 🟡 已定稿取舍（见第 3 条） |
| 合同订立与审核 | 项目无合同环节 | ⚪ 范围外 |
| 采购、验收与会计记录 | 采购（`PROCUREMENT`）／收货（`RECEIVER`）／记录（系统自动）三方分离 | ✅ |
| 付款的申请、审批与执行 | **v1 不拆出纳**：`FINANCE` 同时审核与付款，由"三单匹配 + 状态机"兜底 | 🟡 已定稿取舍（见第 7 条） |

### 本项目的硬约束（写入即生效，改代码时不得绕过）

1. **提交人不得审批自己的申请。** 落点是**三层**，缺一层就有口子：

   | 层 | 位置 | 挡的是 |
   | --- | --- | --- |
   | ① 建链时 | `_plan_tasks` → `domain/approval_engine.exclude_requester` | **会签**（预分配人）与"该级只剩提交人"（→ 提交时 422 `SELF_APPROVAL_NOT_ALLOWED`） |
   | ② 待办查询 | `ApprovalRepository.list_todo` 里 `PurchaseRequestRecord.requester_id != actor_id` | **或签**：或签任务 `assignee_id` 是 NULL、只按角色可见，①挡不住它 |
   | ③ 决定/认领 | `decide` / `claim` 的 `NOT EXISTS(该申请是 actor 提的)` + `_assert_can_act` 的 403 | 直接用 id 打接口（Postman 绕过界面） |

   判定本身是 `domain/` 里的**纯函数 + 失败关闭**（`is_eligible_approver` / `exclude_requester`）。
2. **可见范围外 → 404；可见但无权 → 403。** 既有约定，SoD 的拒绝也归 403。
3. **被拒的尝试也要留痕** —— 见下面第 10 条。

### 要一起记住的两条边界

- **不要引入"发起人自选审批人"。** 国内某些平台提供这个功能，但它**本身就是绕过职责分离的口子**
  （自己挑一个会批的人）。本项目不提供。**2026-10-03 定稿：也继续不做"后端权限清单下发"** ——
  8 个角色规模下，菜单按 `me.roles` 前端自判够用；后端始终是最终权限边界。
  角色/权限复杂度明显上升时再改。
- **不做委托/转办（2026-10-03 定稿）。** 审批任务只允许**符合候选条件**的审批人认领或处理；
  不实现转派、代理、委托、审批人替换。将来要做时，一次把
  "**转派后重新校验权限、角色、范围、历史责任链**"设计进去
  （外部实现 SecureCICD 把 `reassigned` 与自审并列为三类拒绝之一）。

## 10. 授权失败要留痕（2026-10-03 定稿）

**规则**：对**越权访问、越级审批、无权限操作**记录安全/审计事件。

**最小字段**：`actor`、`action`、`resource`、`timestamp`、`result=DENIED`、`request_id`（关联 ID）。

**一条硬边界**：**不要把这些失败请求伪装成业务 `request_events`。**

| | `request_events`（既有） | 授权失败事件（本规则） |
| --- | --- | --- |
| 记什么 | **成功的业务动作**（创建/提交/审批通过/驳回…） | **被拒绝的尝试** |
| 用途 | 申请人看的时间线 | 安全审计与排查 |
| 归属 | 挂在某张采购申请上 | 与具体业务单**无关**（可能压根没找到资源） |

所以两者**分开存**：审计事件不带 `request_id`（业务申请），只带 `request_id`（请求关联 ID）。
否则时间线会被"谁试图越权"刷屏，而申请人**不该看到**这些内容。

> **落地时机**：M8（回归验收）或 M9 之后补。当前状态是"只有成功动作留痕"，
> 已记入 `PROGRESS.md` 的待修表。**修之前不要在时间线里造审计事件。**

## 附：三条"静默失败"约束（违反不会报错，只会算错）

这三条和上面 10 条同等重要，但危险得多——**出错时没有任何异常，只有错误的结果**：

| 约束 | 违反的后果 |
| --- | --- |
| **审批链不许为空** | 某金额区间的申请无人审批直接通过（合规失控） |
| **预留与实付的差额必须显式释放** | 差额永久挂在 `amount_reserved`，可用额度虚低、账目对不上 |
| **权限范围必须写进 `WHERE`** | 写成"查出来再判断能不能看"，漏一处就是越权，且不会报错 |

所以这三条必须靠**验收项主动去撞**，而不是等它自己暴露。见 `PROGRESS.md`。

> **第 9 条（职责分离）也属于这一类**：自审自批**不会报任何错**，账面完全正常，
> 只是内控失效。它同样得靠验收项去撞。
