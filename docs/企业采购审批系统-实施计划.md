## 前置约定：本计划采用的技术基线

| 项 | 选型 | 备注 |
| --- | --- | --- |
| 后端 | FastAPI + SQLAlchemy 2.0 async + Alembic + Pydantic v2 | 全部保留原项目选型 |
| 数据库 | PostgreSQL 16 + pgvector | 用 `pgvector/pgvector:pg16` 镜像，阶段 8 之前用不到 vector |
| 前端 | React 18 + Vite + TypeScript + Tailwind + TanStack Query + React Router | 就业价值最高的组合 |
| Python 包管理 | uv（推荐）或 venv + pip | uv 快很多，但 pip 也完全可以 |
| Node 包管理 | npm | 不用换 |
| 容器 | **只有 db 一个**，API 和前端本地直跑 | 开发期效率最高 |
| 金额 | 一律整数「分」 | 见领域设计 5.8 |
| 测试 | pytest + pytest-asyncio + httpx AsyncClient | |
| 工期基准 | 每周投入 10-15 小时 | 全职可压缩到 40% |

**如果你更想用 Vue 或不想碰 TypeScript**，替换成本很低——本计划里前端相关的部分改一下写法即可，后端部分完全不变。

## 一、计划总览

### 1.1 里程碑一览（M0–M10 共 11 个阶段）

| 阶段 | 主题 | 工期 | 前置 | 核心产出 | 关键验收 |
| --- | --- | --- | --- | --- | --- |
| M0 | 准备与设计定稿 | 3-5 天 | — | ER 图、规则清单、环境可跑 | 连得上数据库、空测试通过 |
| M1 | 骨架贯通 | 1 周 | M0 | 一条数据从库到页面的完整链路 | 浏览器能看到并新增数据 |
| M2 | 主数据 | 1 周 | M1 | 品类、供应商、部门、预算 | 管理页能配一个品类 |
| M3 | 账号与权限 | 1 周 | M2 | 7 角色 + JWT + 权限依赖 | 越权访问返回 403 |
| M4 | 采购申请 | 1.5 周 | M3 | 草稿 CRUD、明细行、提交与撤回 | 能建、能改、能提交 |
| M5 | **审批引擎** | 2 周 | M4 | 动态审批链、待办、通过/驳回、策略快照 | 500/5000/50000/200000 元 → 1/2/4/5 级 |
| M6 | **预算并发预留** | 1 周 | M5 | 预留、释放、转已花、流水 | 并发只有一笔成功 |
| M7 | 附件与时间线 | 1 周 | M6（与 M6 可互换） | 上传下载、事件流界面 | 越权下载返回 403 |
| M8 | 履约链 | 2 周 | M7 | 询价→定标→订单→收货→发票→三单匹配→付款 | 全链路走通，超容差被挂起 |
| M9 | AI 制度助手 | 2 周 | M5（不依赖 M8，可提前） | 知识库、检索、引用、流式 | 无来源不回答 |
| M10 | 桌面壳与移动端 | 1 周 | M9 | .exe 与 APK | 双击能打开 |

**各阶段相加约 14.5 周，加 M0 的 3-5 天约 15 周；再算上 M5/M6 各留 1 周缓冲，按 17 周排比较现实**（每周 10-15 小时）。

> 口径统一说明：本文按 11 个阶段（M0–M10）计。早期文档里写过的"约 13-14 周"是按无缓冲的理想值算的，容易低估，以本表相加结果为准。

M5 和 M6 是整个项目的分水岭，建议这两阶段各留出至少 2 周缓冲，不要赶。

### 1.2 阶段依赖关系

```
M0 --> M1 --> M2 --> M3 --> M4 --> M5 --> M6 --> M8 --> M9 --> M10
                                          \    /
                                           M7

说明：
- M0-M5 必须严格串行，后者依赖前者的表和接口。
- M6（预算）和 M7（附件）互不依赖，可以交换顺序或并行。
- M8 必须等 M6 和 M7 都完成（付款要预算、定标要附件）。
- M9、M10 完全独立。**M9 只依赖 M-01 基础设施，不依赖履约链**，所以它可以放在 M5 之后的任何位置：想在写 M8 之前换换脑子，就提前插进来做。
- **M5 与 M6 各留 1 周缓冲**：这两阶段是全项目唯一"做不完就没有价值"的地方，挤时间是本末倒置。
```

#### 实施步骤

**第 1 步：建仓库骨架**


`.gitignore` 至少包含：`__pycache__/`、`.venv/`、`node_modules/`、`.env`、`backend/uploads/`、`*.pyc`。

**第 2 步：写 `docker-compose.yml`，只起数据库**

```yaml
services:
  db:
    image: pgvector/pgvector:pg16
    environment:
      POSTGRES_DB: procurement
      POSTGRES_USER: app
      POSTGRES_PASSWORD: devpassword
    ports: ["5432:5432"]
    volumes: ["pgdata:/var/lib/postgresql/data"]
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d procurement"]
      interval: 5s
      retries: 20
volumes:
  pgdata:
```

起库并验证：

```powershell
docker compose up -d
docker compose exec db psql -U app -d procurement -c "select version();"
```

**第 3 步：搭后端空壳**

```powershell
cd backend
py -3.12 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip -i https://pypi.tuna.tsinghua.edu.cn/simple
pip install fastapi "uvicorn[standard]" sqlalchemy asyncpg alembic pydantic pydantic-settings -i https://pypi.tuna.tsinghua.edu.cn/simple
pip install pytest pytest-asyncio httpx -i https://pypi.tuna.tsinghua.edu.cn/simple
pip freeze > requirements.txt
```

**用 `py -3.12`，不是 `py -3.13`**——本机只装了 3.12.2（见 M0 的环境实测）。**`-i` 镜像源也不是可选项**：实测直连 `pypi.org` 会挂起（`pip download` 跑满 3 分钟无任何输出），不换源这一步会耗掉你一整个晚上。

把镜像配成全局的，比每条命令都带 `-i` 省事：

```powershell
python -m pip config set global.index-url https://pypi.tuna.tsinghua.edu.cn/simple
python -m pip config set global.timeout 30
```

写一个只有 `/health/live` 的 `main.py`，跑起来访问 `http://127.0.0.1:8000/health/live`。

**第 4 步：搭前端空壳**

```powershell
cd frontend
npm create vite@latest . -- --template react-ts
npm install
npm install react-router-dom @tanstack/react-query
npm install -D tailwindcss @tailwindcss/vite
npm run dev
```

**两处和早期写法不同，按这里来**：

1. **不要装 `axios`**。M1 的 `client.ts` 是 `fetch` 封装（原生够用，少一个依赖），装了就一定会有人顺手用上，于是项目里同时存在两套 HTTP 客户端。
2. **Tailwind 用 `@tailwindcss/vite` 插件**，不再需要 `postcss` / `autoprefixer`，也**没有 `npx tailwindcss init -p` 这一步**——本机是 Node 24，装到的会是 Tailwind v4，配置方式已经变了：在 `vite.config.ts` 里加 `tailwindcss()` 插件，然后在 CSS 顶部写 `@import "tailwindcss";` 即可。

**第 6 步：写仓库 `repositories/catalog_repo.py`**

```python
from sqlalchemy import select
from sqlalchemy.ext.asyncio import AsyncSession

from app.infrastructure.records.catalog import SupplierRecord


class CatalogRepository:
    def __init__(self, session: AsyncSession) -> None:
        self.session = session

    async def list_suppliers(self, only_active: bool = True) -> list[SupplierRecord]:
        statement = select(SupplierRecord).order_by(SupplierRecord.name)
        if only_active:
            statement = statement.where(SupplierRecord.active.is_(True))
        return list((await self.session.scalars(statement)).all())

    async def create_supplier(self, *, name: str, code: str) -> SupplierRecord:
        record = SupplierRecord(name=name, code=code)
        self.session.add(record)
        await self.session.flush()
        return record
```

**注意 `flush()` 不是 `commit()`**：仓库层不决定事务边界，提交由上层用例决定。这样多个仓库操作才能处于同一个事务里。

**第 7 步：写路由 `boundaries/http/catalog.py`**

```python
from fastapi import APIRouter, Depends
from pydantic import BaseModel, Field
from sqlalchemy.ext.asyncio import AsyncSession

from app.database import get_session
from app.infrastructure.repositories.catalog_repo import CatalogRepository

router = APIRouter(prefix="/api/v1/suppliers", tags=["供应商"])


class SupplierIn(BaseModel):
    name: str = Field(min_length=1, max_length=200)
    code: str = Field(min_length=1, max_length=64)


class SupplierOut(BaseModel):
    id: str
    name: str
    code: str
    active: bool


def to_out(record) -> SupplierOut:
    return SupplierOut(
        id=str(record.id), name=record.name, code=record.code, active=record.active
    )


@router.get("", response_model=list[SupplierOut])
async def list_suppliers(session: AsyncSession = Depends(get_session)):
    records = await CatalogRepository(session).list_suppliers()
    return [to_out(record) for record in records]


@router.post("", response_model=SupplierOut, status_code=201)
async def create_supplier(payload: SupplierIn, session: AsyncSession = Depends(get_session)):
    record = await CatalogRepository(session).create_supplier(
        name=payload.name, code=payload.code
    )
    await session.commit()
    return to_out(record)
```

**第 8 步：`app/main.py` 挂路由**（外加统一错误处理与 request_id）

```python
import uuid

from fastapi import FastAPI, Request
from fastapi.responses import JSONResponse

from app.boundaries.http import catalog
from app.config import get_settings

settings = get_settings()
app = FastAPI(title="采购审批系统")

    request.state.request_id = request.headers.get("X-Request-Id") or uuid.uuid4().hex[:12]
    response = await call_next(request)
    response.headers["X-Request-Id"] = request.state.request_id

            "message": exc.message,
            "request_id": request.state.request_id,
        }},
    )

    return {"status": "ok"}
```

**统一错误响应体不是可选项，因为前端已经在依赖它了。** M1 的 `client.ts` 读的是 `body?.error?.message`——如果后端这时候返回的还是 FastAPI 默认的 `{"detail": "..."}`，那个 `??` 后面的兜底文案会永远生效，你就再也看不到真正的错误原因。**形状要在第一天定死**：

```json
{ "error": { "code": "BUDGET_INSUFFICIENT", "message": "预算不足", "request_id": "9f2c1a7b4e01" } }
```

`request_id` 同时放进响应头和响应体：出错时前端直接把它显示给用户（或写进 console），你在后端日志里搜这 12 个字符就能还原整条请求链路。12 位十六进制足够本地开发用，不必上 UUID4 全量。

**日志格式也要在第一天定死**，否则 `request_id` 只是响应头里一个没人用的字符串。约定：**每一条日志都必须带 `request_id`，并且用结构化的 key=value**（不要拼中文字符串）：

```python
# infrastructure/logging.py
import logging
import time

logger = logging.getLogger("procurement")


@app.middleware("http")
async def access_log_middleware(request: Request, call_next):
    started = time.perf_counter()
    response = await call_next(request)
    logger.info(
        "request method=%s path=%s status=%s request_id=%s duration_ms=%.1f",
        request.method, request.url.path, response.status_code,
        request.state.request_id, (time.perf_counter() - started) * 1000,
    )
    return response
```

三条约定：

1. **业务日志也带 `request_id`**（从 `request.state` 取），否则排查时串不起来。
2. **用 `%s` 占位而不是 f-string**——`logging` 是惰性格式化的，用 f-string 会白白付出字符串拼接成本。
3. **金额一律用"分"打印，并且字段名带 `_fen`**，避免日志里再出现一次单位混乱。

> **用 key=value 而不是 JSON，是刻意的**：目前只需要人肉 `Select-String` 日志，key=value 更易读，也不用引 `python-json-logger`。等你真的要把日志喂给采集系统时再换 JSON——那时只需要改这一个文件的 formatter。

**第 0 步：用 Vite 代理解决跨域，而不是靠 CORS**

这一步放在最前面，因为它能一次性消掉后面所有"跨域相关"的坑。`vite.config.ts`：

```ts
import react from "@vitejs/plugin-react";
import { defineConfig } from "vite";

export default defineConfig({
  plugins: [react()],
  server: {
    port: 5173,
    proxy: {
      // 前端仍然请求 /api/...，但由 Vite 转发到 8000，浏览器看到的始终是同源
      "/api": { target: "http://127.0.0.1:8000", changeOrigin: true },
    },
  },
});
```

**为什么强烈建议这么做**：

| | 用 Vite 代理（推荐） | 用 CORS 中间件 |
| --- | --- | --- |
| 浏览器视角 | 同源，没有跨域 | 跨域，靠响应头放行 |
| Cookie | 自动带上 | 要 `credentials: "include"` + 精确 origin，不能用 `*` |
| Android / Tauri 打包 | 换成真实 API 地址即可 | 要额外处理 `capacitor://` 之类的 origin |
| 出错表现 | 代理层直接报 `ECONNREFUSED`，一眼看出后端没起 | 浏览器 Console 报 CORS，容易被误判成后端 bug |

用代理之后，前端代码里的基址是空字符串（同源），**M3 引入 httpOnly Cookie 时不需要改任何前端请求代码**。

顺带说明：`app/main.py` 里那段 CORS 中间件**先不用加**。等到 M3 之后如果你想用 `http://127.0.0.1:8000/docs` 从别的源直接调接口，或者 M10 打包时前后端真的分居两个源，再按需加上——那时候你也已经知道该填哪个 origin 了。

**第 1 步：`src/api/client.ts`**

```ts
// 同源 + Vite 代理：不需要写死 8000，也不需要 credentials
const BASE = "";

async function request<T>(path: string, init: RequestInit = {}): Promise<T> {
  const response = await fetch(`${BASE}${path}`, {
    headers: { "Content-Type": "application/json", ...(init.headers ?? {}) },
    ...init,
  });
  if (!response.ok) {
    const body = await response.json().catch(() => ({}));
    const message = body?.error?.message ?? `请求失败：${response.status}`;
    const rid = body?.error?.request_id;
    throw new Error(rid ? `${message}（request_id: ${rid}）` : message);
  }
  return response.status === 204 ? (undefined as T) : response.json();
}

export type Supplier = { id: string; name: string; code: string; active: boolean };

export const api = {
  listSuppliers: () => request<Supplier[]>("/api/v1/suppliers"),
  createSupplier: (body: { name: string; code: string }) =>
    request<Supplier>("/api/v1/suppliers", {
      method: "POST",
      body: JSON.stringify(body),
    }),
};
```

**第一层：结构校验（Pydantic，能挡住"形状不对"）**

**第二层：语义校验（挡不住就等着静默出错）**

⚠️ **这一层才是关键。** 结构校验通过、但语义错误的策略**不会报任何错**——因为 `rules.py` 对"缺字段"的语义是**返回 False（不满足）**，于是整条规则静默失效，申请会**以更低的审批层级被批准**。这是审批系统里最严重的失败模式。

```python
# domain/rules.py（或 domain/policy_check.py）
ALLOWED_CONTEXT_KEYS = {
    "amount_fen", "urgency", "framework_contract",
    "department_id", "category_id", "requester_id",
}
NUMERIC_OPERATORS = {"lt", "lte", "gt", "gte"}


def collect_paths(rule: Any) -> list[str]:
    """递归收集规则里引用的所有路径。"""
    if not isinstance(rule, dict) or len(rule) != 1:
        raise RuleError("每个规则对象必须且只能包含一个操作符")
    operator, operand = next(iter(rule.items()))
    if operator in {"all", "any"}:
        paths: list[str] = []
        for item in operand:
            paths += collect_paths(item)
        return paths
    if operator == "not":
        return collect_paths(operand)
    if not isinstance(operand, list) or not operand:
        raise RuleError(f"{operator} 需要一个非空数组")
    return [operand[0]]


def validate_policy(policy: ApprovalPolicyIn) -> list[str]:
    """返回问题列表（空 = 通过）。保存策略时调用，有问题直接 422。"""
    problems: list[str] = []
    seen_orders: set[int] = set()
    has_fallback = False

    for step in policy.steps:
        if step.order in seen_orders:
            problems.append(f"order={step.order} 重复：同角色去重会让其中一条静默消失")
        seen_orders.add(step.order)

        # 1) 路径白名单：写成 amount 而不是 amount_fen 必须在这里被拦住
        for path in collect_paths(step.when):
            root = path.split(".")[0]
            if root not in ALLOWED_CONTEXT_KEYS:
                problems.append(
                    f"规则引用了未知字段 {path!r}；允许的字段是 {sorted(ALLOWED_CONTEXT_KEYS)}。"
                    f"注意金额字段叫 amount_fen（单位：分），不是 amount"
                )

        # 2) 阈值单位：必须是整数分，禁止浮点
        for value in iter_numbers(step.when):
            if isinstance(value, float):
                problems.append(f"阈值 {value} 是浮点数；金额一律整数分")

        # 3) 兜底步骤：保证任何金额都能匹配到至少一级
        if is_zero_amount_fallback(step.when):
            has_fallback = True

    if not has_fallback:
        problems.append(
            "策略缺少“任何金额都命中”的兜底步骤：某些金额区间的申请会算出空审批链，"
            "等于无人审批直接通过"
        )
    return problems
```

`iter_numbers` / `is_zero_amount_fallback` 的写法很直白：前者递归收集 `when` 里出现的所有数字，后者判断"这个规则是不是 `{"gte": ["amount_fen", 0]}` 这种零阈值兜底"。

**第三层：链的完整性（放 M5 做，因为要用到引擎）**

"每个步骤都可达"这个检查必须调用 `resolve_approval_chain` 反推（拿几个代表性金额跑一遍，看每个步骤是否至少被触发一次），所以它属于 M5。M5 会把它加进同一套校验器，M2 先把前两层建起来。

**验收方式**：故意提交 `{"gte": ["amount", 100_000]}`（漏了 `_fen`），必须返回 **422 并指出字段名错误**——而不是保存成功、然后在 M5 发现审批链少了一级。

### 阶段 M3 · 账号与权限（1 周）

**目标**：8 个角色能登录，每个接口都有明确的权限边界。

**前置**：M2。

**涉及模块**：M-02。

**新增表**：`users`、`user_roles`（迁移 `0003`）。

#### 实施步骤

**第 1 步：口令哈希用 Argon2**

```python
from argon2 import PasswordHasher

_hasher = PasswordHasher()


def hash_password(raw: str) -> str:
    return _hasher.hash(raw)


def verify_password(raw: str, hashed: str) -> bool:
    try:
        return _hasher.verify(hashed, raw)
    except Exception:
        return False
```

**绝对不要用 MD5/SHA256 存密码**，也不要因为"反正只是练习"就存明文——这个习惯一旦养成很危险。

**第 2 步：JWT 双令牌 + Cookie 安全属性 + 登录限流**

- access token：15 分钟，放 httpOnly Cookie
- refresh token：7 天，数据库只存它的哈希，不存原值

`users` 表加一个 `token_version` 字段。冻结账号时 `token_version += 1`，签发和校验时都要比对——这样旧 token 立刻失效，不用维护黑名单。

**`token_version` 已经覆盖了"refresh token rotation"要解决的问题**（旧凭证立即失效），所以**不要再做 rotation**——那是在同一件事上叠第二套机制，只会让调试变复杂。

**Cookie 的三个属性必须一次写对**：

```python
response.set_cookie(
    "access_token", token,
    httponly=True,        # 防 XSS 读取
    samesite="lax",       # 防 CSRF：跨站发起的 POST 不会带上它
    secure=False,         # 本地 http 开发期必须 False，打包上 HTTPS 后改 True
    path="/",
)
response.set_cookie(
    "refresh_token", refresh,
    httponly=True,
    samesite="lax",
    secure=False,
    path="/api/v1/auth/refresh",   # ← 关键：refresh 只在这一个路径下发出去
)
```

**`refresh` 的 `Path` 限定是这里性价比最高的一行**：refresh token 从此不会出现在任何其他请求里，泄露面被砍到最小。

**CSRF 方案（第一版就这样，够了）**：

| 防线 | 作用 |
| --- | --- |
| `SameSite=Lax` | 挡住所有跨站 POST/PUT/PATCH/DELETE（`refresh` 是 POST，被挡住） |
| refresh Cookie 限定 `Path` | 缩小泄露面 |
| **所有写操作要求 `Idempotency-Key` 自定义头** | 浏览器**不会**跨站自动带上自定义头，这本身就是一道 CSRF 防线——你 M4 加的幂等机制白捡了这个效果 |

> 这也是用 Vite 代理（同源）而不是 CORS 的一个额外好处：同源时 `SameSite=Lax` 完全够用。如果前后端跨源（比如 M10 打包后的 `tauri://`），`Lax` 会导致 Cookie 根本不发送，那时才需要重新设计。**在文档里记一句"上公网再加 double-submit token"，就不用现在做。**

**登录限流（20 行，不要引 Redis）**：

```python
# infrastructure/login_throttle.py
_FAILED: dict[str, list[float]] = {}      # username -> 失败时间戳
MAX_FAILURES = 5
WINDOW_SECONDS = 300


def is_locked(username: str, now: float) -> bool:
    stamps = [t for t in _FAILED.get(username, []) if now - t < WINDOW_SECONDS]
    _FAILED[username] = stamps
    return len(stamps) >= MAX_FAILURES
```

同一进程内的内存字典就够了——**你是单进程 uvicorn 本地跑，没有多实例共享状态的问题**，上 Redis 是纯浪费。登录失败累计 5 次锁 5 分钟，成功则清空。验收：连错 5 次后第 6 次返回 **429**（而不是 401），等窗口过期后恢复。

**第 3 步：权限依赖 `boundaries/deps.py`**

```python
def require_roles(*allowed: str):
    async def dependency(user: CurrentUser = Depends(get_current_user)) -> CurrentUser:
        if not allowed:
            return user
        if not set(user.roles) & set(allowed):
            raise HTTPException(status_code=403, detail="权限不足")
        return user

    return dependency
```

路由上这样用：

```python
@router.get(
    "/approvals/tasks",
    dependencies=[Depends(require_roles("DEPT_MANAGER", "DEPT_HEAD"))],
)
```

**但角色校验只解决了一半问题，另一半是"数据级权限"，必须在 M3 就定下来。**

`require_roles` 回答的是"这个角色**能不能用**这个接口"；它回答不了"这个角色**能看到哪些行**"。真实采购系统里这两种权限是分开的，而且第二种才是最容易出事的地方：

| 谁能看什么 | 规则 |
| --- | --- |
| `REQUESTER` | 只看自己提的申请 |
| `DEPT_MANAGER` / `DEPT_HEAD` | 看本部门（含子部门）的申请 |
| `PROCUREMENT` / `FINANCE` / `RECEIVER` / **`GM`** | **跨部门看全公司**（这是它们的职责） |
| `ADMIN` | 全部 |

> **`GM` 是第 8 个角色**（审批策略第 5 级会用到它，200000 元的验收要求产生 GM 任务），但领域设计的角色表里漏了它。**推荐的处理方式：让 `ADMIN` 兼任 `GM`**——给同一个用户同时挂 `ADMIN` + `GM` 两个角色即可，`user_roles` 本来就是多对多，不用改表、不用加角色。GM 的业务含义是"金额很大时的最终审批人"，与系统管理员兼任完全合理。
>
> 如果你更想让它独立成第 8 个角色，那就要一次补齐四处：角色常量表、可见范围（同上表）、权限矩阵、前端菜单项。

建议在 M3 就写一个**唯一的范围判定函数**，后面所有查询和下载都走它：

```python
# domain/permissions.py 或 application/coordinators/auth.py
def visible_request_filter(user: CurrentUser):
    """返回一个可以直接塞进 select().where() 的条件。

    所有"按 id 取单条"的地方都必须带上它，取不到就 404，
    而不是"取到了再判断能不能看"。
    """
    if user.is_admin or user.has_any("PROCUREMENT", "FINANCE", "RECEIVER"):
        return true()
    if user.has_any("DEPT_MANAGER", "DEPT_HEAD"):
        return PurchaseRequestRecord.department_id.in_(user.visible_department_ids)
    return PurchaseRequestRecord.requester_id == user.id
```

配套两条约定：

- **`GET /requests/{id}` 一律用它过滤**（查不到就是 404），别写成"先查再比 `requester_id`"。把权限写进 `WHERE` 而不是写在 `if` 里，是让你不可能忘记加权限的唯一办法。
- **403 和 404 的选择**：资源**在**他的可见范围内但没权限操作 → 403；资源**不在**可见范围内 → 404（不告诉他这东西存在）。这条和领域设计 7.1 的错误码约定是一致的。

每个角色的可见范围和"能执行哪些操作"要写成一张**权限矩阵表**放进 README，验收时逐格测——这张表本身就是作品集里最容易被追问的部分。

**第 4 步：前端路由守卫**

- 未登录访问任何业务页，跳登录页
- 已登录但角色不匹配，显示"无权限"而不是白屏

#### 常见坑

| 坑 | 说明 |
| --- | --- |
| 只靠前端隐藏菜单 | 用 Postman 直接打接口就绕过了，后端必须自己校验 |
| 只做角色校验，不做范围过滤 | "能不能用接口"和"能看到哪些行"是两件事；后者必须写进 `WHERE` |
| 权限写成"先查出来再判断能否看" | 那样漏一处就是越权；把过滤条件塞进查询，漏不掉 |
| JWT 密钥写死在代码里 | 从配置读，`.env` 加进 `.gitignore` |
| refresh token 存原值 | 只存哈希；数据库泄露时原值也拿不到 |
| Cookie 忘了 httpOnly / SameSite | `httpOnly=True` 防 XSS；`SameSite=Lax` 是本地开发的 CSRF 主防线 |
| refresh Cookie 不限定 `Path` | 它会跟着每个请求到处跑；限定到 refresh 接口，泄露面立刻变小 |
| 又去做一遍 refresh token rotation | `token_version` 已经解决"旧凭证失效"；两套机制叠加只会增加调试成本 |
| 为了登录限流去装 Redis | 单进程本地跑，内存字典就够；Redis 是这里最典型的过度设计 |
| 越权返回 404 还是 403 分不清 | 可见范围内没权限 → 403；不在可见范围 → 404 |

不要一次把 12 个状态全写完。M4 只需要：

```python
TRANSITIONS = {
    "DRAFT":       {"IN_APPROVAL", "DISCARDED"},
    "IN_APPROVAL": {"WITHDRAWN"},       # M5 会往这里加 SOURCING 和 REJECTED
    "DISCARDED":   set(),
    "WITHDRAWN":   set(),

```

**每次只加当前阶段用得到的转移**。一次写完 12 个状态，测试会非常难写，而且大部分分支根本没有触发路径。

**第 2 步：主单与明细分两张表**

`purchase_requests` 的关键字段：

**关键约定**：`amount_total` 不落库由前端传，而是**后端根据明细行重新算**。前端传的金额一律不信任。

**第 3 步：乐观锁用条件更新，不要用"查了再比"**

```python
statement = (
    update(PurchaseRequestRecord)
```

把 `version` 和 `status` 一起放进 `WHERE`，能一次性挡住"版本过期"和"状态不对"两种冲突。

**第 4 步：幂等依赖**

```python
async def idempotency_key(
    x_idempotency_key: str | None = Header(default=None, alias="Idempotency-Key"),
) -> str:
    if not x_idempotency_key or len(x_idempotency_key) > 128:
        raise HTTPException(status_code=400, detail="缺少有效的 Idempotency-Key")
    return x_idempotency_key
```

`IdempotencyCoordinator` 的逻辑：把 `(actor_id, scope, key)` 作为唯一索引；先算 `payload_hash`，然后

1. 查到记录且 `payload_hash` 相同 → 直接返回上次的响应
2. 查到记录但 `payload_hash` 不同 → 409
3. 查不到 → 执行操作，连同响应一起写入记录

**`scope` 必须明确定义，不能含糊。** 建议就用**端点标识**，比如 `POST:/api/v1/requests/{id}/submit`。如果 `scope` 留空或随手写，同一把 key 会在"提交"和"撤回"之间互相污染——第二次请求会拿到第一次的响应，而且看起来一切正常。

**上面的第 3 条有一个并发漏洞，必须补。** 两个请求带着**同一个 key 同时**到达时，两边都"查不到记录"，于是两边都执行了操作——幂等失效，而且失效得悄无声息。正确流程是把"占位"和"执行"分开：

```
1. 独立事务：插入占位行 (actor_id, scope, key, payload_hash, status=IN_PROGRESS)
   ├─ 撞唯一索引 → 说明已有同 key 请求：再查它的 status
   │    ├─ COMPLETED 且 payload_hash 相同 → 返回它存下的响应
   │    ├─ payload_hash 不同              → 409
   │    └─ IN_PROGRESS                    → 409（"正在处理中，请稍后重试"）
2. 业务事务：执行操作 → 把响应和 status=COMPLETED 回填到占位行 → commit
3. 业务失败：回滚业务事务，并把占位行标记为 FAILED（或直接删掉），让客户端可以重试
```

**占位行必须用独立事务提交**，否则业务回滚会把它一起带走，第二步就永远查不到它。

顺带说清 `idempotency_records` 表需要补的列：`status(IN_PROGRESS/COMPLETED/FAILED)`、`response`、`payload_hash`，以及 `(actor_id, scope, key)` 的唯一约束。

**第 5 步：事件流**

每次状态变更写一条 `request_events`：`event_type / from_status / to_status / actor_id / payload / created_at`。**只追加，永不更新或删除。**

事件表价值很大：时间线页面直接读它、排查问题时能还原完整历史、将来做审计不用另建表。

#### 验收标准

- [ ] 能建草稿、改草稿、加三行明细，`amount_total` 由后端算出来且正确
- [ ] 用旧 `version` 提交修改，返回 **409**
- [ ] 同一个 `Idempotency-Key` 提交两次，只产生一条申请
- [ ] 同一个 `Idempotency-Key` 但改成不同金额，返回 **409**
- [ ] **同一个 `Idempotency-Key` 并发提交（`asyncio.gather` 两个请求），只产生一条申请，另一个拿到 409 或重放响应**
- [ ] 提交后状态变 `IN_APPROVAL`，时间线上出现两条事件
- [ ] 已提交的申请不能再 `PATCH`（返回 409）

#### 常见坑

| 坑 | 说明 |
| --- | --- |
| 信任前端传的 `amount_total` | 后端必须按明细重算 |
| 乐观锁写成"先查再比再写" | 并发下依然会冲突，必须用条件更新 |
| 幂等只记 key 不记 payload 哈希 | 那样同键不同载荷会被错误地当成重放 |
| 幂等只有"查不到就执行" | 并发同 key 会双双执行；必须先用独立事务插 `IN_PROGRESS` 占位行 |
| `scope` 没定义 | 同一把 key 会在不同接口之间串味；用端点标识当 scope |
| 事件表可更新 | 事件流一旦可改就失去审计意义 |
| 一次写完全部状态 | 只加当前阶段需要的转移 |

**产出**：申请全生命周期的前半段（草稿到提交）。

### 阶段 M5 · 审批引擎（2 周，核心）

**目标**：提交时按规则动态生成审批链；审批人能看到待办；能通过或驳回；全部通过后主单自动推进。

**前置**：M4。

**涉及模块**：M-06、M-07。

**新增表**：`approval_flows`、`approval_tasks`（迁移 `0005`）。

#### 实施顺序（很重要）

**先写纯函数和测试，再写数据库。** 这是本次项目最值得学的一个工作方式：

1. 写 `domain/rules.py`（附录 A.1 的代码）
2. 写 `tests/test_rules.py`，跑通
3. 写 `domain/approval_engine.py`（附录 A.2 的代码）
4. 写 `tests/test_approval_engine.py`，用 M0 那张《金额→审批链》对照表当参数
5. **测试全绿之后**才开始动数据库

纯函数阶段你一行数据库都不需要，跑测试是毫秒级的，改代码的反馈循环极快。等逻辑对了再接数据库，能省掉大量"改一行、重启服务、点半小时页面"的痛苦。

#### 实施步骤

**第 1 步：两张表**

`approval_flows`：`id / request_id / status(RUNNING/APPROVED/REJECTED/CANCELLED) / policy_snapshot(JSONB) / policy_version(INT) / started_at / completed_at`

> **`policy_snapshot` 与 `policy_version` 是这一阶段不能省的两列。** 它们存的是"这笔申请提交那一刻，品类上那份 `approval_policy` 的原件"和它的版本号。没有它们，管理员改一次阈值，你就再也说不清历史申请当时为什么只走两级——`approval_tasks` 只记录了结果，没记录依据。成本是一列 JSONB，收益是审批链可复现、可解释、可审计。

`approval_tasks`：

```
id, flow_id, request_id, step_order, role, mode(SINGLE/ALL), status,
assignee_id(NULL=未认领), decided_by, decided_at, comment, delegated_from
```

`request_id` 是受控冗余（与 `flow_id` 同时写入），专门为"待办一次 JOIN 查完"服务；索引：`(assignee_id, status)`、`(flow_id, step_order)`。

**第 2 步：提交用例接上审批链**

`POST /requests/{id}/submit` 的事务里依次做：

```
1. 乐观锁推进状态 DRAFT -> IN_APPROVAL
2. 从品类读 approval_policy，**连同 category.version 一起留一份原件**
3. 组装 request_context（amount_fen、urgency、framework_contract、department_id…）
4. chain = resolve_approval_chain(policy, request_context)
5. 建 1 条 approval_flow（写入 policy_snapshot + policy_version）+ N 条 approval_task
6. 写 request_events
7. 写 idempotency_records
8. commit
```

**全部在同一个事务里**，任何一步失败整体回滚。第 5 步产生的任务数就是 M0 那张对照表验证的东西。

第 2 步的"留一份原件"指的是把读出来的策略深拷贝一份存进 `approval_flows.policy_snapshot`——**不是存品类 id 让以后现查**。品类策略是会被改的，现查等于拿今天的规则解释三个月前的申请。

**第 3 步：任务到底分配给谁（这一步不能跳）**

这是 M5 最容易含糊过去、然后在写代码时卡住半天的地方。**必须先把五条规则定死**：

**规则 1：`SINGLE` 生成 1 条任务，`ALL` 生成 N 条任务。**

| mode | 生成几条 | `assignee_id` | 谁算"通过" |
| --- | --- | --- | --- |
| `SINGLE`（或签） | **1 条** | 初始 `NULL`（谁先认领谁审） | 该步骤任一任务通过 |
| `ALL`（会签） | **N 条**（N = 该角色下的合格人数） | **建任务时就预分配** | 该步骤全部任务通过 |

**会签不能抢单**——"所有人都要通过"和"谁抢到算谁的"在语义上互斥。所以 `ALL` 模式的任务**建的时候就把 `assignee_id` 填好**，每人的待办里立刻出现自己那条。

**规则 2：候选人从哪里解析，按角色分两类。**

| 角色 | 候选人来源 | 说明 |
| --- | --- | --- |
| `DEPT_MANAGER` / `DEPT_HEAD` | **申请人的部门（含子部门）**下所有持有该角色的人 | 部门主管只能审本部门 |
| `PROCUREMENT` / `FINANCE` / `GM` | **全局**持有该角色的人 | 采购和财务本来就跨部门 |

**规则 3：解析出 0 个候选人 → 提交直接 422，不允许生成"没人能审"的任务。**

```python
chain = resolve_approval_chain(policy, request_context)
for step in chain:
    candidates = await resolve_candidates(session, step.role, requester.department_id)
    if not candidates:
        raise BusinessError(
            f"审批链第 {step.order} 级（{step.role}）没有任何可用审批人，申请无法提交",
            status_code=422,
        )
```

**这一条比什么都重要**：它把"申请提交成功后永久卡死、没有任何提示"变成"提交时就报错、立刻能修"。审批系统里最糟的体验就是单据进去了、没人能处理、也没人知道为什么。

**规则 4：第四层配置校验——链的完整性与可达性（接 M2 的第 3 步）。**

现在引擎已经能算了，把第三层校验补上，一起挂在保存策略的 422 上：

```python
PROBE_AMOUNTS_FEN = [0, 100_00, 1_000_00, 10_000_00, 100_000_00, 1_000_000_00]


def check_reachability(policy: dict) -> list[str]:
    """拿几个代表性金额反推：每个步骤是否至少被触发一次；有没有金额算出空链。"""
    problems: list[str] = []
    triggered: set[int] = set()
    for amount in PROBE_AMOUNTS_FEN:
        chain = resolve_approval_chain(policy, {"amount_fen": amount})
        if not chain:
            problems.append(f"金额 {amount} 分算出的审批链为空（无人审批）")
        triggered |= {step.order for step in chain}
    for step in policy["steps"]:
        if step["order"] not in triggered:
            problems.append(f"order={step['order']} 在任何探测金额下都不会被触发")
    return problems
```

**验收**：故意配一份"最低阈值 100 元、没有零阈值兜底"的策略，保存必须返回 422；把兜底步骤加回去就能保存成功。

**规则 5：提交时把解析结果和快照一起落库**，方便事后解释"当时为什么是这几个人"。

`approval_tasks` 建任务时写入 `assignee_id`（会签预分配 / 或签为 NULL）、`request_id`、`role`、`mode`、`step_order`；同时在 `approval_flows.policy_snapshot` 里已经存了策略原件。

**第 4 步：待办查询**

```sql
SELECT * FROM approval_tasks
 WHERE status = 'PENDING'
   AND (assignee_id = :me OR (assignee_id IS NULL AND role = ANY(:my_roles)))
 ORDER BY created_at DESC;
```

`assignee_id IS NULL AND role = ...` 是"未认领但属于我这个角色"的任务——它**只对 `SINGLE`（或签）有意义**；`ALL`（会签）的任务在第 3 步就已经预分配了 `assignee_id`，所以每个会签人只能看到自己那一条。**建议第一版就做认领**（`assignee_id` 从 NULL 置为当前用户），因为"抢单"是真实业务里很常见的模式。

**列表页一定要一次 JOIN 查完。** 待办列表要显示金额、申请人、品类，而这些字段在 `purchase_requests` 和 `purchase_categories` 上——如果写成"查出 20 条任务，再循环查所属申请"，20 条任务就是 21 次查询（经典的 N+1）。

要一次查完，`approval_tasks` 上需要有一个 `request_id`。这里有两种做法：

| 做法 | 代价 | 适用 |
| --- | --- | --- |
| 通过 `approval_flows` 多 join 一张表 | 待办查询多一次 join | 表最"规范"，`request_id` 不冗余 |
| **在 `approval_tasks` 上加 `request_id`（推荐）** | 一列冗余，建任务时一起写 | 待办是全系统最频繁的查询，少一次 join 很值 |

推荐第二种：`approval_tasks` 加一列 `request_id`（与 `flow_id` 同时写入，属于受控冗余，不是随手反范式）。这样待办列表一次查询就够：

```python
statement = (
    select(ApprovalTaskRecord, PurchaseRequestRecord, PurchaseCategoryRecord)
    .join(PurchaseRequestRecord, ApprovalTaskRecord.request_id == PurchaseRequestRecord.id)
    .join(PurchaseCategoryRecord, PurchaseRequestRecord.category_id == PurchaseCategoryRecord.id)
    .where(
        ApprovalTaskRecord.status == "PENDING",
        or_(
            ApprovalTaskRecord.assignee_id == me,
            and_(ApprovalTaskRecord.assignee_id.is_(None), ApprovalTaskRecord.role.in_(my_roles)),
        ),
    )
    .order_by(ApprovalTaskRecord.created_at.desc())
    .limit(size)
    .offset((page - 1) * size)
)
```

验收方式很直接：**打开 SQLAlchemy 的 `echo=True`，刷一次待办列表，数日志里出现几条 `SELECT`。** 一条是对的，二十条就是 N+1。

**第 5 步：审批决定，用条件更新防并发**

```python
statement = (
    update(ApprovalTaskRecord)
    .where(
```

两个人同时点"通过"，只有一个成功——这就是条件更新的价值。

**第 6 步：步骤完成判定（或签与会签）**

每处理完一个任务，就检查它所属的 `(flow_id, step_order)`：

| mode | 步骤完成条件 |
| --- | --- |
| `SINGLE` | 该步骤下**任意一个**任务 `APPROVED` |
| `ALL` | 该步骤下**全部**任务 `APPROVED` |

步骤完成后，才看下一 `step_order` 是否还有待处理任务。

**第 7 步：审批流完成，推进主单**

当所有步骤都完成：

```
approval_flows.status -> APPROVED
写一条 request_events: APPROVAL_COMPLETED
主单状态机推进 IN_APPROVAL -> SOURCING
```

**主单状态由审批模块的完成事件驱动，不是审批模块直接改主单字段。** 这条边界守住了，将来加"补充式驳回"之类的新流程才不会把代码搅成一团。

驳回时同理：`IN_APPROVAL -> REJECTED`，同时写事件。

```
POST /api/v1/approvals/tasks/{id}/reject    驳回（意见必填）
```

- `approver/TaskDetail.tsx`：申请全貌 + 预算余额 + 通过/驳回

#### 验收标准

- [ ] **500 元 / 5000 元 / 50000 元 / 200000 元四笔申请，生成的审批任务数分别是 1 / 2 / 4 / 5**
- [ ] 金额 500 元的申请，只有部门主管能看到待办；采购和财务看不到
- [ ] 两个人同时通过同一个任务，只有一个成功，另一个 409
- [ ] 部门主管驳回后，主单变 `REJECTED`，申请人时间线上能看到驳回意见
- [ ] **待办列表用一次 JOIN 查出来**（金额、申请人、品类一次带出），不是"查 20 条任务再逐条查申请"
- [ ] 全部通过后，主单自动变 `SOURCING`，时间线上有 `APPROVAL_COMPLETED`
- [ ] 改一下品类的审批策略（比如把阈值从 10000 改成 5000），**不改任何代码**，重新提交的申请审批链跟着变
- [ ] **改完策略后，之前那笔申请仍能显示出它当时用的策略**（`approval_flows.policy_snapshot` 里存的是提交那一刻的原件）
- [ ] **把某部门的 `DEPT_HEAD` 角色全删掉，再提交一笔需要部门负责人审批的申请 → 返回 422 并说明是哪一级缺人**（而不是提交成功后永久卡死）
- [ ] **`ALL`（会签）模式：该角色有 3 个人 → 生成 3 条任务、3 条都预分配了 `assignee_id`、3 人各看到自己那一条；3 条全部通过后该步骤才算完成**
- [ ] **`SINGLE`（或签）模式：该角色有 3 个人 → 只生成 1 条任务，3 人都能在待办里看到，任一人认领并通过后该步骤完成**
- [ ] **配一份没有零阈值兜底的策略 → 保存返回 422；配一份有步骤永远不会被触发的策略 → 同样 422**

最后一条是这个阶段的核心验收——**它证明你的审批链真的是数据驱动的，而不是硬编码的 if/else。**

倒数第二条同样重要，而且它比看上去更容易漏：只存"结果"（几条任务）不存"依据"（当时那份策略），等你改过两次阈值之后，就再也解释不清任何一笔历史申请为什么走了那么几级。**审批链是结果，策略快照是依据，两个都要落库。**

#### 常见坑

| 坑 | 说明 |
| --- | --- |
| 审批逻辑和主单状态写在同一个函数里 | 两层状态要解耦，用事件连接 |
| 忘了同一角色去重 | 部门主管可能被插入两次，待办出现重复条目 |
| 会签判定漏了"未处理"的任务 | `ALL` 模式必须等全部任务都有结论 |
| 会签任务也允许抢单 | "全部通过"和"谁抢到算谁的"语义互斥；会签必须建任务时就预分配 `assignee_id` |
| 候选人解析出 0 个人却照样提交 | 申请会永久卡死且无人知情；提交时就要 422 |
| 部门主管的候选人从全局解析 | 那样 A 部门主管能审 B 部门的单；`DEPT_MANAGER/DEPT_HEAD` 必须按申请人部门（含子部门）解析 |
| 驳回后没释放资源 | M6 之后，驳回必须释放预算预留 |
| 先写数据库再写逻辑 | 顺序反了，调试成本会翻好几倍 |
| 审批链硬编码 or 写死在代码里 | 必须从品类策略读，验收第 8 条专门测这个 |
| 只做结构校验不做可达性校验 | 步骤永远不被触发 = 审批层级静默降低 |

**产出**：整个项目最有含金量的模块，以及一套可复用的纯函数测试。

### 阶段 M6 · 预算并发预留（1 周，核心）

**目标**：申请提交时预留预算，驳回或撤回时释放，付款成功时转为已花。

**前置**：M5。

**涉及模块**：M-08。

**新增表**：`budget_transactions`（迁移 `0006`）。

#### 实施步骤

**第 1 步：写 `repositories/budget_repo.py`**

把附录 A.4 的三个函数敲一遍：`reserve_budget` / `release_budget` / `spend_budget`。三个都用条件更新。

> ⚠️ **附录 A.4 的 `available` 那一行在 SQLAlchemy 里会直接抛异常，必须先改再看。** 详见领域设计附录 A.4 里已经改好的版本——那个 `if` 判断会触发 `TypeError: Boolean value of this clause is not defined`。正确写法是把列之间的减法**写在 `where()` 的守卫条件里**，让数据库去做减法：

```python
guard = (BudgetRecord.amount_total
         - (BudgetRecord.amount_reserved + BudgetRecord.amount_spent)) >= amount_fen
```

这样写还顺带避开了资金类型问题：减法留在 SQL 层就是 `bigint` 运算，不会因为哪天金额列改成 `NUMERIC` 而在 Python 侧拿到 `Decimal` 再和 `int` 混算。

**第 2 步：`reserve_budget` 必须带上 `request_id`**

```python
async def reserve_budget(session, budget_id, request_id, amount_fen: int) -> bool:
```

理由有两个，都很实际：

1. **防重复预留**：不带 `request_id`，"同一笔申请因为重试/并发被预留两次"在库里看不出任何异常。带上它，就可以在 `budget_transactions` 上对 `(request_id, kind)` 建唯一约束（`RESERVE` 一笔申请只能有一条），重复预留会直接撞唯一索引。
2. **释放时能定位原预留**：第 3 步那条"没有 RESERVE 流水就抛异常"的断言，只有拿到 `request_id` 才写得出来。

**第 3 步：接进提交事务**

在 M5 的提交事务里，**在推进状态之后、commit 之前**插入：

```python
ok = await reserve_budget(session, budget_id, request_id, amount_fen)
if not ok:
    raise BusinessError("预算不足", status_code=422)
await write_budget_transaction(session, budget_id, request_id, "RESERVE", amount_fen)
```

顺序很重要：**先推进状态再扣预算**，还是**先扣预算再推进状态**都行，但两者必须在同一事务里，失败必须整体回滚。

**第 4 步：接进驳回与撤回**

- 驳回（M5）→ `release_budget`
- 撤回（M4）→ `release_budget`
- 付款成功（M8）→ `spend_budget`

**这三个入口一个都不能漏。** 建议在 `release_budget` 里加断言：如果该申请没有对应的 `RESERVE` 流水，直接抛异常——能立刻发现遗漏。这也正是第 2 步要把 `request_id` 传进来的原因。

> 预算总额被调低时也要过一遍这个校验：`amount_reserved + amount_spent` 可能已经超过新的 `amount_total`。**在 `budgets` 表上加一条 CHECK 约束**（`amount_reserved >= 0 AND amount_spent >= 0 AND amount_reserved + amount_spent <= amount_total`）当兜底，比只在应用层判断可靠——应用层总有一条路径是你没想到的。

**第 5 步：写并发测试**

```python
# tests/test_budget_concurrency.py
async def test_concurrent_reserve_only_one_succeeds(session_factory, budget_id, request_id_a, request_id_b):
    async def attempt(rid):
        async with session_factory() as session:
            ok = await reserve_budget(session, budget_id, rid, amount_fen=80_000_00)
            await session.commit()
            return ok

    results = await asyncio.gather(attempt(request_id_a), attempt(request_id_b))
    assert sorted(results) == [False, True]

    # 最终预留不超过总额
    async with session_factory() as session:
        budget = await session.get(BudgetRecord, budget_id)
        assert budget.amount_reserved <= budget.amount_total


async def test_same_request_cannot_reserve_twice(session_factory, budget_id, request_id):
    """同一笔申请重试：第二次必须失败（唯一约束挡住），而不是又预留一次。"""
    async with session_factory() as session:
        assert await reserve_budget(session, budget_id, request_id, 10_000) is True
        await session.commit()
    async with session_factory() as session:
        try:
            await reserve_budget(session, budget_id, request_id, 10_000)
            await session.commit()
            raised = False
        except IntegrityError:
            raised = True
    assert raised, "同一 request_id 不应能重复预留"
```

**必须用 `asyncio.gather`，串行 `await` 测不出问题。** 这是全项目最重要的一个测试。

**第二段测试同样重要**，它验证的是"重试不会重复扣钱"——这是幂等和预算两套机制真正咬合的地方，也是真实系统里最容易出资金事故的地方。

**第 6 步：预留金额与实付金额的差额必须显式释放**

⚠️ **这一步不做，预算账目会永久对不上。** 金额在流程里是会变的：

```
提交申请  → 预留 amount_total（申请金额，比如 1000 元）
询价定标  → 中标价可能更低（比如 900 元）        ← 差额已经出现
生成订单  → 订单金额 = 中标价
收货发票  → 发票金额在订单金额 ±2% 容差内（900 ± 18 元）
执行付款  → 实际付出 invoice_amount
```

**付款时必须按"实付金额"结转，并把差额释放掉**：

```python
reserved = await get_reserved_fen(session, request_id)      # 当初预留了多少
actual   = invoice_amount_fen                                # 实际付了多少

if reserved < actual:
    raise BusinessError("实付金额超过预留金额，请检查单据", status_code=422)

ok = await spend_budget(session, budget_id, request_id, actual)         # 已预留 → 已花（按实付）
if not ok:
    raise ConflictError("预算预留状态异常")
if reserved > actual:
    await release_budget(session, budget_id, request_id, reserved - actual)   # 差额释放
```

**两条流水都必须写**（`SPEND` = actual，`RELEASE` = reserved − actual），这样 `budget_transactions` 加起来永远等于预算变动，事后能对账。

**三个数量关系必须成立**（可以写成断言，也可以写成测试）：

| 关系 | 含义 |
| --- | --- |
| `amount_spent` 只增**实付**金额 | 多记一分都是账目错误 |
| 付款完成后该申请的 `amount_reserved` **归零** | 不归零就是差额没释放，可用额度会虚低 |
| `amount_total` 全程不变 | 预留/释放/结转只动另外两个字段 |

**第一版不做部分付款**，所以一笔申请一次结清；如果将来要做分次付款，`UNIQUE(request_id)` 和这条"一次性结清"的假设都要一起改——这也是为什么它俩现在必须写在同一个地方。

**第 7 步：前端预算看板**

`finance/BudgetBoard.tsx`：部门 × 品类的表格，列是"总额 / 已预留 / 已花 / 可用"。可用额度用进度条可视化，低于 20% 标黄。

#### 验收标准

- [ ] 预算总额 1000 元时，同时提交两笔 800 元的申请，只有一笔成功，另一笔返回 422
- [ ] 驳回后，预算可用额度恢复
- [ ] `budget_transactions` 里能看到 RESERVE / RELEASE / SPEND 三类流水，金额能对上
- [ ] **同一笔申请重放（同一 `Idempotency-Key`）不会产生第二条 `RESERVE` 流水**
- [ ] **申请 1000 元、实际付款 900 元之后：`amount_spent` 增加 900、该申请的 `amount_reserved` 归零、`amount_total` 不变**（差额 100 元被释放）
- [ ] **`budget_transactions` 里该申请的三类流水相加（RESERVE − RELEASE − SPEND）= 0**
- [ ] 并发测试稳定通过（**连跑 20 次都不失败**）

#### 常见坑

| 坑 | 说明 |
| --- | --- |
| 先 SELECT 查余额再 UPDATE | 并发下必然超额。这是本阶段唯一必须做对的事 |
| `where()` 里用 Python 层的 `if` 判断余额 | `available >= amount` 会抛 `TypeError: Boolean value of this clause is not defined`；守卫条件必须整个写在 `where()` 里 |
| 事务边界不对 | 预留和状态变更必须在同一事务，否则一边成功一边失败 |
| 忘了写流水 | 事后对不上账，说不清钱去哪了 |
| 遗漏释放入口 | 驳回、撤回、申请作废都要释放；建议在仓库层加断言兜底（要用到 `request_id`） |
| 改动 `amount_total` 时没考虑已预留 | 调低总额可能导致"已预留 > 总额"；加 CHECK 约束 + 应用层校验 |
| 重试导致重复预留 | `budget_transactions` 上对 `(request_id, kind)` 建唯一约束，别只依赖幂等表 |
| **付款只做 `spend` 不释放差额** | 预留 1000 实付 900，那 100 会永远挂在 `amount_reserved` 上，可用额度虚低且永远对不上账；必须 `SPEND(实付) + RELEASE(差额)` |
| 用预留金额去 `spend` | `amount_spent` 会多记；已花必须是**实付**金额 |
| `amount_reserved` 付款后不归零 | 差额没释放的典型症状；验收里专门有一条测它 |

**产出**：并发安全的预算机制，以及一个能证明它的并发测试。

### 阶段 M7 · 附件与时间线（1 周）

**目标**：能上传和下载附件（报价单、合同、发票、验收照片），并能看到完整事件时间线。

**前置**：M6。

**涉及模块**：M-10、M-11。

**新增表**：`attachments`（迁移 `0007`）。

#### 实施步骤

**第 1 步：本地对象存储 `infrastructure/object_store.py`**

```python
from pathlib import Path
from uuid import uuid4


class LocalObjectStore:
    def __init__(self, root: Path) -> None:
        self.root = root
        self.root.mkdir(parents=True, exist_ok=True)

    def save(self, content: bytes, suffix: str) -> str:
        """返回 storage_key。绝不使用用户提供的文件名。"""
        key = f"{uuid4().hex}{suffix}"
        target = self.root / key[:2] / key
        target.parent.mkdir(parents=True, exist_ok=True)
        target.write_bytes(content)
        return key

    def load(self, key: str) -> bytes:
        return (self.root / key[:2] / key).read_bytes()
```

**`save` 必须用 UUID 生成文件名，绝不能拼用户上传的原始文件名。** 否则 `../../app/main.py` 这种文件名会造成路径穿越，直接覆盖你的源码。

**第 2 步：`attachments` 表**

```
id, request_id, kind(QUOTATION/CONTRACT/INVOICE/RECEIPT/OTHER),
original_filename, content_type, size_bytes, sha256, storage_key, uploaded_by, created_at
```

**原始文件名只当元数据存**，磁盘上永远用 UUID。

**第 3 步：上传接口**

```
POST /api/v1/requests/{id}/attachments   multipart/form-data
GET  /api/v1/attachments/{id}/download   鉴权下载
```

上传时依次校验（**六步，顺序不要调**）：

1. 申请存在且属于当前用户
2. 文件大小 ≤ 10 MB
3. **内容类型白名单**：`application/pdf`、`image/jpeg`、`image/png`
4. **文件头 magic bytes 与声明的 `content_type` 必须一致**（PDF 是 `%PDF`，JPEG 是 `FF D8 FF`，PNG 是 `89 50 4E 47`）
5. **图片必须真正解码一次**（见下）
6. 计算 SHA-256 存元数据

**只校验扩展名是不够的**——把 `evil.exe` 改名成 `evil.pdf` 就能绕过；但**只校验 magic bytes 也还不够**，文件头是可以伪造的。图片类附件必须真的交给解码器解析一次：

```python
from io import BytesIO

from PIL import Image


def verify_image(content: bytes) -> tuple[int, int]:
    """真正解码一次。返回 (宽, 高)。解码失败说明这不是一张合法图片。"""
    try:
        with Image.open(BytesIO(content)) as image:
            image.verify()                    # 校验文件完整性
        with Image.open(BytesIO(content)) as image:
            width, height = image.size
    except Exception as exc:
        raise BusinessError("图片文件损坏或格式不合法", status_code=422) from exc

    # 压缩炸弹：声明 10 MB 的 PNG 可以解出几个 GB 的位图
    if width * height > 50_000_000:           # 约 5000 万像素
        raise BusinessError("图片尺寸过大", status_code=422)
    return width, height
```

**为什么这两条值得单独写**：`verify()` 能挡住"文件头对、内容假"的构造文件；而**压缩炸弹**是上传接口里最容易被忽略的拒绝服务面——10 MB 的文件可以让解码器吃光内存。`width * height` 的上限检查是成本最低的防线（先看尺寸，再决定要不要解码像素）。

> PDF 不做内容解析（`pypdf` 解析不可信 PDF 本身就是攻击面），第一版**只校验文件头 + 大小**就够。真要更强，把附件存成不可执行、并且永远以 `attachment` 形式下载（第 4 步已经做了），就已经把主要风险关掉了。

**第 4 步：下载接口必须鉴权**

```python
@router.get("/attachments/{attachment_id}/download")
async def download(attachment_id: UUID, user=Depends(get_current_user), session=Depends(get_session)):
    attachment = await get_attachment(session, attachment_id)
    request = await get_request(session, attachment.request_id)
    if not can_view_request(user, request):
        raise HTTPException(status_code=403, detail="无权访问该附件")
    content = store.load(attachment.storage_key)
    return Response(
        content,
        media_type=attachment.content_type,
        headers={
            # 一律作为附件下载，不让浏览器内联渲染
            "Content-Disposition": f'attachment; filename="{quote(attachment.original_filename)}"',
        },
    )
```

**两件事都要做**：`content_type` 用**入库时校验过的那一个**（不是用户这次请求里带的），并且**强制 `Content-Disposition: attachment`**。少了后者，浏览器会按 `content_type` 去内联渲染——虽然你已经把类型限制在白名单里，但"永远以附件形式返回用户上传的东西"是一条不需要每次重新论证的习惯。文件名记得 URL 编码（`urllib.parse.quote`），中文文件名直接塞进 header 会引发编码异常。

**不要把 `uploads/` 挂成静态目录。** 那样任何知道文件名的人都能下载，等于没有权限控制。

**第 5 步：时间线页面**

`components/ApprovalTimeline.tsx` 扩展成完整的 `RequestTimeline`：读 `request_events`，展示"谁在什么时候把状态从 X 改成了 Y"，并在需要时附上操作意见。

**区分清楚两个组件的数据来源**，别混在一张表上：

| 组件 | 数据来源 | 回答的问题 |
| --- | --- | --- |
| `ApprovalTimeline` | `approval_tasks`（+ `policy_snapshot`） | 这笔申请**卡在谁那里**、还有几级没走 |
| `RequestTimeline` | `request_events` | 这笔申请**经历过什么**（含询价、收货、付款） |

前者是"当前审批链的进度视图"，后者是"全生命周期的事件流水"。它们看起来都是时间轴，但一个会随任务状态变化，另一个只追加。混用会让你在 M8 想加"付款完成"事件时无处安放。

#### 验收标准

- [ ] 上传 PDF 成功，返回附件 id
- [ ] 上传 11 MB 文件返回 422
- [ ] 上传改名成 `.pdf` 的 exe，返回 422
- [ ] **上传一张文件头像 PNG、内容不是图片的文件，返回 422（解码失败）**
- [ ] **上传一张超大尺寸的 PNG（比如 20000×20000），返回 422（压缩炸弹防护）**
- [ ] 用别的用户的 token 下载附件，返回 **403**

- [ ] 时间线按时间正序展示全部事件

#### 常见坑

| 坑 | 说明 |
| --- | --- |
| 用用户提供的文件名存盘 | 路径穿越漏洞，能覆盖任意文件 |
| `uploads/` 挂成静态目录 | 等于公开所有附件 |
| 只校验扩展名 | 改名即可绕过，要校验 magic bytes |
| 下载接口不查权限 | 改个 id 就能下载别人的发票 |
| 忘了 `Content-Disposition` | 浏览器可能内联渲染上传内容；一律强制"下载" |
| 中文文件名直接写进 header | 会抛编码异常；用 `quote()` 编码 |
| 审批链视图和事件流水混成一个组件 | 一个查 `approval_tasks`，一个查 `request_events`，别混 |
| 附件删除用物理删除 | 用软删除标记，保留审计痕迹 |

**产出**：受控的文件上传下载链路 + 完整事件时间线。

### 阶段 M8 · 履约链（2 周）

**目标**：从"审批通过"走到"付款归档"，把采购和报销真正区分开的那一段做出来。

**前置**：M6、M7（付款要预算接口，定标要附件）。

**涉及模块**：M-12、M-13、M-14。

**新增表**：`quotations`、`purchase_orders`、`purchase_order_lines`、`goods_receipts`、`goods_receipt_lines`、`invoices`、`payments`（迁移 `0008`）。

#### 8.1 询价与定标（约 3 天）

**接口**

```
GET  /api/v1/sourcing/queue            待询价队列（状态 = SOURCING）
POST /api/v1/requests/{id}/quotations  登记报价（供应商 + 金额 + 有效期 + 报价单附件）
GET  /api/v1/requests/{id}/quotations  比价表
POST /api/v1/requests/{id}/award       定标
```

**核心规则在 `domain/sourcing_policy.py`**

```python
MIN_QUOTATIONS = 3


def check_awardable(quotations: list, threshold_fen: int, amount_fen: int) -> list[str]:
    problems: list[str] = []
    valid = [q for q in quotations if q.status == "SUBMITTED" and not q.is_expired]
    if amount_fen >= threshold_fen and len(valid) < MIN_QUOTATIONS:
        problems.append(f"金额超过比价线，至少需要 {MIN_QUOTATIONS} 家有效报价，当前 {len(valid)} 家")
    return problems
```

**注意这里和审批引擎是同一个模式**：规则是纯函数、返回问题列表、阈值来自配置。

定标时把选中的报价标记 `SELECTED`，其余标记 `NOT_SELECTED`，主单 `SOURCING -> AWARDED`。

**验收**：只有 2 家报价且金额超过阈值时定标返回 422；补到 3 家后成功。

#### 8.2 订单与收货（约 3 天）

**接口**

```
POST /api/v1/requests/{id}/orders       由定标结果生成采购订单
GET  /api/v1/orders/{id}
GET  /api/v1/receipts/queue             待收货队列（状态 = ORDERED）
POST /api/v1/requests/{id}/receipts     收货登记（逐行填实收数量）
```

**订单生成时做一件事：把申请明细行复制成订单明细行，带上单价。** 不要把订单明细直接指向申请明细——订单一旦生成就是独立凭证，申请后续不能改它。

**主单状态**：`AWARDED -> ORDERED -> PARTIALLY_RECEIVED -> RECEIVED`

第一版**可以先只支持全部收货**（直接 `ORDERED -> RECEIVED`）。既然只做整单收货，就**先不要在 `TRANSITIONS` 里写 `PARTIALLY_RECEIVED`**——状态机里留一个永远走不到的状态，只会让"合法转移/非法转移"的测试变得没有意义。等真的要做部分收货时，再按 5.5 节 E 的步骤把状态和转移一起加进去。

**验收**：收货数量超过订单数量时返回 422；全部收齐后主单变 `RECEIVED`。

#### 8.3 发票与三单匹配（约 4 天）

**接口**

```
POST /api/v1/requests/{id}/invoices          登记发票（发票号 + 金额 + 税额 + 供应商 + 附件）
GET  /api/v1/payments/queue                  待付款队列（状态 = INVOICED）
GET  /api/v1/requests/{id}/match             三单匹配预检结果
```

**核心在 `domain/settlement_policy.py`**，直接用附录 A.5 的 `match_three_way`。

**但先要把"数据粒度"定死，否则这一步会卡住。** A.5 的函数签名全是标量（整单对整单），而表结构里订单有明细行、收货有多行、发票可以有多张——**两边的粒度对不上**。第一版按下面这样定，改动最小、又能把三单匹配的价值演示完整：

| 匹配项 | 取自哪里（第一版：**订单级**） |
| --- | --- |
| `ordered_qty` | `SUM(purchase_order_lines.quantity)` |
| `ordered_amount_fen` | `purchase_orders.amount`（订单总额） |
| `order_supplier_id` | `purchase_orders.supplier_id` |
| `accepted_qty` | `SUM(goods_receipt_lines.accepted_quantity)`（**所有收货单求和**） |
| `invoice_amount_fen` | `SUM(invoices.amount)`（**所有发票求和**） |
| 发票供应商一致性 | **所有**发票的 `supplier_id` 都等于订单供应商，才判一致 |

**写进文档并明确标注：「明细行级匹配」进"暂时砍掉"清单，M8 之后按需。** 行级匹配（能发现"甲行多收、乙行少收"这种对不上的情况）确实更有价值，但它要求三张表逐行对齐、还要处理行与行之间的数量拆分，是另一套逻辑量级的活。**先订单级跑通，你 M8 不会在"该按行还是按单"上耗掉两天。**

**另外把"匹配在什么时候跑"写清楚——文档里有两处说法不一致**（一处说创建付款单时校验，一处说执行付款时触发）：

| 时机 | 做什么 |
| --- | --- |
| 创建付款单（`PENDING`） | 只校验"主单 = RECEIVED、且至少有一张发票" |
| **执行付款（`pay`）** | **在这里跑三单匹配**，通过才 `spend_budget` |
| 预检接口 `GET /requests/{id}/match` | 只读展示，给前端渲染对比页用，**不做任何状态变更** |

**匹配跑在"执行付款"这一步**，因为那是唯一真正动钱的时刻，也是唯一能保证"校验通过后没有再改单据"的时机。

**设计要点：匹配结果是一个"问题列表"，不是布尔值。** 前端拿它渲染三列对比页：

```
采购订单          收货单           发票
数量 100          实收 100          —
金额 ¥12,000      —                金额 ¥12,300   ← 差异 +2.5%，超出容差
供应商 甲          —                供应商 甲  ✓
                                    ↑ 高亮这一行
```

#### 8.4 付款与归档（约 2 天）

**接口**

```
POST /api/v1/requests/{id}/payments   创建付款单（status = PENDING）
POST /api/v1/payments/{id}/pay        执行付款（触发三单匹配）
POST /api/v1/requests/{id}/close      归档
```

**先把 `payments.status` 的值域定死**（文档里原来只出现过一次 `PAID`，没有定义）：

```
PENDING  →  刚创建，还没付
PAID     →  已执行付款
FAILED   →  付款尝试失败（保留痕迹，允许重新发起）
```

**一笔申请第一版只允许一笔付款**：`UNIQUE(request_id)`。这条和主单状态机只有 `INVOICED → PAID` 一次转移是自洽的；部分付款/分次付款进"暂时砍掉"清单——**如果要改，`UNIQUE` 约束、状态机、以及 M6 那条"一次性结清"的假设必须一起改**，三处是绑定的。

**`pay` 的执行顺序很关键**：

```
1. 校验主单状态 = INVOICED
2. 校验三单匹配无问题（有问题直接 422，返回问题列表）
3. 用条件更新把 payments 从 PENDING 推到 PAID（rowcount != 1 → 409，"该笔付款已被处理"）
4. 按实付金额 spend_budget（已预留 → 已花）
5. 释放差额：release_budget(reserved - actual)，若 reserved == actual 则跳过
6. 主单 INVOICED -> PAID（同样用条件更新）
7. 写 request_events（PAYMENT_COMPLETED，payload 里带实付金额与释放的差额）
8. commit
```

**第 2 步不能省。** 这是"收货才能付款、金额要匹配"这两条业务规则真正的执行点。

**第 3 步也不能省，而且顺序要在 `spend_budget` 之前。** 付款是这个系统里唯一真正"动钱"的操作，两个财务同时点"付款"必须只有一个成功——和 M5 的审批决定、M6 的预算预留是**完全同一个套路**：把状态推进写成条件更新，用 `rowcount` 判定胜负。把它放在 `spend_budget` 之前有个额外好处：**先抢到付款权的那一方才去动预算**，抢输的一方在动钱之前就退出了。

**第 4、5 步是 M6 那条差额规则的落地**：`amount_spent` 只按**实付**增加，预留与实付之间的差额必须显式释放，否则可用额度会永久虚低。这里没有"只做 spend 就够了"的简化空间——两笔流水都要写。

数据库层再加一道兜底：`payments` 上对 `request_id` 建唯一约束（一笔申请只能有一张有效付款单），或者在 `paid_at` 上加"同一 `request_id` 只能有一条非空"的部分唯一索引。

#### 验收标准

- [ ] 走通一笔完整流程：申请 → 审批 → 询价 → 定标 → 订单 → 收货 → 发票 → 付款 → 归档
- [ ] 故意把发票金额改到超出容差，付款返回 422 并列出具体差异
- [ ] 未收货就创建付款单，返回 422
- [ ] **两个人同时点"付款"，只有一个成功，另一个 409；`amount_spent` 只增加一次**
- [ ] 付款成功后，预算的"已预留"减少、"已花"增加，总额不变
- [ ] **预留 1000 元、实付 900 元：`amount_spent` +900、该申请 `amount_reserved` 归零、流水里有 `SPEND 900` 和 `RELEASE 100`**
- [ ] **登记两张发票：`GET /requests/{id}/match` 用的是两张发票的金额之和**（验证订单级粒度）
- [ ] 三单匹配对比页能正确显示三列和差异高亮

#### 常见坑

| 坑 | 说明 |
| --- | --- |
| 容差只写死一个比例 | 应该是"比例和绝对值取较大者"，否则小额单永远匹配不上 |
| 订单明细指向申请明细 | 订单是独立凭证，要复制快照 |
| 付款前不重新校验匹配 | 登记发票时匹配过，付款前还要再校验一次 |
| 付款没有并发保护 | 两个财务同时付款 = 重复付款 + 预算重复转已花；用条件更新 + 唯一约束 |
| **匹配粒度没定，边写边改** | 标量签名对不上多行多张表；先把"订单级 + 求和"写死 |
| **付款只 `spend` 不释放差额** | 预留与实付的差额会永远挂着，可用额度虚低且对不上账 |
| **`payments.status` 没定义值域** | 至少要有 `PENDING / PAID / FAILED`，否则"创建了但没付"的单据在库里无法表达 |
| 主单状态跳级 | 每个接口入口都要校验前置状态 |
| 忘了给采购专员配"跨部门可见" | 采购通常要看全公司；数据级权限的范围过滤规则要在 M3 就定下来（见 M3 第 3 步） |

**产出**：完整的采购履约链，以及三单匹配这个最有演示价值的页面。

### 阶段 M9 · AI 制度助手（2 周）

**目标**：能问"多少钱需要走招标""报销标准是多少"这类制度问题，答案带制度出处，查不到就说查不到。

**前置**：M5（**不依赖 M8**——知识库只用到 M-01 基础设施，履约链写到哪一步都不影响它）。

> 这条前置关系容易看错：文档前面写的是 M9 前置 M8，但按模块地图，M-15 知识助手只依赖 M-01。所以 **M9 是这张路线图里唯一一个可以自由挪动的阶段**——写 M8 写累了想换个口味，就直接把 M9 提前插进来。别因为"文档说它排在最后"而把自己卡在一条直线上。

**涉及模块**：M-15。

**新增表**：`knowledge_docs`、`knowledge_chunks`、`chat_sessions`、`chat_messages`、`chat_sources`（迁移 `0009`）。

#### 重要：顺序不能反

很多人一上手就"接个大模型"，结果做出一个会编造制度条文的玩具。**正确顺序是：先有知识库，再有检索，最后才是模型。**

#### 实施步骤

**第 1 步：启用向量扩展**

```sql
CREATE EXTENSION IF NOT EXISTS vector;

ALTER TABLE knowledge_chunks ADD COLUMN embedding vector(1024);
CREATE INDEX ON knowledge_chunks USING hnsw (embedding vector_cosine_ops);
```

> **维度先定死，否则你会在换真模型的那天才发现要重建全表。** `vector(N)` 里的 `N` 是**列定义的一部分**，换 embedding 模型几乎必然换维度，而 PostgreSQL 改这个维度只能新建列、重灌数据、再建索引。所以：
>
> - 用真实接口（如 DashScope `text-embedding-v4`）→ `vector(1024)`
> - 用本地假 embedding（原项目那套 signed-hashing 是 **256 维**）→ `vector(256)`
>
> **两个数字必须一致。** 定下来之后，在 `knowledge_docs` 上补一列 `embedding_model`（如 `local-hash-256` / `text-embedding-v4`），把每份文档用的是哪个模型、哪个维度记下来——将来混用两种模型的向量，检索结果会静默地变差，而且极难排查。

**第 2 步：文档入库**

```
POST /api/v1/admin/knowledge-docs
```

流程：上传 → 提取文本 → 按 500-800 字切分（带重叠）→ 调 embedding 接口 → 存 `knowledge_chunks`。

本地开发期可以先用一个**假的 embedding**（比如复用原项目的 hash embedding 那套思路），把整条链路跑通，最后一步再换成真实接口。这样能省掉调试期的 API 费用。

**但假 embedding 有一个坑**：它没有语义能力，只能靠字面重合度，所以"多少钱要招标"这种问法大概率检索不到"采购金额超过 10 万元须公开招标"。**别用它的效果来判断你的 RAG 设计好不好**——它只能验证"链路通不通"。真判断效果必须换真模型，那时候记得同步处理上面的维度问题。

另外，切分结果建议在 `knowledge_chunks` 里存下 `chunk_no`、字符起止位置和原文片段，出问题时你能一眼看出是"没检索到"还是"切碎了"。

**第 3 步：检索**

```python
async def search(session, query_embedding, top_k: int = 5):
    statement = (
        select(KnowledgeChunkRecord)
        .order_by(KnowledgeChunkRecord.embedding.cosine_distance(query_embedding))
        .limit(top_k)
    )
    return list((await session.scalars(statement)).all())
```

pgvector 的 `cosine_distance` 直接就是 SQL 排序，不用手写任何距离计算。

**第 4 步：组装 Prompt，强制引用**

```python
SYSTEM_PROMPT = """你是企业采购制度助手。规则：
1. 只根据提供的制度片段回答，不得编造制度条文、金额标准或流程。
2. 回答必须标注引用来源编号，例如「根据《采购管理办法》第 12 条」。
3. 如果提供的片段不足以回答，直接说"制度中没有找到相关规定"，不要猜测。
4. 你是解释工具，不能执行任何采购操作，也不能改变任何单据状态。
"""
```

检索到的片段用编号拼进 user message，回答里带上编号，前端再把编号映射回文档标题和段落。

**第 5 步：流式**

用 `StreamingResponse` 转发上游的 SSE：

```
event: meta     {"sources": [...]}     先发来源，前端可以先渲染引用卡片
event: delta    {"text": "根据..."}    正文逐段推送
event: done     {}
event: error    {"message": "..."}     出错时明确告知，不要静默截断
```

**先发 `meta` 事件**是这个设计的关键：用户能在正文还没出来时就先看到引用来源，信任感强很多。

**第 6 步：溯源策略单独成文件**

`domain/grounded_answer.py` 里放两条规则，都是纯函数、都值得单独写测试。

**规则一：没有依据就不调用模型。**

**检索结果为空或全部低于相似度阈值时，不调用模型，直接返回"未找到相关规定"。**

**规则二：引用必须可信（"有引用"不等于"引用是真的"）。**

光要求模型"标注来源"是不够的——它完全可能引一个不存在的编号，或者嘴上说"根据《采购管理办法》第 12 条"而正文里根本没有引用标记。**这两条都要用纯函数事后校验：**

```python
# domain/grounded_answer.py
import re

CITATION_PATTERN = re.compile(r"\[(\d+)\]")


def check_citation_integrity(answer: str, sources: list[dict]) -> list[str]:
    """校验回答里的引用是否可信。返回问题列表（空 = 通过）。

    sources 是这次检索到的片段，编号从 1 开始。
    """
    problems: list[str] = []
    cited = {int(n) for n in CITATION_PATTERN.findall(answer)}
    valid = set(range(1, len(sources) + 1))

    # 1) 引用了不存在的编号 —— 典型的"编造出处"
    if cited - valid:
        problems.append(f"回答引用了不存在的来源编号：{sorted(cited - valid)}")

    # 2) 有实质内容但一个引用都没有 —— "无出处的断言"
    if not cited and len(answer.strip()) > 20:
        problems.append("回答包含实质内容但没有任何引用编号")

    # 3) 检索到了来源却完全不引用 —— 说明答案不是基于制度片段生成的
    if sources and not cited:
        problems.append("检索到了制度片段，但回答没有引用任何来源")

    return problems
```

**发现问题怎么办？** 第一版最简做法：**不阻断，但把问题记进 `chat_sources` / 日志**，并在回答末尾追加一行"本条回答的来源校验未通过"。等积累了样本，再决定是重试一次还是直接换成拒答。**关键是这个校验必须存在**——原项目的 `GroundedAnswerPolicy` 只保证了"有来源才回答"，没保证"回答里的引用是真的"，**这一条是你能讲出来的、相对原项目的真实增量**。

#### 制度文档的版本与生效时间

`knowledge_docs` 上加两列：

```
version        INT          同一份制度的第几版
effective_from TIMESTAMPTZ  这一版从什么时候开始生效
```

**检索时只取"当前生效版本"**（`effective_from <= now()` 里每份文档取 `version` 最大的那一版）。不这么做的话，制度修订后新旧条文会同时出现在检索结果里，模型会把已经作废的规定和现行规定一起引给你——**对一个"制度助手"来说，这比查不到更糟**。

再加一列 `embedding_model`（如 `local-hash-256` / `text-embedding-v4`），把每份文档用的是哪个模型记下来：换模型时旧向量必须重灌，混用两种模型的向量会让检索结果静默变差。

- [ ] **问文档里没有的问题，明确回答"制度中没有找到相关规定"，不编造**
- [ ] 流式回答逐字出现，不是一次性刷出来

#### 常见坑

| 坑 | 说明 |
| --- | --- |
| 不做检索直接问模型 | 会一本正经地编造制度条文，这是最典型的失败模式 |
| 把整份文档塞进 Prompt | 又贵又慢，而且效果通常更差 |
| 不要求引用 | 无法验证答案真假，用户不敢信 |
| **只要求引用、不校验引用** | 模型可以引一个不存在的编号；"有引用"不等于"引用是真的"，必须事后校验 |
| **制度文档不做版本/生效时间** | 修订后新旧条文同时被检索到，作废规定和现行规定一起被引用——比查不到更糟 |
| 切分粒度太大或太小 | 500-800 字带重叠是比较稳的起点 |
| 先接模型再接检索 | 顺序反了，会做出一个会编造的玩具 |
| 只有一路 RAG 还硬做融合 | 单路就够，不要抄原项目的 RRF 融合，那是双路才需要的 |
| 换 embedding 模型不记版本 | 同一张表里混着两种模型的向量，检索静默变差且极难排查 |

**产出**：一个真正基于自有制度的助手，而不是一个会编造制度的聊天机器人。

### 阶段 M10 · 桌面壳与移动端（1 周）

**目标**：同一套前端代码，打包成 Windows 独立窗口，再打包成 Android APK。

**前置**：M9 或任意你满意的阶段（M10 完全独立，任何时候做都可以）。

**涉及模块**：M-18。

#### 第 1 步：先用最低成本验证形态

写一个 `.bat`，用浏览器的 app 模式打开：

```bat
start msedge --app=http://localhost:5173
```

双击就是一个没有地址栏、没有标签页的独立窗口，看起来已经很像桌面应用了。**先这样用一两天，感受一下是不是你想要的形态。**

#### 第 2 步：Tauri 打包（推荐）

```powershell
npm install -D @tauri-apps/cli
npx tauri init
npx tauri dev     # 开发模式
```

如果不想碰 Rust，换成 **pywebview**：

```python
import webview

# 指向 npm run build 的产物目录，不要指向后端
webview.create_window("采购审批系统", "frontend/dist/index.html")
webview.start()
```

> **这里有个容易踩的坑**：早期写法是 `http://localhost:8000/static/index.html`，但那要求 FastAPI 把前端产物挂成静态目录——而 M7 刚刚明确过"**`uploads/` 不要挂静态目录**"，现在又要为了桌面壳挂一个静态目录，两条纪律就开始打架了，而且后端一旦挂了 `static/`，你很难保证它不会顺手把 `uploads/` 也暴露出去。
>
> 更干净的做法是**让桌面壳直接加载本地产物文件**（上面这样），后端只提供 `/api`。这样后端永远只有一个职责，M7 的验收第 5 条（`uploads/` 直接访问拿不到文件）也不会因为 M10 而失效。

#### 第 3 步：Capacitor 打包 Android

```powershell
npm install @capacitor/core @capacitor/cli
npx cap init
npx cap add android
npm run build
npx cap sync
npx cap open android     # 用 Android Studio 打开，然后 Run
```

**唯一的注意点**：APK 里的前端不能访问 `localhost:8000`，要把 API 地址改成局域网 IP 或公网地址，并且 Android 默认禁止明文 HTTP。开发期可以先用 `adb reverse` 把端口映射过去。

#### 验收标准

- [ ] 双击 `.exe` 能打开，窗口没有浏览器地址栏
- [ ] APK 装到手机上，能登录、能看到待办
- [ ] 桌面端和移动端用的是**同一份 `frontend/src`**，没有分叉出第二套代码

#### 常见坑

| 坑 | 说明 |
| --- | --- |
| 为桌面端单独写一套代码 | 那就失去了 Web 优先的意义 |
| 忘记改 API 地址 | 打包后前端还在找 `localhost`，必然连不上 |
| Android 明文 HTTP | 默认被拦，要么上 HTTPS，要么配 `network_security_config` |
| 一开始就纠结打包 | 打包是最后一步，前 9 个阶段完全可以在浏览器里做完 |

**产出**：可双击运行的桌面应用 + 可安装的 APK。

### 5.3 数据库迁移操作手册

改了模型之后的标准三步：

```powershell
cd backend
.\.venv\Scripts\Activate.ps1

# 1. 生成迁移
alembic revision --autogenerate -m "add quotations table"

# 2. 人工打开 migrations/versions/xxxx_add_quotations_table.py 检查
#    重点看：索引、唯一约束、server_default、字段类型、有没有多余的 drop

# 3. 应用
alembic upgrade head
```

其他常用命令：

```powershell
alembic current              # 当前版本
alembic history --verbose    # 全部历史
alembic downgrade -1         # 回退一步（仅本地，谨慎使用）
alembic upgrade head         # 前进到最新
```

四条纪律：

1. **已经执行过的迁移文件不要再改**，要调整就新建一条。
2. **每次改完迁移，都新起一个空库跑一遍 `upgrade head`**，确保能一条命令建好整个库。
3. `autogenerate` 生成的东西**必须人工看**，它经常漏索引和约束名。
4. **永远不要手动 `ALTER TABLE`**，迁移文件才是数据库结构的唯一事实来源。

### 5.4 测试与自查

跑测试：

```powershell
cd backend
.\.venv\Scripts\Activate.ps1

pytest -m unit                                 # 纯函数：毫秒级，不需要数据库
pytest -m integration                          # 仓库与并发：需要 PostgreSQL 在跑
pytest                                         # 全部
pytest tests/test_approval_engine.py -v        # 单个文件
pytest -k "concurrent" -v                      # 按名字筛选
pytest -x                                      # 遇到第一个失败就停
```

**请务必分成 `unit` 和 `integration` 两档，这是让"先写纯函数"真正省时间的前提。** 写 `pyproject.toml`：

```toml
[tool.pytest.ini_options]
asyncio_mode = "auto"
markers = [
  "unit: 纯函数测试，不连数据库",
  "integration: 需要 PostgreSQL 与迁移的测试",
]
addopts = "-m unit"
```

`addopts = "-m unit"` 是关键：**默认只跑毫秒级的纯函数测试**，于是 `pytest` 这个最常敲的命令永远秒回。要跑全量就显式 `pytest -m ""` 或 `pytest -m integration`。对应地在测试文件顶部加标记：

- `test_rules.py` / `test_approval_engine.py` / `test_state_machine.py` / `test_settlement_policy.py` → `pytestmark = pytest.mark.unit`
- `test_budget_concurrency.py` / `test_api_*.py` → `pytestmark = pytest.mark.integration`

> **一个容易踩的坑**：`pytest-asyncio` 的 `asyncio_mode` 在 1.x 之后建议显式写成 `"auto"`；如果哪天测试报"coroutine was never awaited"，先回来检查这一行。

#### 前端测试：只测三个点，别铺开

后端测试规划得细，前端如果完全不测，`DynamicForm` 和鉴权那两块**改一次崩一次**。但也不要铺开——只补三个高价值点，工具用 `vitest` + `@testing-library/react`：

```powershell
cd frontend
npm install -D vitest @testing-library/react @testing-library/jest-dom jsdom
```

| 测什么 | 为什么是它 |
| --- | --- |
| `DynamicForm.tsx` 按 `form_schema` 渲染 | 数据驱动的组件，逻辑最密、最容易错；给一份 schema 断言渲染出的字段和必填项数量 |
| `ApprovalTimeline` 的三态渲染 | "已完成 ✓ / 当前 ● / 未开始 ○"是纯输入输出，最好测 |
| `api/client.ts` 的 401 处理 | 鉴权是全局的，错一次全线崩 |

**端到端（Playwright）留到 M8 再做**——那时你才有一条值得端到端验证的完整链路（申请→审批→询价→定货→收货→付款），现在给空壳写 E2E 是纯浪费。

```powershell
Select-String -Path backend\app\domain\*.py -Pattern "import (fastapi|sqlalchemy|redis|httpx|minio)"
```

### 5.4.1 演示数据脚本（建议 M2 就写，别拖）

**`scripts/seed.ps1` 不是"以后有空再说"的东西，它是 M2 之后每个阶段验收的前提。** 从 M2 起，你的验收项越来越依赖"库里得先有一些数据"：M2 要"能配一个带 3 条审批规则的品类"，M5 要"500/5000/50000/200000 元四笔申请"，M8 要"全链路走通"。没有脚本，这些验收每次都要你手点几十次界面。

脚本至少要能：建部门树 → 建 8 个角色各一个账号（**`GM` 由一个账号兼任，即同时挂 `ADMIN` + `GM`**）→ 建品类（含完整 `approval_policy`，**阈值记得写"分"**）→ 建供应商 → 给某部门某品类配预算 → 建一笔草稿申请。

三个好处，一个比一个重要：

1. **验收可重复**：任何时候 `alembic downgrade base` + `upgrade head` + `seed.ps1`，就回到已知状态。
2. **并发测试需要它**：M6 那个 `asyncio.gather` 测试必须有确定的 `budget_id` 和金额，靠手点界面造不出来。
3. **演示和截图需要它**：作品集要展示"三单匹配差异高亮"这种页面，空库是截不出图的。

建议写成 `seed.ps1` 调用一个小 Python 脚本（`backend/scripts/seed.py`），用**同一套 ORM 模型**写数据，不要手写 SQL——这样迁移一改，种子数据跟着改，不会悄悄失效。

### 5.5 开发任务手册（常见操作的固定步骤）

这六件事你会反复做。把步骤固定下来，每次照做，就不会漏。

#### A. 加一张新表

1. 在 `records/<聚合>.py` 里加 `XxxRecord`（只有新聚合才新建文件）
2. 如果是新文件，去 `migrations/env.py` 里加一行 import（否则 autogenerate 看不到）
3. `alembic revision --autogenerate -m "add xxx"`
4. 人工检查生成的迁移文件
5. `alembic upgrade head`，再用 `\d xxx` 在 psql 里确认结构
6. **新起一个空库跑一遍 `upgrade head`**，确认能一次建好

#### B. 加一个新接口

按依赖方向从内到外写，顺序不要反：

1. 判断它属于哪个模块、哪个协调者
2. 有业务判断的，先在 `domain/` 写纯函数加测试
3. 在 `repositories/<聚合>_repo.py` 加数据访问方法（只 `flush()`，不 `commit()`）
4. 在 `application/coordinators/<域>.py` 写用例（在这里决定事务边界、编排多个仓库）
5. 在 `boundaries/http/<域>.py` 加路由：Pydantic 模型 + 权限依赖 + 幂等依赖
6. **先在 `/docs` 手工验证一次**，再写对应的 `test_api_*.py`

#### C. 加一个新页面

1. 在 `pages/<角色>/` 建组件
2. 在 `api/hooks/` 加 `useQuery` / `useMutation`
3. 在 `router.tsx` 注册路由 + 角色守卫
4. 在 `Layout.tsx` 的菜单里按角色加一项
5. 手工走四遍：正常流程、越权访问、空数据、后端报错

#### D. 改一条审批规则（不改任何代码）

1. 用管理员账号登录
2. 进入品类配置页
3. 编辑 `approval_policy` 的 `steps`，比如把金额阈值从 10000 改成 5000
4. 保存
5. 新建一笔申请，确认审批链跟着变了

**这条路走通了，说明你的审批引擎是真正数据驱动的。** 如果改规则需要改代码，说明哪里写硬编码了。

#### E. 加一个新状态

1. `domain/enums.py` 加枚举值
2. `domain/state_machine.py` 的 `TRANSITIONS` 加重定向
3. 写测试：合法转移通过、非法转移抛异常、终态无出口
4. 前端 `StatusBadge.tsx` 加颜色和中文标签

#### F. 加一条新业务规则（TDD 三步）

1. **先写测试**：在 `tests/` 里写一个必定失败的测试（红）
2. 在 `domain/` 写纯函数让测试变绿（绿）
3. 再到 `application/coordinators/` 里调用它（重构）

顺序不能反。先写实现再补测试，通常补出来的是"验证实现"，不是"验证需求"。

### 5.6 常见问题排查

| 现象 | 可能原因 | 排查方法 |
| --- | --- | --- |
| 前端请求失败 | 代理没生效（`vite.config.ts` 里没配 `/api`）或后端没起 | 直接 `curl http://127.0.0.1:8000/api/v1/suppliers`：通=后端没问题，是代理/前端的问题 |
| 代理层报 `ECONNREFUSED` / `proxy error` | 后端没起来，或端口不是 8000 | 看后端终端；`netstat -ano \| findstr :8000` |
| 一直跳登录页 | Cookie 没带上 / token 过期 / SameSite 太严 | 浏览器 DevTools → Application → Cookies 看有没有 |
| 接口返回 200 但数据没保存 | 忘了 `await session.commit()` | 检查用例层；用"重启后端数据还在"来验收 |
| 接口返回 200 但报 500 | 提交后访问了已过期对象 | `async_sessionmaker` 加 `expire_on_commit=False` |
| `alembic revision --autogenerate` 生成空迁移 | 模型没被 import | 检查 `migrations/env.py` 里的 import 列表 |
| `connection refused` 连不上数据库 | 容器没起 / 端口不对 | `docker compose ps`，看 db 是不是 healthy |
| 8000 端口被占用 | 上次的 uvicorn 没关干净 | `netstat -ano \| findstr :8000`，找到 PID 后结束进程 |
| `pip install` 了但 import 不到 | 虚拟环境没激活 | 看命令行提示符前面有没有 `(.venv)` |
| `Activate.ps1` 无法加载 | PowerShell 执行策略 | `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned` |
| 改了后端代码没生效 | 忘了 `--reload` | 重启，或者确认启动命令带了 `--reload` |
| 前后端时间差 8 小时 | 时区没统一 | 数据库字段统一用 `timestamptz`，前端负责本地化显示 |
| 并发测试本地过、偶尔失败 | 测试是串行写的 | 必须用 `asyncio.gather` 才有并发 |
| `403` 和 `404` 分不清 | 权限语义没设计好 | 越权用 403；只有"不该让他知道存在"才用 404 |

## 七、风险与调整机制

### 7.1 四个高风险点

| 风险 | 症状 | 应对 |
| --- | --- | --- |
| **M5 审批引擎卡住超 3 周** | 越写越乱，测试也写不出来 | 退回到"先只支持单级审批"，把链路跑通，再回来加多级 |
| **M6 并发测试总是不稳定** | 时过时不过 | 检查是不是串行调用了；确认两个任务用了不同的 session |
| **前端写不动** | 一个页面写三天 | 先不做样式，用最丑的 HTML 表格把功能跑通；Tailwind 最后统一美化 |
| **M8 履约链范围失控** | 边写边加需求 | 回到领域设计第十二节"第一版先砍掉这些"，砍掉部分收货、合同管理、多币种 |

### 7.2 三条调整原则

1. **砍功能，不砍纪律。** 可以不做部分收货、不做审批委托、不做拆单检测；但幂等、乐观锁、条件更新、`domain` 层不 import 框架，这四条一条都不能省——它们才是你真正要学的东西。**另外三条"静默失败类"的约束同样不能省**：审批链不许为空、预留与实付的差额必须显式释放、权限范围必须写进 `WHERE`。它们和上面四条的区别是——**违反了不会报错，只会算错**。
2. **跳阶段，不跳验收。** 如果时间紧，可以不做 M9（AI）和 M10（打包），直接从 M8 收尾。但 M0-M8 的顺序不能乱，也不要把某阶段的验收推后。
3. **遇阻两小时原则。** 一个问题卡超过两小时，就记下来先跳过，做别的。个人项目最怕的是在一个点上耗掉全部热情。

### 7.3 如果时间比预期少

| 你能投入 | 建议范围 | 大概需要 |
| --- | --- | --- |
| 每周 2-3 小时 | M0 → M5 | 5-6 个月 |
| 每周 10-15 小时 | M0 → M8 | 3 个月 |
| 每周 25 小时以上 | M0 → M10 全部 | 6-8 周 |

**不管投入多少，M0 → M5 这一段必须走完。** 走完这一段，你就完整掌握了这套架构的核心；M6 之后是加分项，不是必需项。

### 7.4 进度跟踪

最轻的做法：仓库根目录放一个 `PROGRESS.md`，内容就是第六节那张表，做完一项把 `[ ]` 改成 `[x]`，并在下面追加一行日期和一句备注。

不要一开始就上 Jira、Notion 看板——管理工具本身会消耗掉你做项目的时间。

## 八、一句话总结

**十个阶段，两条主线：M0-M4 修路，M5-M6 建核心，M7-M8 补完整，M9-M10 加彩头。**

如果中途只能记住三件事：

1. **M5 之前不要碰 AI。**
2. **M5 和 M6 必须先写纯函数和测试，再动数据库。**
3. **`domain/` 里永远不出现 `import sqlalchemy`。**
